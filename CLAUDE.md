## Commonly Used Commands

### Environment & Dependencies
```bash
# Set up virtual environment and install dependencies
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# If system Chrome is not installed, install Playwright Chromium
.venv/bin/playwright install chromium
```

### Running the Gateway
```bash
# Start the FastAPI server on 127.0.0.1:8000
./run.sh
# Or directly via uvicorn (note: `python -m uvicorn`, not `.venv/bin/uvicorn`):
.venv/bin/python -m uvicorn server:app --host 127.0.0.1 --port 8000
```

**Why `python -m uvicorn` and not `.venv/bin/uvicorn`**: a venv's console scripts bake in the **absolute** interpreter path from creation time, so a venv that was moved or copied (as this machine's `.venv` was — created under a different project directory) fails with `bad interpreter: No such file or directory` while the venv itself is perfectly usable. `run.sh` therefore resolves an interpreter that can actually `import uvicorn` (project venv first, system `python3` as fallback) and launches it as a module, which needs no shebang and works in both cases. Repairing the moved venv's scripts is `sed`-level work on the stale shebang line; recreating it (`python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt`) is the heavier alternative.

**Before the first start after a long idle period**, run the login pass first: the startup sequence performs a silent token refresh and an initial health probe for each provider, and with stale credentials each of those is a real upstream request — exactly the "automated credential attempt" signature the risk-control line exists to avoid. `.venv/bin/python login.py all` first, then `./run.sh`.

.venv/bin/python tests/test_stream_start_reclaim.py # [C2] All three streaming paths hold upstream resources *before* the response body exists (`execute_chat` has already read the first chunk and holds the node semaphore; `/v1/responses` also calls `load_balancer.acquire()` before building the response), while every release lives in the body generator's `finally`. `aclose()` on a never-started async generator is a **no-op** (its `finally` never runs), so a client that vanishes before the response head leaked LB quota, the node semaphore and the upstream stream on all three protocols -- permanently, until restart. .venv/bin/python tests/test_handshake_budget.py # [BUDGET] A boundary attached to the wrong layer: `GATEWAY_FIRST_CHUNK_TIMEOUT` is enforced **per candidate**, and the dispatch loop walks every candidate in the ring, so the real wait is `candidates x per-attempt` -- measured `failed after 5.0s` with a 1s timer and a dead five-node ring, i.e. **900s** at the default 180s. ## Architecture & Code Structure

The repository is a local multi-protocol API gateway (`server.py`) supporting three standard protocols:
- **OpenAI Chat Completions** (`/v1/chat/completions`, `/chat/completions`)
- **Anthropic Messages** (`/v1/messages`, `/messages`, `/v1/messages/count_tokens`)
- **OpenAI Responses** (`/v1/responses`, `/responses` for Codex CLI)

### Core Subsystems
1. **Peer Capability Rings & Failover Grid (`providers/failover.py`)**:
   - Manages three capability rings: `REASONING`, `FLAGSHIP`, and `SPEED`.
   - Ensures transparent failover before the first token chunk is emitted, preventing half-packet pollution.
   - Dynamic cooldown avoidance for WAF (e.g., RGV587) and 429 rate limits, with exponential backoff (30s~120s).
   - Adaptive pacing, jitter injection, and per-provider concurrency limiting via semaphores.

2. **Self-Healing & Auto-Hotfix Brain (`healing/`)**:
   - `HealthMonitor` (`healing/monitor.py`): Performs non-blocking background probes (interval: `HEAL_CHECK_INTERVAL`, default 300s). Transitions state across `healthy`, `degraded`, `recovering`, and `offline`.
   - `HealingEngine` (`healing/healer.py`): Upon upstream protocol failure, elects the highest-performing healthy model to craft repair prompts and dispatches local CLI repair agents.
   - `AgentRunner` (`healing/agent_runner.py`): Discovers and bootstraps local `claude` or `codex` CLI environments, launching isolated subagents to update code and run tests.

3. **HTTP/2 Connection Pool Management (`providers/http_client.py`)**:
   - Global singleton `AsyncClient` configured with connection limits (max 100 conns, 40 keep-alive, 30s expiry).
   - Multiplexing enabled via `http2=True`.

4. **Atomic Credential Store (`session_store.py`)**:
   - Resolves credentials with priority: `Environment Variables > session/<provider>.json > None`.
   - Thread-safe POSIX atomic write pattern (`os.replace` + `os.fsync`) with strict `0o700` directory and `0o600` file permissions.

5. **Tool / Function Calling & Token Counting**:
   - `anthropic_compat.py`: Balanced bracket parser supporting deeply nested JSON tool calls and XML tool syntax.
   - `responses_compat.py`: Standard OpenAI Responses protocol serializer with `function_call_arguments.delta` / `done`.
   - `base.py`: Token estimation (`_est_tokens`) supporting bilingual CJK weighting.

6. **Smart Session Affinity & State Handoff Engine (`providers/session_affinity.py`)**:
   - Manages LRU and TTL-based conversation tracking to pin multi-turn agent sessions to the same upstream provider.
   - Detects provider degradation, WAF cooldown, or failure and performs seamless cross-model state handoff with heterogeneous upstream conversation ID stripping.
   - Emits `x-session-affinity`, `x-session-handoff-from`, and `x-session-turns` telemetry headers across all protocols.

7. **SingleFlight & Stream Fanout Engine (`providers/singleflight.py`)**:
   - Computes deterministic cross-protocol SHA-256 fingerprints across wire parameters and payload semantics.
   - Leader/Follower flight groups with streaming multi-subscriber fanout and historical replay buffers.
   - Non-streaming response coalescing with `x-singleflight: leader | follower` telemetry headers and zero duplicate upstream calls.

8. **Disconnect Guard & Upstream Reclamation (`providers/disconnect_guard.py`)**:
   - Propagates client disconnects to the upstream async generator and explicitly closes it, releasing the HTTP/2 connection slot and upstream concurrency quota immediately instead of letting an abandoned stream drain quota.
   - Guarantees a terminal state for the SingleFlight flight group on every exit path, including `CancelledError`, and reclaims flight groups whose leader vanished so followers can never hang.
   - Emits `x-disconnect-guard` telemetry headers across all protocols.

9. **Token Count Cache (`providers/token_counter_cache.py`)**:
   - Memoizes the deterministic `/v1/messages/count_tokens` result behind a bounded LRU, eliminating repeated O(n) estimation on long conversations.

10. **Request Lifecycle Finalization & Quota Reclamation (`providers/singleflight.py:terminate_aborted_group`)**:
    - Guarantees the non-streaming SingleFlight leader path terminates its flight group on every exit, including client aborts (`CancelledError` is a `BaseException`, so `except Exception` never fires) — without it the group stays non-terminal forever, hanging every follower.
    - Makes the `load_balancer` concurrency slot deterministically idempotent-released on abort; the Responses endpoint previously had no `finally`, so an aborted request leaked its slot permanently and the balancer would shed away from that provider until restart.
    - See `tests/test_lifecycle.py`.

11. **Risk-Control Ledger & Durable Cooldown (`providers/risk_ledger.py`)**:
    - Persists each provider's cooldown deadline and consecutive-failure count with a POSIX atomic write (`os.replace` + `os.fsync`, dir `0o700` / file `0o600`), so a restart no longer wipes avoidance and immediately re-pokes a node that upstream has already risk-banned (the ban window is only lengthened by retries).
    - Appends every risk/WAF-captcha/auth interception to an auditable JSONL ledger (time, node, HTTP status, severity tier, reason, evidence excerpt), auto-pruned at `GATEWAY_RISK_LEDGER_MAX_LINES`.
    - Severity tiers `auth > ratelimit > waf`: repeated (≥3) auth failures escalate to a long cooldown (`GATEWAY_AUTH_COOLDOWN_BASE` × 2ⁿ, capped by `GATEWAY_AUTH_COOLDOWN_MAX`), while a first auth failure keeps the short legacy cooldown so a re-login never locks a healthy node for an hour.
    - Exposes `risk_ledger` diagnostics via `/v1/diagnostics` and a 24h summary via `/health`; `GATEWAY_DISABLE_RISK_LEDGER=1` degrades to pure in-memory cooldowns. See `tests/test_risk_ledger.py`.

12. **Cooldown-Aware Health Probe Gate (`healing/monitor.py`)**:
    - `HealthMonitor` consults `CooldownTracker` before every probe: a node in a risk-avoidance cooldown is marked `cooling` and the real network probe is skipped entirely. Without this the 300s audit loop re-poked an upstream-banned node every interval, lengthening the ban window — exactly the failure mode the durable ledger guards against, one layer up.
    - Cooling probes neither increment `consecutive_failures` nor trigger self-healing, so a risk ban is never misread as a node fault; `GATEWAY_DISABLE_PROBE_COOLDOWN_GATE=1` disables the gate and `/v1/diagnostics` exposes `healing_status.cooldown_probe_skips`. See `tests/test_probe_gate.py`.
    - **[OPT-018] Read-time cooldown overlay + healer election avoidance**: `ProviderHealth.status` defaults to `healthy`, so before the first probe cycle (or right after a restart) a node sitting in a risk-avoidance cooldown still *reports* healthy — and `pick_healer_model` would elect it as the self-healing brain, dispatching a real upstream completion through a banned account. `get_status()`/`get_all_statuses()` now overlay live cooldown state ("cooling") at read time without persisting it, `pick_healer_model` excludes cooling candidates via `monitor.get_cooldown_remaining()` and records `cooldown_healer_skips`, and when no non-cooling candidate remains it returns `None` so healing is deferred instead of touching the banned node. The single master switch for all cooldown avoidance is `GATEWAY_DISABLE_COOLDOWN_GATE=1` (`GATEWAY_DISABLE_PROBE_COOLDOWN_GATE` remains as a back-compatible alias).

13. **Cooldown-Aware Token Refresh Gate (`server.py:_auto_refresh_stale_sessions`)**:
    - The startup silent token-refresh pass consults the cooldown tracker: a node in a risk-avoidance cooldown is not refreshed (a login/refresh call to an upstream-banned account would only deepen the ban). Deferred nodes are retried by a bounded background thread (`GATEWAY_REFRESH_DEFER_POLL`, `GATEWAY_REFRESH_DEFER_MAX_WAIT`, default 24h) that refreshes once the cooldown clears and otherwise gives up cleanly. See `tests/test_refresh_gate.py`.

14. **Evidence-Driven Adaptive Pacing (`providers/failover.py:compute_pacing_multiplier`)**:
    - The traffic pacer widens each provider's call interval proportionally to its recent risk-control interceptions (weighted `waf > auth > ratelimit`), so a node that just tripped a captcha or 429 is called more slowly until its 6h evidence window drains. This is the "avoidance" half of the ban problem: when a ban cannot be bypassed, slow down before it happens. Cached per provider (`GATEWAY_PACING_EVIDENCE_TTL`, default 60s); `GATEWAY_DISABLE_ADAPTIVE_PACING=1` reverts to the fixed interval. See `tests/test_adaptive_pacing.py`.

15. **Graceful Shutdown Drain (`server.py:_drain_inflight_requests`)**:
    - A pure-ASGI `InflightTrackerMiddleware` counts in-flight requests across the *entire* response (its `await self.app(...)` only returns after a streaming body finishes, unlike `BaseHTTPMiddleware`). On shutdown the lifespan finally-block waits — bounded by `GATEWAY_SHUTDOWN_DRAIN_TIMEOUT` (default 30s) — for that count to reach zero before stopping the health monitor and closing the HTTP client, so a restart no longer severs a half-sent stream (which would make clients retry and re-load upstream). `inflight_requests` is exposed on `/health` and `/v1/diagnostics`. See `tests/test_graceful_drain.py`.

16. **Durable Conversation Deletion Queue (`providers/conversation_gc.py`)**:
    - Anonymous calls (no client `conversation_id`) leave a temporary session in the user's upstream web sidebar, so the gateway deletes it afterwards. The old `asyncio.create_task(provider.delete_conversation(cid))` was fire-and-forget: a failed delete or a process restart silently leaked the session forever. `ConversationGC` now enqueues each deletion in a POSIX-atomic JSON queue (dir `0o700`, file `0o600`) that survives restarts, retries via a background drain (bounded by `GATEWAY_CONVERSATION_GC_MAX_ATTEMPTS`, default 5, then drops with a warning), and drains once at startup to clean up the previous process's leftovers. `GATEWAY_DISABLE_CONVERSATION_GC=1` degrades to the legacy fire-and-forget behavior. Exposed as `conversation_gc` in `/v1/diagnostics`. See `tests/test_conversation_gc.py`.
    - **[OPT-017] Cooldown-aware deletion gate**: a delete is itself a real upstream request, so firing one at a node in a risk-avoidance cooldown is just another channel that keeps touching a banned account. Deletions for a cooling provider are deferred — the entry stays queued and does **not** consume a retry attempt — and are performed by a later drain once the cooldown clears. Mirrors the probe gate (OPT-012) and the refresh gate (OPT-013). `GATEWAY_DISABLE_CONVERSATION_GC_COOLDOWN_GATE=1` reverts; deferrals are exposed as `deferred_by_cooldown` in `/v1/diagnostics`. A gate-query failure never blocks deletion (zero-regression default).

17. **Test Isolation of Durable Stores (`tests/*`)**:
    - The durable stores (risk ledger cooldowns, interception JSONL, conversation GC queue, device identities) resolve to a `tempfile.mkdtemp()` directory under `TESTING=1`, but several legacy suites set fake tokens *without* setting `TESTING`, so a test run wrote fake cooldowns into the developer's real `session/` directory — and, because every `CooldownTracker` restores from the shared ledger singleton, later cases in the same process inherited cooldowns recorded by earlier ones, making results order-dependent (`tests/test_failover.py` was red for this reason). Those suites now set `TESTING=1` (isolated temp dir, zero writes to `session/`), and `tests/test_failover.py` additionally sets `GATEWAY_DISABLE_RISK_LEDGER=1` so it tests pure in-memory cooldown semantics as designed — cross-restart durability has its own suite, `tests/test_risk_ledger.py`. `tests/test_providers.py` was found writing device identities into the real `session/` for the same reason and now sets `TESTING=1` too (see OPT-030).
    - **[OPT-032] The `.env` hole in that isolation**: `server.py` called `dotenv.load_dotenv()` **at import time**, while every suite's "clear all `GATEWAY_*`" prelude runs *before* the import — so one line of real deployment config in `.env` was re-injected into the process *after* the prelude and defeated the isolation entirely. Measured: adding `GATEWAY_QUARANTINE="deepseek:21d"` to `.env` (a legitimate operator declaration) turned `tests/test_quarantine_hardstop.py`'s first case red (`is_quarantined("deepseek")` expected `False`, got `True`) with the code entirely correct — the same "the developer's machine decides the test result" class of order-dependent failure as above, one layer out. `load_dotenv()` is now gated on `TESTING != "1"`, which is the existing convention of every suite that imports `server` (zero new convention, and semantically right: a test process has no "deployment config"). The two suites that import `server` *without* `TESTING` are unaffected.

18. **Operator Quarantine Lease (`providers/quarantine.py`)**:
    - Automatic cooldowns are **capped** (`GATEWAY_AUTH_COOLDOWN_MAX`, default 24h), but a real account-level ban lasts days. When the cap expires the gateway would re-touch a still-banned node and deepen the ban. `QuarantineStore` lets an operator set a durable long-duration lease per provider — resolved by absolute expiry timestamp, POSIX-atomic on disk (dir `0o700`, file `0o600`), re-applied on restart, and expiring lazily. Leases only ever **extend** the avoidance window (reads take `max()`), so a mistyped short lease can never release a banned node early.
    - **Single source of truth**: the lease is folded into `CooldownTracker.get_remaining_cooldown()` / `is_in_cooldown()`, so *every* existing gate honors it with zero extra wiring — health probe (OPT-012), token refresh (OPT-013), conversation GC (OPT-017), healer election (OPT-018), router selection and adaptive pacing.
    - Configuration and admin surface: `GATEWAY_QUARANTINE="deepseek:72h,glm:30m,kimi:2026-10-20T00:00:00"` applies at startup (durations `s/m/h/d` or ISO-8601), `GET/POST/DELETE /v1/admin/quarantine` views/sets/clears at runtime, `GATEWAY_DISABLE_QUARANTINE=1` turns the store off, and `GATEWAY_QUARANTINE_DIR` overrides the location. Exposed as `quarantine` on `/health` (active leases) and `/v1/diagnostics`. See `tests/test_quarantine.py`.
    - **[OPT-021] Hard-stop at the dispatch boundary**: folding the lease into the *cooldown reading* gated probes, refresh, conversation GC and healer election — but **not** the dispatch path. `get_fallback_candidates` only *demoted* cooling nodes, and `execute_chat` dispatched the primary unconditionally, so a node under a 72h lease was still sent real upstream requests on every failover (empirically confirmed for both DeepSeek and Doubao). Quarantine is now a **hard block with semantics distinct from soft cooldown**: a soft cooldown (automatic, capped at `GATEWAY_AUTH_COOLDOWN_MAX`) stays demote-only so a ring where everything is briefly cooling can still make a last-resort attempt — availability is preserved; an operator lease (account-level ban, measured in days) is never dispatched at all, at any point. A quarantined primary is redirected, quarantined nodes are excluded from the candidate set, and if the whole ring is quarantined the request **fails closed** with `503 / err_type="quarantined"`, zero upstream calls, and a message telling the operator how to lift the lease (`overloaded_error` in the Anthropic protocol). `GATEWAY_DISABLE_QUARANTINE_HARD_STOP=1` reverts to demote-only. See `tests/test_quarantine_hardstop.py`.

19. **Post-Avoidance Recovery Probation (`providers/failover.py`)**:
    - **[OPT-022] Canary re-entry after an avoidance episode**: avoidance solves *not touching* a banned node but not *not re-triggering* the ban. When a multi-day ban lifts, the demand that was suppressed for days releases at once — the same burst signature that caused the original ban, immediately re-banning the account. On the first dispatch after an avoidance episode ends (risk cooldown expiry, or a quarantine lease expiring or being cleared), the node enters a **probation window** (`GATEWAY_PROBATION_WINDOW`, default 300s) during which at most **one handshake is in flight** and the pacing interval is multiplied (`GATEWAY_PROBATION_PACING_FACTOR`, default 2.0×). It graduates after `GATEWAY_PROBATION_MIN_SUCCESSES` (default 3) consecutive successes; the window is a *renewal unit*, not a licence to resume at full speed (see the [OPT-028] bullet below).
    - The serialization gate covers *handshake to first chunk* only, not the whole streaming response, and is acquired **before** the concurrency semaphore so requests cannot occupy concurrency slots while queued behind the gate. Because plain 5xx/timeouts are upstream faults rather than account flagging, they never enter probation — no thundering herd to protect against, hence zero regression for existing paths. **[OPT-028] Graduation is evidence-based, never time-based**: the window is only a *renewal unit* — exhausting one renews it (up to `GATEWAY_PROBATION_MAX_RENEWALS`, default 3, i.e. at most `window × 4` gated) with the serialization gate and widened pacing still in force, and once the renewal budget is spent the node is graduated only if it holds positive evidence (≥1 successful handshake); with zero evidence it stays gated, because gating a node that has never been successfully verified costs nothing (no successful handshake means no burst to release) while un-gating hands a completely unproven account full concurrency. The same applies to `GATEWAY_PROBATION_WINDOW=0` ("no time allowance", not "release immediately"); `GATEWAY_DISABLE_PROBATION=1` remains the full off switch. A late success always graduates the node, so the gate can never deadlock. See `tests/test_probation.py`.
    - `GATEWAY_PROBATION_PACING_FACTOR` is applied inside `CooldownTracker.compute_pacing_interval()` (pure, order-correct: base × evidence multiplier × probation multiplier) so it composes with the OPT-014 adaptive multiplier instead of replacing it. Probation state is persisted (`episode_ends`) and survives restarts, since a restart would otherwise be a one-step bypass — the retention horizon covers the **renewed** window, so a restart mid-renewal cannot discard the episode. `GATEWAY_DISABLE_PROBATION=1` turns it off entirely. Telemetry: `x-risk-probation: 1` header plus `probation.active` / `probation.stats` on `/v1/diagnostics` (the stats include derived `renewing` / `awaiting_first_handshake` / `budget_exhausted`, so "is the probation actually doing anything?" is observable rather than assumed). See `tests/test_probation.py`.

20. **Risk-Control Dossier & Avoidance Verdict (`providers/risk_dossier.py`)**:
    - **[OPT-023] All-time interception record + the "can it be bypassed?" answer**: `recent_interceptions()` is a *sliding window* (24h default), which is right for driving real-time avoidance but wrong for answering the operational question "how many times has this provider been intercepted, for what reasons, can it be worked around, does re-login help?". A per-provider ban window is measured in *days*, so the 24h window has almost always discarded the evidence before the ban lifts. The dossier aggregates the **whole** (bounded) ledger: total count, first/last timestamps, severity breakdown, and the last real upstream message verbatim.
    - **Posture derivation, fail-closed**: the facts are scattered across four places — quarantine lease, soft cooldown, recovery probation (OPT-022) and the OPT-014 evidence-driven pacing multiplier. They collapse into one posture, heaviest-wins: `quarantined` > `cooling` > `probation` > `watch` > `clear`, each with a `dispatchable` flag. Only a hard lease is non-dispatchable; a soft cooldown stays dispatchable, preserving the last-resort availability semantics of OPT-021.
    - **Avoidance verdict per severity** (`AVOIDANCE_MATRIX`): each tier answers `technically_bypassable` (never true — no client-side action evades a risk control), `recoverable_by_relogin`, `auto_recovers`, typical span, and a concrete strategy. `auth` (expired token/session) and `waf` (captcha/RGV587) *do* recover via `python login.py <provider>`; `ratelimit` is transient and self-healing, so re-login is pointless; an account-level ban (`ban`) is **not** recoverable by re-login — the ban binds the account, not the token — and the only correct strategy is zero-touch waiting for the platform to lift it. Providers holding a lease are always judged as `ban` regardless of what the ledger says.
    - **Read-only**: querying the dossier never mutates risk state (no lease cleared, no cooldown reset, no ledger append), so it is safe to expose on diagnostic paths. `GATEWAY_DISABLE_RISK_DOSSIER=1` marks it disabled. Telemetry: `risk_dossier_summary` on `/v1/diagnostics`, full detail (plus `?provider=<key>` for a single node) on `GET /v1/admin/risk`. See `tests/test_risk_dossier.py`.

21. **Cross-Provider Risk Correlation (`providers/risk_correlation.py`)**:
    - **[OPT-024] The blind spot of per-account reasoning**: every avoidance mechanism so far (OPT-011..OPT-023) is scoped to a *single* provider account — that account was intercepted, so cool it, quarantine it, watch it. But there is a second cause of interception: **our own client footprint** (header fingerprint, UA, device params, egress IP, request timing) being flagged by the platform. The accounts are then not intercepted independently — they are multiple symptoms of one root cause. The two causes demand **opposite** responses: for a single-account cause "switch to another node and keep going" is correct; for a systemic cause it is useless and actively harmful, because the new node gets flagged on the same footprint and you simply burn the remaining accounts one by one. Per-account reasoning can never see this layer — it explains each interception as "this provider's risk control is strict" and hands over all five accounts in sequence.
    - **Correlation is measured in *distinct providers*, not interception counts**: one account intercepted a hundred times is still a single-account problem. The detector scans the ledger (read-only) over `GATEWAY_RISK_CORRELATION_WINDOW` (default 900s) and computes the largest number of distinct providers intercepted inside any `GATEWAY_RISK_CORRELATION_BURST_WINDOW` sub-window (default 120s), using a two-pointer sliding window so it stays O(n).
    - **Grading, strongest signal first**: `systemic` when the burst holds `GATEWAY_RISK_CORRELATION_SYSTEMIC_MIN` (default 3) distinct providers — several different accounts hit within minutes is essentially impossible from independent causes; else `widespread` when `GATEWAY_RISK_CORRELATION_WIDESPREAD_MIN` (default 3) distinct providers appear in the window but not as a burst; else `localized`; else `none`.
    - **Global pacing governor**: `systemic` multiplies every node's interval by `GATEWAY_RISK_CORRELATION_SYSTEMIC_FACTOR` (default 2.0), `widespread` by `GATEWAY_RISK_CORRELATION_WIDESPREAD_FACTOR` (default 1.25). This composes as a fourth factor in `CooldownTracker.compute_pacing_interval` and in `TrafficPacer`, so it multiplies with the OPT-014 evidence factor and the OPT-022 probation factor rather than replacing either. The multiplier is TTL-cached (`GATEWAY_RISK_CORRELATION_CACHE_TTL`, default 15s) because the pacing path is hot, and defaults to **1.0** whenever there is no correlation evidence — zero regression.
    - Each grade carries a playbook stating explicitly whether `rotate_node_helps` and `per_account_avoidance_helps`. Telemetry: `risk_correlation` on `/v1/diagnostics`, full report at `GET /v1/admin/risk/correlation`. `GATEWAY_DISABLE_RISK_CORRELATION=1` disables. See `tests/test_risk_correlation.py`.

22. **Whole-Ring Credential Outage & Fast-Fail (`providers/credential_watch.py`)**:
    - **[OPT-025] Live evidence — the outage was misdiagnosed as a WAF ban**: the risk ledger recorded 335 interceptions over 80 minutes, of which **312 were `auth` (401), not `waf`**, with all five providers returning 401 in the *same second*, repeating every ~7 minutes. Five independent token expiries in the same second is not a coincidence: the real sequence is **one client request failing over through all five nodes, every node rejecting on an expired credential**, so a single request emits five auth records in one second. The ring has zero serving capacity — failover cannot possibly succeed.
    - **The storm is itself the risk trigger**: with no usable credentials the gateway still walked all five nodes for every client request. 335 failed requests carrying invalid credentials in 80 minutes is exactly the *automated credential attempts* signature upstream WAFs score on — the storm was itself inflating the risk score, plausibly contributing to the bans. So the correct behaviour is not "retry harder" but **stop immediately**, which is precisely what a per-node cooldown cannot express: each node cooling independently still lets the whole ring be walked.
    - **Semantics distinct from everything else**: a soft cooldown is per-node, time-capped and self-healing; a quarantine lease (OPT-020/021) is per-node, operator-declared and measured in days. A credential outage is **ring-wide**, needs no operator declaration, and recovers the instant credentials are renewed — it is not "this node has a problem" but "we have no usable credentials", so the remedy is re-login, not avoidance. Detection is by **distinct providers** (as in OPT-024, not by failure count): `GATEWAY_CREDENTIAL_OUTAGE_MIN_PROVIDERS` (default 3) different providers auth-failing within `GATEWAY_CREDENTIAL_OUTAGE_WINDOW` (default 300s) trips it.
    - **Fast-fail at the dispatch boundary**: checked at the top of `execute_chat`'s dispatch loop — *before* the OPT-021 quarantine branch and before any provider is even instantiated — so the request is refused with `503 / err_type="credential_outage"` and **zero upstream calls** (`authentication_error` in the Anthropic protocol, the closest enum, since Anthropic has no credential-outage type). The message names the dead providers and tells the operator to run `.venv/bin/python login.py all`.
    - **Never wedges**: the state carries a TTL (`GATEWAY_CREDENTIAL_OUTAGE_TTL`, default 120s) after which exactly one request is let through as a probe; if the ring is still 401ing, the very first failure re-arms it. Probing therefore degrades from "once per client request" to "once per TTL" — the storm is flattened with no possibility of the state deadlocking into permanent refusal. A single success (`record_success` → `note_success`) drops that provider from the failed set, so capacity returning below the threshold **immediately resumes dispatch** (fail-open). `GATEWAY_DISABLE_CREDENTIAL_WATCH=1` disables it (and `GATEWAY_DISABLE_RISK_LEDGER=1` co-disables, matching the quarantine convention so pure in-memory cooldown suites are unaffected). Telemetry: `credential_outage` on `/v1/diagnostics`, `GET/DELETE /v1/admin/credential-outage` to inspect the state and to lift it immediately after re-login. See `tests/test_credential_watch.py`.

23. **Credential Renewal Detection & Cause-Scoped Avoidance Release (`providers/credential_renewal.py`)**:
    - **[OPT-026] The 24-hour tail after the storm**: `record_failure` escalates auth failures as `GATEWAY_AUTH_COOLDOWN_BASE`(1800s) × 2ⁿ, capped at `GATEWAY_AUTH_COOLDOWN_MAX`(86400s). The real ledger shows 54/54/54/87/60 auth failures per node — **every one hit the 24h cap**, and the state is persisted and restored across restarts. So after the storm the five nodes each stay frozen for a full day.
    - **Why the escalation becomes wrong once the cause is gone**: it punishes *holding one dead credential and retrying with it* — which is correct, since every retry is another "automated credential attempt". But once the credential is renewed the offence no longer exists; continuing to freeze punishes the *already-repaired system*. `get_remaining_cooldown()` still returns 24h → probes skipped, healer election excludes the node, routing demotes it, and worst of all `server.py:_deferred_refresh_after_cooldown` **defers the silent token refresh itself by up to 24h** — i.e. the state the credential failure created locks the only mechanism that can repair it. Reverse check: OPT-023's dossier already answers `auth → recoverable_by_relogin = True`, so the gateway tells the operator "re-login fixes this" and then keeps avoiding the node for 24h after they do it.
    - **Renewal detection by content fingerprint**: on every auth failure the credential source (`session/<provider>.json`) is fingerprinted — `sha256(token|cookie|captured_at|user_id|device_id)`, degrading to `meta:mtime_ns:size` when unparseable. The fingerprint is persisted with the cooldown, so "re-login first, restart second" is still recognised. `Session.save()` writes atomically via `os.replace` and refreshes `captured_at` on every capture, so any real re-login necessarily changes the fingerprint. The tracker only *answers* "did the credential change"; the state mutation lives in `CooldownTracker.release_auth_avoidance()`.
    - **Cause-scoped, fail-closed release**: only a cooldown whose most recent severity is `auth` may be released (the severity is persisted alongside the cooldown; when the record is missing — state predating this mechanism, e.g. the real ledger's five 24h freezes — it degrades to a *read-only* query of the ledger's most recent interception for that node, still cause-scoped). A node holding an operator lease is **never** released (a lease is an account-level ban; re-login is useless). A `waf`/`ratelimit` cause is **never** released on its behalf. No record / unreadable credential / unchanged fingerprint → "not renewed". Release re-enters via the OPT-022 recovery probation (serialized canary + widened pacing), because the demand suppressed for days releases at the moment of renewal with the same burst signature the probation exists for.
    - **Unblocks the repair chain**: releasing zeroes `get_remaining_cooldown()`, so the OPT-013 refresh gate stops deferring the silent token refresh — the one automatic repair path. Startup runs the scan (`await cooldown_tracker.release_renewed_credentials()`), because "re-login + restart" is the common operator flow. `GATEWAY_DISABLE_CREDENTIAL_RENEWAL=1` disables it (and `GATEWAY_DISABLE_RISK_LEDGER=1` co-disables, matching the quarantine convention). Telemetry: `credential_renewal` on `/v1/diagnostics`, `GET /v1/admin/credential-renewal`, `POST /v1/admin/credential-renewal/scan` (body `{"providers":[...]}` for env-var credentials with no file to fingerprint), and `DELETE /v1/admin/credential-outage` now also releases the auth avoidance of the cleared providers. See `tests/test_credential_renewal.py`.

24. **Account-Level Ban Inference & Self-Clearing Auto Lease (`providers/failover.py` / `providers/quarantine.py`)**:
    - **[OPT-027] The loop OPT-026 left open**: OPT-026 releases the auth avoidance the moment a renewed credential appears — correct, but *if the node still 401s* the gateway re-dispatches, takes another 401, re-escalates by 2ⁿ back to 24h, and OPT-026 releases again on the next scan. Each round touches the upstream account once more, and the loop never terminates on its own. That is exactly the failure mode the standing constraint forbids: a banned node must be **zero-touched**, not periodically poked.
    - **401 has two causes whose remedies are opposite**: (a) *credential expiry* → the fix is re-login (`python login.py <provider>`), which OPT-026 already handles; (b) *account-level ban* → re-login is **useless** (the ban binds the account, not the token), and the only correct action is zero-touch waiting for the platform to lift it. Treating (b) as (a) is precisely how a retry loop keeps re-triggering a ban. So the mechanism is worthless without a **discriminator**, and the gateway already possesses it: *"the credential has provably changed and the node is still rejected"* — this **excludes** explanation (a), which leaves (b). This is the machine-readable form of the operator's question "现在受到风控的 LLM 能通过重新登陆恢复使用吗": for DeepSeek the answer is no.
    - **Evidence, reset per credential**: `CredentialRenewalTracker.note_auth_failure()` now returns whether the failure landed on a credential *different from the last one it recorded* — and it must decide this **before** overwriting the record, or the evidence destroys itself on every call. `CooldownTracker` keeps `_fresh_credential_rejected[provider]` as a counter, **reset to 1 (not incremented)** each time a newer credential appears: every renewed credential gets its own chance, so one earlier rejection can never accumulate onto a credential that has never actually been tried. Reaching `GATEWAY_BAN_INFERENCE_MIN_FAILURES` (default 2) applies an **auto lease**.
    - **Semantics distinct from all four existing avoidance kinds**: a soft cooldown is the gateway's own inference about *load*; an operator lease is a human declaration about *policy*; a credential outage is ring-wide about *capacity*; an auto lease is the gateway's own inference about *the account itself*. It is marked `source="auto"` in `QuarantineStore`, which is persisted per provider (dir `0o700` / file `0o600`), so a restart cannot launder an auto lease into an undeletable one, and `release_auto_lease()` structurally **cannot** release an operator lease — precedence runs one way only (an operator declaration always overwrites an auto mark, never the reverse; an unknown/missing source is conservative-`operator`). Duration `GATEWAY_AUTO_QUARANTINE_DURATION` (default 259200s = 72h), shorter than the multi-day manual leases because an inference deserves less authority than a human's.
    - **Self-clearing, because an inference must be revisable**: the whole justification for the lease is "we tried a renewed credential and it was still refused"; a *newer* credential invalidates exactly that evidence, so the auto lease is lifted automatically when the fingerprint moves on, the evidence map is cleared, and the node re-enters via the OPT-022 recovery probation. Without this one wrong inference would freeze a perfectly-repaired account for 72h. Operator leases are exempt: they are never auto-lifted, and the fingerprint-comparison logic never touches them.
    - **Zero-touch dispatch**: the auto lease rides the existing OPT-021 hard-stop (folding the lease into the cooldown reading means every gate — probe, refresh, conversation GC, healer election, routing — honours it with no extra wiring), so an inferred ban produces **zero upstream calls** at any point, including as a failover fallback. `GATEWAY_DISABLE_BAN_INFERENCE=1` disables inference (and it co-disables with quarantine/ledger, whose disable switches would leave the conclusion nowhere to live). Evidence, auto-lease fingerprints and the rejection counts persist across restarts, so a restart is never a bypass. Telemetry: `ban_inference` on `/v1/diagnostics`, `GET /v1/admin/ban-inference` for the report, `DELETE /v1/admin/ban-inference` to lift auto leases early once the operator confirms the platform has lifted the ban. See `tests/test_ban_inference.py`.

25. **Severity-Aware Avoidance Duration & Human-Gated Release (`providers/failover.py` / `providers/credential_renewal.py`)**:
    - **[OPT-029] The tier that requires a human had the least patience**: `record_failure` put `waf` and `ratelimit` in the *same* escalation branch (`base × 1.2**min(n-1, 3)`, capped by `GATEWAY_WAF_COOLDOWN_MAX` 900s), so a repeated captcha interception **saturated at ~78s on the 4th failure and never grew again** — the node was re-poked every ~78s forever — while `auth` (whose remedy is a trivial automated re-login) escalated to 24h. That is the semantics exactly inverted: per the OPT-023 dossier, `waf` is the *only* tier whose `auto_recovers` is `False` and whose remedy is a human completing a slider, yet it received the *most* frequent automated retries. Every such retry is another "automated attempt" on a captcha-flagged account — the same signature as the OPT-025 storm, but per-node and self-sustaining, and in direct conflict with the standing constraint of never deepening another vendor's risk score.
    - **Escalation**: repeated `waf` (≥ `GATEWAY_WAF_ESCALATION_MIN_FAILURES`, default 3) escalates by powers of two (`GATEWAY_WAF_LONG_COOLDOWN_BASE` 3600s × 2ⁿ, capped by `GATEWAY_WAF_LONG_COOLDOWN_MAX` 86400s), structurally identical to the auth tier (measured 45 → 54 → 3600 → 7200 → 14400 s). A *single* human-verification hit is never escalated, and a non-captcha risk hit keeps the legacy short cooldown. `ratelimit` is deliberately untouched: it is transient and self-healing, so "retry once it clears" *is* the correct recovery, and its short cooldown and cap are value-for-value what they were before — verified as the suite's first case.
    - **The release, without which the escalation is a dead end**: a long avoidance is only acceptable if a human can end it, and the only observable evidence that a human intervened is that the **credential file changed** (a completed `login.py`/slider necessarily refreshes the token, and `Session.save()` refreshes `captured_at`, so the fingerprint always moves). A WAF interception therefore records a credential baseline (`CredentialRenewalTracker.note_interception`) and the release path accepts `auth` **and** `waf` (`_RELEASABLE_BY_RENEWAL`) — without this half the escalated avoidance would be a permanent freeze, i.e. the self-lock OPT-026 already fixed wearing a different cause. `ratelimit` is never releasable (re-login means nothing there), an operator quarantine lease still wins over every release path, and a released node re-enters the OPT-022 probation so it is re-verified by a serial canary rather than flooded.
    - **The ban-inference discriminator is not polluted**: `note_interception` records *only* a baseline — it does **not** return "was this failure on a renewed credential", which is OPT-027's discriminator and is strictly scoped to 401s. Folding human verification into it would fire auto leases for an entirely different cause; `tests/test_waf_escalation.py` asserts the ban-inference path stays empty and no auto lease is applied.
    - **Dossier advice branches on the cause**: the OPT-023 cooling posture used to hand out one generic recommendation, so an escalated `waf` node inherited `ratelimit`'s "no human intervention needed" — telling the operator to wait out a node only a human can fix. The dossier now exposes `cooldown_cause` per provider and branches: `waf` → a human must complete the verification (`.venv/bin/python login.py <provider>`, and explicitly **do not** script the captcha); `auth` → re-login; `ratelimit` → no human needed and explicitly no re-login. Telemetry: `cooldown_cause` on the dossier entry. See `tests/test_waf_escalation.py`.
26. **Stable Per-Node Device Identity & Self-Consistent Client Hints (`providers/device_identity.py`)**:
    - **[OPT-030] The fixable half of OPT-024's systemic cause**: OPT-024 concludes that several different accounts intercepted inside one burst window cannot be independent — the root cause is *our own client footprint* (headers, UA, device params, egress IP, timing), where rotating nodes is useless and per-account avoidance actively harmful. Its remedy is a **global pacing slowdown**, which treats the symptom: the footprint itself is untouched. This optimizes a root cause inside that footprint that is both verifiable and repairable.
    - **Evidence (reproduced)**: `_make_provider` is called from `execute_chat`'s dispatch loop, so a **fresh provider object is constructed on every dispatch attempt** — and Kimi's `X-Msh-Device-Id` (plus `X-Msh-Session-Id`) and GLM's `X-Device-Id` (which also prefixes `X-Request-Id`) were built as `device_id or random.randint(...)` / `device_id or uuid.uuid4().hex`, with the session file's `device_id` empty (login only captures the ByteDance TEA `web_id`, for Doubao). So **every single upstream request from Kimi and GLM announced a brand-new device** (measured: three consecutive constructions gave three different ids). Qwen and Doubao are stable *with* a cookie, but in the env-token deployment the credential-renewal admin API explicitly supports, Qwen regenerated `x-device-id` per request, Doubao fell back to the **current millisecond**, and its `_fp` re-randomized per request.
    - **Why this is risk-control-grade, not hygiene**: "one account + one stable cookie/token + a different device on every request" is among the strongest automation signatures an anti-bot system can score. A real browser's device identifier is *constant* within a profile; it varying per request can only come from automation. It is also the *strongest* thing we could do to trip the four vendors the standing constraint says must be protected — Kimi and GLM are two of them.
    - **The fix — identity is minted once and reused forever**: `stable_device_id(key, generate)` persists per-node identities in `session/device_identity.json` (dir `0o700` / file `0o600`, POSIX atomic `os.replace` + `os.fsync`), so the caller's random expression runs exactly **once**; every later request reuses the stored value. It is **decoupled from credentials on purpose** — a real device is still the same device after a re-login, so a token refresh or re-login must *never* change it (this is a deliberately separate evidence chain from OPT-026/OPT-029's credential fingerprint).
    - **Zero regression by construction**: an explicitly passed `device_id` (the captured truth) and an identity already present in the cookie always win — the store only takes over the cell that *would have* been randomized. Identities are **node-scoped and mutually distinct** (a shared id would itself be a new correlation signal across platforms, i.e. exactly OPT-024's shared footprint) and slot-scoped within a node. Unreadable/corrupt storage degrades to the caller's generator without raising, and `GATEWAY_DISABLE_DEVICE_IDENTITY=1` restores the pre-fix behavior exactly. Diagnostics expose only a 6-char prefix plus age and counters (`created` / `reused` / `revived_from_disk` / `bypassed`) — device identifiers are the most sensitive field an anti-bot system keys on, so a screenshot or log line must not leak a complete one.
    - **Self-consistent client hints (same insight)**: GLM hardcoded `Sec-Ch-Ua: "Chromium";v="130"` alongside a *dynamic* `User-Agent`. It matched only because Playwright's bundled Chromium happens to be 130 — the moment the browser updates, the UA says Chrome/141 while the hint still claims 130, a **self-contradictory fingerprint** that modern anti-bot stacks cross-check. The hints are now derived from the effective UA (`Sec-Ch-Ua`, `Sec-Ch-Ua-Mobile`, `Sec-Ch-Ua-Platform`), and for a non-Chromium UA they are **omitted entirely** — which is what a real Firefox/Safari does, and therefore the only self-consistent choice. See `tests/test_device_identity.py`.
27. **Long-Avoidance Hard-Stop at the Dispatch Boundary (`providers/failover.py`)**:
    - **[OPT-031] The gap between OPT-021 and OPT-025**: the dispatch loop had exactly two pre-flight gates — OPT-021 blocks *operator/auto leases* (`is_quarantined`) and OPT-025 blocks a *whole-ring 401 outage* (`credential_watch`). Between them lies **a ring where every node sits in a long avoidance of mixed causes** (some escalated `waf`, some escalated `auth`, hours-to-days). `apply_pacing_and_acquire` only sleeps the *pacing interval* — it never waits out the cooldown — and `get_fallback_candidates` merely **demoted** cooling nodes, so every client request still walked all five nodes, producing several fresh interceptions for a request that could not possibly succeed. This is exactly the OPT-025 storm shape (the storm *is* the risk trigger), with the cause moved from 401 to waf/auth escalation.
    - **The design tension, and the only defensible discriminator — duration**: OPT-021 deliberately keeps soft cooldowns **demote-only** "so a ring where everything is briefly cooling can still make a last-resort attempt — availability is preserved". A blanket "all cooling → fail closed" would contradict that decision. The discriminator is *how long*: a **short** soft cooldown (rate-limit backoff, seconds-to-two-minutes) is worth one last-resort attempt; a **long** avoidance (escalated auth/waf, hours) is not — upstream has already answered with *repeated* interceptions.
    - **The threshold is a vacuum band, not a tuned constant**: the short-cooling max is the code-level cap `GATEWAY_WAF_COOLDOWN_MAX` (default 900s; the rate-limit exponential also saturates at `base × 1.2³`, deepest reachable 103.7s), and the escalation floor is `GATEWAY_AUTH_COOLDOWN_BASE` (default 1800s) with WAF escalation starting at 3600s. The band is `(900, 1800)` and `GATEWAY_LONG_AVOIDANCE_THRESHOLD` defaults to **1200**, its value **clamped** to `[short_cap + 1, escalation_floor - 1]` so a misconfiguration can neither invade the short-cooling band (eating OPT-021's last resort) nor reach the escalation floor (re-opening the storm). Both bounds are *strict* with a 1-second margin — taking the threshold as exactly 1800 was measured to flip the verdict immediately, because the escalated cooldown *is* 1800 and the read-back is 1799.99. `tests/test_long_avoidance.py::test_threshold_sits_in_the_gap` *proves* the band rather than assuming it.
    - **Semantics distinct from all neighbours**: a long avoidance is neither a lease (no human declared it, it is not account-level by itself) nor a credential outage (it is not ring-wide nor 401-only) — it is *the same node*, just given a duration long enough that touching it again is worse than waiting. `is_in_long_avoidance()` therefore treats it as a **hard block**, never a demote: long-avoidance nodes are excluded from `get_fallback_candidates` (short cooling stays demoted, unchanged), a long-avoiding primary is **redirected** to a healthy candidate, and if the ring has no non-avoiding member the request **fails closed** with `503 / err_type="ring_exhausted"` (Anthropic `overloaded_error`), **zero upstream calls**, and a message naming each node with its cause and remaining hours plus the per-cause remedy.
    - **The cause must not mislead the operator**: `long_avoidance_cause()` reports `ban` for anything holding a lease (re-login is useless — the ban binds the account) and only falls back to the soft-cooldown severity otherwise, so the advice never tells an operator to re-login against a banned node — the same class of error OPT-026/027/029 each fixed. `GET /v1/diagnostics` exposes `long_avoidance` (`enabled` / `threshold_seconds` / `avoiding` / `stats`), and the OPT-023 dossier gains a `long_avoidance` posture between `quarantined` and `cooling` with `dispatchable: false`, so the dossier never claims a node is dispatchable when the dispatch boundary hard-blocks it. `GATEWAY_DISABLE_LONG_AVOIDANCE_FAST_FAIL=1` restores the walk-the-ring behaviour exactly. See `tests/test_long_avoidance.py`.
28. **Zero-Upstream Dispatch Dry-Run (`providers/failover.py:audit_dispatch`)**:
    - **[OPT-032] The confirmation cost after every operator action**: the whole avoidance line (OPT-021…031) makes the gateway *refuse* to dispatch to a banned node, but nothing let an operator confirm that a declaration had actually taken effect without sending a real request and observing which nodes got touched — which is exactly the "spend an upstream touch to buy an answer" habit the line exists to eliminate. This was measured, not hypothesised: after declaring the DeepSeek ban, confirming it required a hand-written script that injected a fake provider factory and posted through `TestClient`. That confirmation is a *daily* action (after every lease change, env change and restart), and none of the five admin endpoints answers it — they all report a node's *posture*, whereas the question is "what is this request's dispatch decision right now".
    - **Read-only, zero upstream calls, and provably so**: `audit_dispatch(provider_key, wire_model)` never instantiates a provider — it only asks the **same gate predicates** the dispatch loop asks, in the **same order** (ring-wide credential outage → operator disable `DISABLED_PROVIDERS` → operator/auto lease → long avoidance), because "which gate fires first" is itself the information an operator needs. `GET /v1/admin/dispatch-audit?model=<alias>` resolves the alias and returns `upstream_calls: 0`, per-node `blocked_by` (`credential_outage` / `disabled` / `quarantine` / `long_avoidance`) with remaining time and cause, plus `predicted_primary_dispatchable` / `predicted_redirect_target` / `predicted_fail_closed` / `predicted_err_type`. `tests/test_dispatch_audit.py::test_endpoint_never_instantiates_a_provider` proves the zero-upstream claim *constructively* by swapping `_make_provider` for an implementation that raises.
    - **No drift, by construction and by test**: the redirect target is taken from the real `get_fallback_candidates()` — **not** from "the first dispatchable ring member". Measured: those differ, because the candidate list is sorted by `(cooldown, risk level, failure count)`, so `glm` can precede the ring-earlier `qwen`; the first version of this feature predicted `qwen` while the real dispatch served `glm`. The suite now asserts the prediction against what `execute_chat` actually does — both the redirect target (from the observed touched-node set) and the thrown `err_type` / status — so a dry-run that stops matching reality fails the build instead of becoming a more convincing lie. For the same reason the audit **raises** on an unresolved model alias rather than silently answering about a provider key that does not exist (which would report a banned node as dispatchable).
    - **Scoped honestly rather than completely**: it deliberately does not simulate load-balancer selection or session affinity, so the fields are named `predicted_*` and the payload carries a `scope_note` saying exactly that. Re-implementing each protocol's pre-dispatch pipeline here would recreate the "documented behaviour drifts from real behaviour" defect this codebase keeps fixing; saying clearly what it does not cover is the better trade.
    - Idempotent and side-effect-free (verified by `test_audit_is_read_only`: no lease changed, no cooldown reset, no ledger append), so it is safe on any diagnostic path.

29. **Single Gate Definition & Operator-Disable Hard-Stop (`providers/failover.py:evaluate_dispatch_gate`)**:
    - **[OPT-033] The bug OPT-032's own dry-run exposed — a gate with two copies**: OPT-032 made "preview == dispatch" a property enforced by *tests* (predicted redirect X ⇒ real dispatch must serve X). That is one step better than two code paths that happen to agree, but tests only cover the cases you thought of. This one was missed and found by measurement: `execute_chat` had **no gate at all** for `DISABLED_PROVIDERS` (the operator's declaration that a node is not part of this deployment), while the dry-run reported such a node as `blocked_by="disabled"` and predicted a redirect to `glm`. Reproduced: `DISABLED_PROVIDERS=deepseek` + `execute_chat("deepseek", …)` dispatched **deepseek** (`TOUCHED=['deepseek']`) — the request went straight into a node the operator had explicitly disabled. The load balancer and session affinity both honoured it; the dispatch boundary, which is the last line and must be self-protecting (the OPT-021 rationale verbatim), did not. The cause was not a missing `if`: the gate **order** existed in two copies, one in the dispatch loop and one in `audit_dispatch`.
    - **The fix is to have one copy**: `FailoverRouter.evaluate_dispatch_gate(provider_key, outage_active)` is now the single definition of the gate order (ring-wide credential outage → operator disable → operator/auto lease → long avoidance), returning `dispatchable` / `blocked_by` / `remaining_seconds` / `cause`. `execute_chat`'s loop selects its handling branch from `gate["blocked_by"]` instead of re-deriving the predicates, and `audit_dispatch` asks the same function — so "preview == dispatch" is now **structural**, not merely tested. `tests/test_dispatch_gate.py::test_dispatch_decision_is_derived_from_the_single_gate_definition` proves the structural claim the only way that really proves it: it **rigs the single gate** to claim a healthy node is blocked and asserts the real dispatch then refuses that node — a dispatch loop that had kept its own copy would sail past the tampering and fail the test.
    - **The new gate is a hard block, never a demote**: `DISABLED_PROVIDERS` is an operator declaration, the same authority tier as a quarantine lease, so it follows OPT-021: a disabled primary is **redirected**, disabled nodes are excluded from the candidate set, and if the ring holds no non-disabled member the request **fails closed** with `503 / err_type="disabled"` (`overloaded_error` in the Anthropic protocol, alongside `quarantined` / `ring_exhausted`), **zero upstream calls**, and a message naming the effective disabled set. Availability is preserved by construction: only an *explicit* declaration blocks, and short soft coolings keep OPT-021's demote-only "last resort".
    - **One reading per configuration**: `server._is_provider_healthy` (the session-affinity availability check) used to parse `DISABLED_PROVIDERS` **itself**, while `CooldownTracker` snapshotted the same variable into a set at construction — the same configuration interpreted in two places, which disagree the moment it changes inside a running process (the defect class this codebase keeps fixing, cf. OPT-026/029/030). It now delegates to `CooldownTracker.is_disabled()`, which is the single judge and takes the **union** of the programmatic set and the live env read — merging conservatively (a second declaration can only disable more), deliberately preserving the live-env behaviour that `tests/test_affinity.py`'s node-handoff case depends on.
    - Telemetry: `/v1/diagnostics` gains `dispatch_gates` (`disabled_providers` — the effective union — plus `gate_blocks`, a per-gate refusal histogram, so "which gate is carrying the refusals" is observable rather than inferred from logs, and `stats` = redirects / zero-upstream fast-fails). `audit_dispatch` members also carry informational `disabled` / `quarantined` / `in_long_avoidance` flags, so a node whose own state is masked by the ring-level credential-outage gate is still visible. See `tests/test_dispatch_gate.py` (10 cases).

30. **Operator-Disable Propagation to Every Upstream Self-Maintenance Channel (`providers/failover.py:touch_avoidance_reason`)**:
    - **[OPT-034] The same declaration, honoured by only some channels**: `DISABLED_PROVIDERS` is the operator's statement that a node is not part of this deployment. The dispatch boundary honours it (OPT-033) and so does the health probe (OPT-012) — but the other three self-maintenance channels only asked about *cooldown*, never about *disable*. A node declared out of scope that happened to hold no cooldown was therefore still touched upstream for real: a startup silent token refresh (**a real upstream login request**), the deletion of an anonymous call's temporary conversation (**a real delete request**), and the election of a repair model for self-healing (**a real upstream completion**). Reproduced: with `DISABLED_PROVIDERS=kimi` and no cooldown, `_refresh_stale_provider("kimi", …)` really invoked the refresher (`[网关] kimi 令牌已超过 6h，尝试静默刷新…`). An account the operator had already taken out of service kept being touched — precisely the failure mode the standing "never touch a banned/withdrawn node" constraint exists to prevent.
    - **One declaration, one judge**: `CooldownTracker.touch_avoidance_reason()` is the single judgement for all background touches — `disabled` → `quarantined` → `cooldown`, heaviest-wins, `""` meaning "may touch". All four channels (probe, token refresh, conversation GC, healer election) evaluate it, and it is wired once in `server.py`. This is the OPT-020 pattern again (fold the declaration into the reading so every gate honours it with zero extra wiring), applied to a declaration that had been left out.
    - **Distinct from every neighbour, and *stricter* than the dispatch gate in exactly one place**: a background touch is never worth risking an avoiding node for, so the short soft cooldown that the dispatch boundary deliberately leaves as a "last resort" (OPT-021) blocks here unconditionally. The **cause is returned honestly** rather than collapsed into "cooling": disabled is lifted by editing configuration, a lease by a human revoking it, a cooldown by waiting — conflating the three is the "misleading the operator" defect class this codebase keeps fixing (OPT-026/027/029/031).
    - **Disabled is not deferred; cooling is**: a cooling node is waiting on a window that will expire, so it re-enters a bounded deferred-retry queue (OPT-013/017). A disabled node is waiting on a human to change configuration — there is no window to wait for — so a disabled provider is never refreshed and never queued, and re-enabling it simply means the next startup refreshes it. This is why the verdicts must stay distinguishable rather than both reporting `cooling`.
    - **One reading per configuration, again**: `HealthMonitor.is_disabled` used to read `DISABLED_PROVIDERS` **itself** — a third copy of the same configuration, disagreeing with the tracker's set the moment the set changes in-process. It now receives the tracker's `is_disabled` as an injected gate (falling back to the env read when constructed standalone, so the class stays usable outside the gateway).
    - **The cooldown master switch must not release a disabled node**: `GATEWAY_DISABLE_COOLDOWN_GATE=1` means "revert to no cooldown awareness", but operator-disable is a deployment declaration, not cooldown awareness — the switch silently releasing a node the operator had declared out of service was the trap. Disabled judgements are therefore *not* covered by that switch; lease/cooldown judgements still are, value-for-value as before.
    - Telemetry: `touch_gates` on `/v1/diagnostics` (`blocked_by_cause` — a refusal histogram per cause; each call site asks the judge exactly when it is about to touch upstream, so the histogram reads as *blocked touch attempts*, not node counts), and conversation GC's `deferred_by_cooldown.per_cause` splits deferrals by cause. `GATEWAY_DISABLE_CONVERSATION_GC_COOLDOWN_GATE=1` still reverts the GC gate; without an injected cause gate the GC falls back to the cooldown float gate and reports `cooldown`, value-for-value as before. See `tests/test_disabled_propagation.py` (9 cases).

31. **Dossier/Posture Agreement with the Dispatch Fact (`providers/risk_dossier.py:derive_posture`)**:
    - **[OPT-035] The same "the dossier lied" bug as OPT-031, one cell over**: the dossier's job (OPT-023) includes answering "can this node be dispatched right now", and the dispatch boundary is the only source of that fact. OPT-031 found the *long-avoidance* cell where the boundary hard-blocked a node while the dossier reported `cooling (dispatchable)`, and added a posture. The **operator-disable cell was missed in exactly the same way**: the boundary hard-blocks it (OPT-033) while the dossier reported `posture=clear, dispatchable=True`. Reproduced with `DISABLED_PROVIDERS=qwen`, no lease, no cooldown: `dispatch gate → {'dispatchable': False, 'blocked_by': 'disabled'}` vs `dossier posture → clear`. An operator reading the dossier concludes a node they had declared out of service is healthy and available.
    - **Posture vocabulary gains `disabled`, ordered danger-first**: `POSTURE_ORDER` is `quarantined → disabled → long_avoidance → cooling → probation → watch → clear`. The order is deliberate, not alphabetical: a node that is **both banned and disabled** (this machine's DeepSeek) must report `quarantined` first, because if it reported `disabled` the operator's natural reaction is "then just lift the disable" — re-dispatching a node upstream has banned. Reporting the ban gives the correct action (wait for the platform), and `disabled` stays visible as an informational per-node flag (`entry["disabled"]`) and in `POSTURE_LABELS`.
    - **The agreement is asserted as a property, not as six cases**: `tests/test_dossier_dispatch_agreement.py` checks, for *every* per-node state (healthy / short cooling / escalated long avoidance / lease / disable), that `dossier.dispatchable == gate.dispatchable`. OPT-031 and OPT-035 were both a single missed cell; a property test means the next missed cell turns red instead of waiting for an operator to measure it. The one deliberate exception — a **ring-wide credential outage** (OPT-025) is a ring-level fact while the dossier is per-node, so the dossier reports `clear` while the gate reports `blocked_by=credential_outage` — is asserted explicitly rather than hidden, so it can neither be mistaken for a bug nor silently change.
    - **The verdict branches on the cause, and never recommends a useless remedy**: `AVOIDANCE_MATRIX["disabled"]` answers `technically_bypassable: False`, `recoverable_by_relogin: **False**` (a configuration declaration is not a credential problem — re-login cannot help), `auto_recovers: False`. `_avoidance()` places the disabled branch *after* the quarantine branch so a leased node keeps its `ban` advice, and `recommended_actions` for `POSTURE_DISABLED` names `DISABLED_PROVIDERS` and says re-login is useless — the recurring "misleading the operator" defect class (OPT-026/027/029/031/034) closed in the dossier too. `entry["disabled"]` is informational only and never mutates risk state; the whole query path stays read-only.
    - Telemetry: `posture_counts` on the dossier summary gains a `disabled` bucket, and `AVOIDANCE_MATRIX` gains a `disabled` row — both are part of the `/v1/admin/risk` and `/v1/diagnostics` surface, and `tests/test_risk_dossier.py` pins them so a vocabulary change cannot slip through unnoticed. `GATEWAY_DISABLE_RISK_DOSSIER=1` still disables the whole surface. See `tests/test_dossier_dispatch_agreement.py` (6 cases).

32. **Tool-Loop Closure & Anti-Fabrication (`providers/base.py`, `providers/tool_streamer.py`)**:
    - **[TOOL-LOOP] The loop had two open ends, and both were silent.** (a) `flatten_messages` read only `content` and never `tool_calls`, so an agent's second round sent a tool result for a call the model could not see itself having made; `continuation_content` unconditionally took the last `user` message, so in continuation mode the tool result was skipped entirely and the *previous question* was re-sent — the loop could never close. (b) `finalize()` parsed without the declared-name allowlist, so a name the streamer had already rejected could be re-accepted at the end of the stream, producing a call the client cannot execute while swallowing the tail as already-emitted text. Both are fixed at the source, with the same allowlist threaded through every parse site.
    - Anti-fabrication is three layers, each necessary: a **format whitelist** (`json` stays allowed — real models do emit ```` ```json ```` for calls; `python`/`ts` are rejected), a **strict shape** check (`_extract_single_tool_strict`), and a **declared-name allowlist**. Format alone cannot work: disabling `json` would break normal calls, and keeping it lets any JSON block look like a call. A rejected call is returned to the user as text rather than disappearing.
    - The behavioural claim is asserted end-to-end in `tests/test_agent_loop.py`, on **the prompt upstream actually receives** — not on the gateway's own response object. A gateway that returns a perfect `tool_calls` payload while upstream never saw the call still fails the user's agent.

32b. **Streaming Item Lifecycle (`server.py`, all three protocols)**:
    - **[ANTHROPIC-STREAM] / [RESPONSES-STREAM] The same bug, twice, in two protocols.** Anthropic's tools path closed the thinking block when switching to text but not the text block when the model thought again, so an alternating turn emitted `start(1,text)` immediately followed by `start(1,thinking)` — one index opened twice and never closed in between. Responses' path went further: every index increment was deferred to the end of the stream, so a reasoning item and a message item both claimed `output_index 0`, and a *second* reasoning stretch was appended to a message item that already carried text. Clients archive content by index, so duplicate indices overwrite each other — the symptom is "the agent's output is missing half of it", with no error anywhere.
    - Reasoning that reappears after text is not an edge case: it is what a reasoning model does on every tool turn. Both paths now close the current item before opening the next (buffer cleared per item, so a second reasoning item does not inherit the first one's text) and give each item its own index in arrival order.
    - The invariant is asserted structurally, not case by case: `_assert_item_lifecycle` (Responses) and `_assert_block_lifecycle` (Anthropic) check, for every case in both suites, that indices are unique and sequential, that deltas only land on an open item of the matching kind, that `done` content equals the concatenated deltas of that same item, and that items close in order.

33. **Streaming Heartbeat (`providers/stream_keepalive.py`)**:
    - **[STREAM-KEEPALIVE] The silence between two bytes is the failure.** All six `StreamingResponse` exits were bare generators: whatever the upstream web UI did between "request accepted" and "first character" (tens of seconds, and longer for reasoning models), the client saw nothing. Codex CLI / Claude Code judge "connection opened, no bytes" on a short window and reconnect or give up — the user sees "the gateway connected but the agent says nothing" while the gateway log looks perfectly healthy.
    - `sse_keepalive()` yields `: keepalive` comment frames during silence. The `:` prefix is a spec-level SSE comment, so all three protocols' clients must ignore it and no event stream can be polluted; it is still real bytes, so it resets the client's idle timer. Default 15s (`GATEWAY_STREAM_KEEPALIVE`), 0 disables to the byte-identical old behaviour.
    - **The implementation detail is the point**: the obvious `await asyncio.wait_for(iterator.__anext__(), timeout)` is *wrong* — on timeout it cancels `__anext__`, which is thrown into the async generator body and closes it, so **every chunk after the first silence is permanently lost**. The first version did exactly that and `tests/test_stream_keepalive.py` caught it dropping the second and third chunks. The pull now lives in a task that is never cancelled mid-stream (only in the `finally`, for the disconnect path), and the timeout merely emits a frame. Upstream exceptions still propagate — a heartbeat must never disguise a real failure as "still thinking".
    - All six exits are structurally asserted to be wrapped (`test_all_streaming_responses_are_wrapped` fails when the exit count changes), because six hand-wired call sites is precisely the shape of change that goes half-done.

34. **Agent-CLI Model Alias Coverage (`server.py:resolve_model`)**:
    - **[AGENT-LOOP] A 404 at handshake is indistinguishable from "the gateway does nothing".** `resolve_model` matched OpenAI names from a fixed table; `gpt-5`, `gpt-5-codex`, `o4-mini` and `codex-mini-latest` — what current Codex CLI builds actually request — were absent, so the client got `404 model_not_found` and never sent a single request. The table gained those names, and unknown `gpt-*` / `o*` / `codex*` ids now fall back to a tier by prefix. The failure direction is deliberate: a fixed table can never keep up with vendor releases, so an unrecognised id is served at the most plausible tier rather than refused — a degraded answer beats a handshake rejection.

34b. **`tool_choice` Enforcement & Agent-History Fidelity (`providers/tool_streamer.py:resolve_allowed_tools`, `providers/responses_compat.py`)**:
    - **[TOOL-LOOP] A constraint that lived only in the prompt is not a constraint.** `tool_choice` was translated into one sentence of system prompt ("Do not call any tool in this turn") and nothing else; the parser still admitted every declared tool. Web models do not reliably obey prompt constraints, so a `tool_choice:"none"` request that came back with a ```` ```tool_call ```` block still returned `tool_calls` / `tool_use` / `function_call` — measured on all three protocols (`finish_reason: tool_calls` with `tool_choice:"none"`). The client, following its own contract, never executes that call, so the whole turn is dead. Enforcement now lands on the **parse**: `resolve_allowed_tools(tools, tool_choice)` returns the effective allowlist (`none` → empty set, a named tool → just that name, `auto`/`required`/unknown → all declared names), and all six parse/stream sites ask it instead of `tool_names_of`. The prompt directive stays, as the thing that lowers the probability; the allowlist is what guarantees the outcome. A tool call filtered by the allowlist is returned to the user as text, never silently dropped — the same rule as an undeclared name.
    - **Fail-open on shapes, fail-closed on semantics**: an unrecognisable `tool_choice` shape, or a named tool that was never declared, keeps the full declared set rather than narrowing to nothing — narrowing there would turn a perfectly serviceable turn into an empty one. `none` is the only value that empties the set, because it is the only one that means "no tools at all".
    - **[AGENT-LOOP] Codex replays its own reasoning items, and they were arriving as user input.** The Responses input converter's fallback branch serialised any unknown item to JSON, so `{"type": "reasoning", "id": "rs_1", "summary": [...]}` — which Codex sends back verbatim in the next turn's `input` — reached the upstream model as a **user message containing raw JSON**. Every turn paid tokens for a blob the model could not interpret, and the model's own prior thinking was replaced by noise. Reasoning items now render as an assistant `<thinking>` block (empty ones are skipped), and `item_reference` / `compaction` — pointers that cannot be resolved without a response store — are skipped instead of being dumped as content. `tests/test_agent_loop.py::test_reasoning_replay_is_not_a_user_message` asserts no `{"type": "reasoning"` text can reach the upstream prompt.
    - **[AGENT-LOOP] `reasoning: {"effort": ...}` was silently dropped.** Codex CLI sends the reasoning intent as an object (`{"effort": "high", "summary": "auto"}`), while the gateway only read the older flat `reasoning_effort` string. Code models such as `gpt-5-codex` also do not match the `o1/o3/o4` reasoning prefixes, so there was no fallback: "think before acting" was lost entirely. Both spellings are now read (`minimal` included), pinned by `test_codex_reasoning_object_enables_thinking`.
    - **[TOOL-LOOP] The same defect class, one field over: `parallel_tool_calls` was never read at all.** All three protocols let a client declare that only one tool call may come back in a turn — OpenAI/Responses `parallel_tool_calls:false`, Anthropic `tool_choice.disable_parallel_tool_use:true` — and the gateway ignored the field on every path. Measured: when upstream returned two ```` ```tool_call ```` blocks, all three protocols returned two calls. For an agent client that cannot execute calls in parallel or merge their results, the second call is one it neither expected nor will run, so the tool-result pairing breaks and the turn is wasted. `parallel_calls_disallowed()` decides, `format_tools_system_prompt(parallel_allowed=...)` adds an explicit "Do NOT emit more than one tool call in a turn" directive, and `cap_parallel_tool_calls()` trims to the **first** call at all six parse/stream collection points.
    - **First, not none**: keeping the first call is what makes the constraint useful — the model's current intent is executed, and the client's next turn continues the remaining work; dropping every call yields a turn in which nothing happened. The rule about which values tighten is the `resolve_allowed_tools` rule exactly: only an explicit `false` / `true` disables, and an absent or unrecognisable shape leaves parallel calls allowed (fail open, zero regression) — pinned by the trailing no-flag assertion in the same test.
    - **[TOOL-LOOP] The third place a tool call can hide: the reasoning channel.** A reasoning model writes "what to do" into its thinking stream, and the web upstreams push thinking and answer through separate channels. Measured: when the model put the entire ```` ```tool_call ```` block in `reasoning_content` and produced no answer text at all, all three protocols treated it as "no tool call in the answer" — OpenAI returned `finish_reason: stop` with `content` padded to a bare `…`, Anthropic returned an empty `content` array. For an agent client that turn did nothing: no answer to read and no call to execute, so the loop stops. `recover_tools_from_reasoning()` now looks in the thinking stream, and all six exit points (three protocols × streaming/non-streaming) call it through one shared helper, `_recover_reasoning_tools`.
    - **Only when the answer is empty** — the whole trade-off. If the model did produce answer text, that text *is* its answer and a tool block in its thinking is most likely an example ("I could have called it like this"); turning that into a real call converts an ordinary answer into a tool execution the client never planned for. An empty answer has no such ambiguity: the turn's only executable content is in the thinking stream. The prefix text is deliberately **not** re-emitted — the thinking stream already went to the client verbatim, so replaying it as answer text would duplicate it. The test pins both directions (thinking-only ⇒ call returned; thinking block + real answer ⇒ call not returned), and `reasoning_recovered_tool_calls` on `/v1/diagnostics` makes a nonzero rate visible as a product signal that an upstream is systematically emitting calls into the thinking channel.
35. **Client-Declared Output Constraints (`providers/stop_sequences.py`, `server.py`)**:
    - **[PROTOCOL] The same defect class one layer out: fields that are parsed and then never applied.** `stop` (OpenAI/Responses, string or list) and `stop_sequences` (Anthropic) were accepted by all three request models and then completely ignored — measured with `stop: ["END"]`, the body returned to the client was `"Here you go.\nEND\nnever mind"`. This is not a missing nicety: agent clients delimit multi-part output with stop sequences, so the surplus tail is read as a continuation of the same segment. `response_format` (`{"type":"json_object"}` / `json_schema`) and the Responses `text.format` equivalent were in the same state — parsed into the request model and never sent upstream, so the upstream model had **no idea** a JSON shape had been requested. Both now reach the prompt (`format_response_format_prompt`) and, for stop, the parser.
    - **Truncated at the gateway, not requested in the prompt.** A prompt only lowers the probability; a stop sequence is hard semantics — a slightly imprecise model drops it and the client receives content it explicitly asked to be cut. Same discipline as `tool_choice`: the prompt lowers the incidence, the parser guarantees the outcome. `StopSequenceScanner` (streaming) and `truncate_final` (non-streaming) do the cut.
    - **Streaming must hold back a tail.** The terminator can be split across chunks (`"EN"` then `"D"`), and bytes already sent cannot be recalled, so the last `len(longest stop) - 1` characters are retained until the next chunk arrives. The delay is invisible to the client (bounded by the terminator length) and the held tail is always released or cut. `test_terminator_split_across_chunks` pins it, and `test_unmatched_stop_does_not_eat_the_tail` pins the opposite error — retaining characters that are never handed back.
    - **Truncation happens *before* tool parsing.** Anything after the truncation point does not exist for the client, so a ```` ```tool_call ```` hiding there must never be executed — that would be a tool call the client never asked for and cannot relate to its own conversation. `SpeculativeToolStreamer.truncate_at_stop()` cuts the accumulated text (and clears the tool buffer and the falsifiable latch) before `finalize()`, and the non-streaming paths call `truncate_final` before `parse_tool_calls_with_healing`. Pinned by `test_tool_call_after_terminator_is_not_executed` on all three protocols.
    - **Each protocol's own terminal enum, not one invented in the middle.** OpenAI's `finish_reason` has no `stop_sequence` value (that is Anthropic's), so a stop hit is plain `"stop"` there — inventing an enum value would break strict clients. Anthropic genuinely has `stop_reason: "stop_sequence"` and its wire contract requires `stop_sequence` to carry **the matched string**, not `null` (`sse_message_delta` / `anthropic_message_response` previously hard-coded `null`, an illegal combination that told the client only *that* it was cut, never by what). Responses has no `stop_sequence` status: the correct form is `status: "incomplete"` + `incomplete_details: {"reason": "stop"}`.
    - **Zero regression, and the shape that nearly shipped.** With no `stop` declared the text must pass through **verbatim** — the first version of the scanner returned `""` when unconfigured, which silently emptied the streaming body on all three protocols (caught by the full suite, now pinned by `test_no_stop_declared_passes_text_through`). This is why the suite asserts the absence case explicitly rather than trusting the feature case.
    - **The test suite carries a tripwire.** Writing the first version of this suite, a streaming helper was called without the `_run(script, fn)` wrapper that installs the scripted provider, so the gateway issued a **real** request to Qwen with the real session credentials (verified afterwards that the risk ledger and the cooldown store were untouched — nothing was recorded against any account). The suite now replaces `srv._make_provider` at import with a factory that raises, and asserts a zero-hit counter at the end: failover wraps the tripwire's exception into a 502, so the counter — not the assertion — is the direct evidence that no upstream call happened. `tests/test_stop_sequences.py` (8 cases).
36. **Upstream Stream Error Classification & Connection Reclamation (`providers/base.py:classify_stream_status`, `read_error_body`)**:
    - **[STREAM-AUDIT] A closed response is not a detail — it destroys the risk signal.** Qwen (`qwen/provider.py`) and DeepSeek (`deepseek/provider.py`) called `resp.raise_for_status()` **inside** `async with client.stream(...)`. When it raises, the context manager has already closed the response, so the outer `except httpx.HTTPStatusError` reading `e.response.text` could only raise `StreamClosed` / `ResponseNotRead` — an exception about *not being able to read the body* covering the *status code*, which is the one thing the avoidance line needs. Everything collapsed to a generic 502: no `auth`, no `waf`, no `ratelimit`, nothing in the ledger. For DeepSeek — the node this deployment has actually been banned on — a Cloudflare 403 **is** the interception that OPT-011…035 exist to observe, and it was invisible.
    - **Read the body before the stream closes.** `read_error_body(resp)` awaits `aread()` inside the stream context and degrades to `""` rather than raising (a missing detail must never mask the status). `classify_stream_status()` maps 401 → `auth_error`, 403 → `waf_blocked`, 429 → `rate_limit_error` (all keeping the **original** status so the ledger's severity tiers apply), and everything else to a generic 502. Applied to the completion stream and to DeepSeek's pre-request session-create / PoW calls, which previously let `HTTPStatusError` escape `chat()` as a bare httpx exception — not even a `ProviderError`, so failover recorded it as an unknown fault.
    - **Kimi and GLM leaked a connection per request.** Both use `client.send(req, stream=True)` and never called `resp.aclose()` — not on success, not on 401/429/5xx. Nothing failed visibly; the shared pool (100 conns / 40 keep-alive) simply drained, and the 300s health probe leaked one more per node each cycle, so the eventual symptom is "the whole gateway got slow" hours after the cause. Both now close in a `finally` around status-check + parse, so every early exit reclaims the slot.
    - **Non-object JSON frames are legal JSON and illegal to `.get()`.** `data: []`, `data: null`, `data: 42` parse fine and then raise `AttributeError` on the first `.get()`, turning one odd frame into a 502 for the whole turn. Kimi and GLM now skip non-dict frames; the same `isinstance(obj, dict)` guard Qwen already had.
    - Pinned offline with `httpx.MockTransport` by `tests/test_stream_errors.py` (9 cases: status preservation per tier, the body being readable rather than `StreamClosed`, 5xx staying 502) and `tests/test_stream_lifecycle.py` (6 cases: `aclose()` on success and on every early exit, non-object frames not crashing).
    - **[STREAM-AUDIT] The concurrency semaphore must outlive the handshake — and this is a risk-control fact, not a tuning detail.** `execute_chat` entered the per-node semaphore via `contextlib.AsyncExitStack` and then `return`ed the wrapped stream from *inside* the `async with`: `__aexit__` ran at `return`, releasing the slot before a single body chunk was read. So `PROVIDER_RISK_SPECS` (qwen 3 / deepseek 2 / kimi 2 / glm 5 / doubao 6) bounded only a millisecond-ish handshake — **measured peak 6 concurrent upstream sessions against a qwen account configured for 3**. "One account, several parallel sessions" is one of the strongest automation signatures an anti-bot system scores, which makes this a direct threat to the constraint that the four vendors not yet flagged must stay that way. The slot is now acquired manually and released in the wrapper's `finally`; the OPT-022 probation lock deliberately **does not** follow it (its contract is handshake→first chunk, otherwise every session would be serialized during probation). Release is `Semaphore.release()`, which is synchronous, so the `GeneratorExit` (client-disconnect) path never needs an `await` there. `test_semaphore_covers_the_whole_stream` measured the old peak at 6 before the fix.
    - **[STREAM-AUDIT] An empty stream is a failure, not a success.** `record_success` ran right after `first_item = await raw_stream.__anext__()` with a `StopAsyncIteration` swallowed into `None`, so a provider that connected and produced **nothing** was recorded healthy and handed an empty answer to the client. All five providers unconditionally end `chat()` with a trailing `("", {"conversation_id": …})` frame, so an immediately-terminating stream can only mean "connected, silent" — now raised as `upstream_error`, which also keeps failover working (the next candidate is tried).
    - **[STREAM-AUDIT] A mid-stream break must cool the node.** The wrapper logged `流传输中途断开` and re-raised with no health consequence, so a node that truncates every few requests kept `failure_count == 0`, stayed the primary, and the user saw "the reply stops halfway" over and over — a direct source of the reported instability. Non-risk failures are now recorded in the wrapper's `except`; risk-class ones (401/429/WAF) are deliberately **not** recorded here because every protocol handler in `server.py` already records them, and double-counting feeds the 2ⁿ escalation (exactly the wrong direction for a banned account). Pinned by `tests/test_stream_concurrency.py` (6 cases: whole-stream coverage, slot return on completion, slot return on disconnect, empty stream ⇒ failure, mid-stream break ⇒ cooling, risk-class ⇒ not double-counted).
    - **[STREAM-AUDIT] Policy, not a bug: Qwen must not auto-refresh after a WAF hit.** On the first RGV587 interception `qwen/provider.py` called `login.refresh_qwen(...)` from inside `chat()` and retried — up to 25 s in the request path. Re-authenticating *immediately after being blocked* is precisely the **automated credential attempt** signature an anti-bot system scores on (the same shape OPT-025 identified for the 401 storm), so it can upgrade a recoverable human-verification challenge into an account-level ban of one of the four vendors this deployment must not lose. Re-login is a **human** action (completing the slider), not something the request path does on its own; the avoidance line then applies (cooling → long avoidance → the message telling the operator to run `login.py qwen`). Now off by default, kept only behind `GATEWAY_QWEN_WAF_AUTOREFRESH=1` for deployments that knowingly want it, and pinned by `test_qwen_waf_does_not_auto_refresh_by_default` (one upstream call, no refresh, actionable message).
37. **Client Thread Id vs Upstream Session Id (`providers/session_affinity.py`)**:
    - **[TOOL-LOOP] The most direct cause of "the model ignores my tools", and it only shows up for *some* clients.** A client-generated `conversation_id` is a **thread identifier**, not an upstream session identifier, and the two were the same value: when the affinity registry held no entry for a thread, the client's id was adopted verbatim as `upstream_conv_id` and handed to the provider. Every provider treats a non-empty `conversation_id` as "continue this upstream conversation" and sends only the delta after the last user turn. On turn one that delta *is* the last user message, so the upstream prompt contained **only the question** — the injected system prompt, `## Tools Available`, the tool-calling rules and `response_format` were all absent. Measured: the same request produced a 990-character prompt when flattened and `'read foo.py'` when treated as a continuation. The model cannot call tools it was never told about, and the failure looked intermittent because it depends on whether the client keys its own threads.
    - **Only an observed upstream id is ever replayed.** `resolve_affinity()` now returns `upstream_conv_id=None` for an unbound thread (and `record_turn()` no longer substitutes the client's id when a provider returned none), so the provider creates a fresh upstream conversation and flattens the full history. `has_upstream_session(session_id)` is the single read-only judge the prompt builder asks — the decision is "does the gateway hold an upstream session for this thread", **not** "did the client send a thread id". A client's `conversation_id` is still echoed back to the client unchanged (it is *their* thread), so thread stability is preserved.
    - Pinned by `test_client_thread_id_does_not_swallow_the_tool_contract` (`tests/test_stop_sequences.py`, 9 cases now), which asserts the decision handed to the provider *and* the resulting prompt — measured failing with the client's id under the old code. `tests/test_affinity.py`'s fresh-decision assertion was corrected to the same semantics, and `tests/test_server.py`'s stateful-lifecycle case now asserts what matters (the provider never receives the client's id, and an established thread is not deleted as an anonymous temporary conversation) rather than pinning the old passthrough.
38. **Prompt-Folding Fidelity (`providers/prompt_optimizer.py`)**:
    - **[TOOL-LOOP] Folding may only shorten history, never rewrite it.** Phase one replaces oversized middle-turn content with a marker, and that marker is *input to the model's next reasoning step*. The old single template asserted `状态正常` unconditionally, so a genuinely failed tool execution was presented to the model as a success: it stopped retrying and reasoned forward from a conclusion that never held. Worse was the code-block path — **every** fenced body over 400 chars was replaced by the same "historical execution result" marker, so a `` ```tool_call `` fence became prose (the model then sees a call with no arguments, and the loop breaks on the spot) and a long code block in a **user** message was re-labelled as tool output, changing who said it.
    - **Three markers, one per truthful reading.** `FOLDED_TOOL_RESULT_TEMPLATE` (success) and `FOLDED_TOOL_ERROR_TEMPLATE` (failure) are chosen by evidence — a `[Tool Error …]` tag prefix on the text path, `is_error` on Anthropic `tool_result` blocks. OpenAI's `role:"tool"` carries **no** success/failure field, so it gets `FOLDED_TOOL_RESULT_UNKNOWN_TEMPLATE`, which states only that the content was omitted: guessing "success" makes the model skip a retry that was needed, guessing "failure" makes it re-run a command that already worked. Bare code blocks get a neutral `FOLDED_CODE_BLOCK_TEMPLATE` because they belong to whoever wrote them, not to a tool. `_PROTECTED_FENCE_LANGS` (`tool_call` / `function_call` / `tool_use` …) is never folded on any path.
    - **Branch 3 only folds self-labelled segments.** Plain-string content now goes through `_fold_text_content(..., fold_code_blocks=False)`: a `[Tool Result]` / `[Tool Error]` fragment *inside* the text is still folded (that is a genuine replayed tool result), but a naked fence is left alone — including in `user` and `assistant` messages, whose code is their own utterance. Content that still blows the budget is handled by phase two, which discards it wholesale and says so.
    - **Phase two's marker no longer lies.** It wrote `[前序对话历史已由网关自适应折叠，保留核心结论与上下文]` ("core conclusions and context retained") while retaining **nothing** — the whole middle band is dropped. A model reading "retained" assumes it inherited prior conclusions and cites agreements that are no longer in the context. The marker now states the number of messages omitted and tells the model to re-read or ask, which is the only honest thing a marker with no content can say.
    - Pinned by `tests/test_folding_fidelity.py` (7 cases, each verified red on the pre-fix code and green after: error-not-success on both the text and `is_error` paths, OpenAI's neutral marker, the immune call fence *with a plain-fence control*, the user/assistant code-block speaker test, an end-to-end `fold_history` run, and the summary marker's count).

39. **Responses Freeform (Custom) Tools (`providers/anthropic_compat.py` / `providers/responses_compat.py`)**:
    - **[TOOL-LOOP] S1.3 — the tool the gateway could not see**: Codex CLI's `apply_patch` is declared as a Responses **custom** tool — `{"type": "custom", "name": "apply_patch"}`, no JSON schema, the call item is `custom_tool_call` and its payload is a raw freeform text field `input`. The gateway knew only `function` tools, and the three places it mattered each failed *silently*: the declaration rendered as `Args: {}` (the model was told the tool accepts nothing, so it never called it); the replay path had no branch for the item type and fell through to its generic fallback, re-serialising the item as a raw-JSON **user** message (the model saw a patch document it had never written — unrecognisable as its own call, and disconnected from the `[Tool Result]` that follows it); and the output boundary reported every tool as `function_call` with JSON `arguments`, so the client's `type` dispatch found no such tool and dropped the turn. All three present as "the agent will not edit files", with no error anywhere. This is the defect class the standing mandate targets: a declared capability that is parsed, or not parsed, and then never honoured.
    - **The contract is synthesized, because no upstream has native tool calling**: tools are emulated by injected prompt text (```` ```tool_call ```` + JSON), so a freeform tool needs *some* shape to travel in. `freeform_tool_input_schema()` declares exactly one required string field, `input`, and the prompt says so — the model is told precisely where its raw text goes. `custom_tool_input_text()` inverts it on the way out, and it accepts **four** shapes because the model does not always obey: the contract `{"input": raw}`, a bare string, a self-invented single field (`{"patch": raw}`), and — the one the non-streaming path actually produces — a JSON **string** of the contract, which is parsed first and only then unwrapped. Handing `apply_patch` the quoted, `\n`-escaped wrapper instead of the patch is a parse failure that silently loses the edit, which is why the string branch parses rather than passing through.
    - **Replay preserves speaker and bytes**: an input-history `custom_tool_call` (and `local_shell_call` / `shell_call`, which are freeform in the same way) becomes an **assistant** call block in the same `{"name": ..., "arguments": {"input": raw}}` form the model itself is asked to produce, carrying the original `call_id`; the matching `custom_tool_call_output` becomes `[Tool Result for <id>]` in a **user** message. The patch survives character-for-character — patches are whitespace-sensitive, so any re-serialisation is corruption.
    - **Output side branches by declaration, never by guesswork**: `freeform_tool_names()` collects *only* `{"type": "custom", "name": ...}` declarations, and only a call whose name is in that set is emitted as `custom_tool_call`; everything else keeps `function_call`. On the streaming path the same branch chooses between `response.custom_tool_call_input.delta` / `.done` and `response.function_call_arguments.delta` / `.done`. Emitting a freeform payload as JSON argument deltas makes the client try to parse a patch as JSON and fail mid-stream.
    - Pinned by `tests/test_responses_custom_tools.py` (6 cases). The pre-fix behaviour was measured directly rather than inferred: `Args: {}` in the prompt, both replayed items as raw-JSON **user** messages, and a `function_call` carrying `{"input": "*** Begin Patch\\n..."}`. Beyond the shape assertions, the end-to-end case drives a real `/v1/responses` stream through a scripted provider and asserts the upstream prompt contained the `input` contract — because a client-side fix that never reaches the model would pass every local shape check and still never call the tool.

41. **Inbound Content Normalization (`providers/base.py:text_of` / `providers/prompt_optimizer.py` / `providers/anthropic_compat.py` / `providers/responses_compat.py`)**:
    - **[PROTOCOL] S1.4/S1.9/S1.10 — three legal request shapes the gateway handled wrong**: the inbound side has four nearly-parallel text extractors (OpenAI parts, Anthropic blocks, Responses blocks, and the prompt optimizer's own copy), and the defects below each lived in *some* of them. They are grouped here because they are one product problem: an operator asking "为什么模型答非所问" gets no error to look at.
    - **Attachments were dropped in silence**: an OpenAI `image_url` / `input_file`, a Responses `input_image` / `input_file`, and an Anthropic `image` (reduced to a bare `[Image: png]` *type label* — metadata, not an announcement that content is missing). No upstream provider accepts anything but text — the five targets are web chat endpoints — so the image genuinely cannot arrive; the bug is that nothing said so. The model received `"what is this?"` with no image and answered anyway, which is a hallucination with the gateway's fingerprint on it. Attachments now reach the prompt as explicit placeholders (`[Image omitted: this gateway's upstream providers accept text only]`, `[File omitted: <name>]`), so the model can say it cannot see the attachment. The file placeholder carries the filename — a model told only "a file is missing" cannot say *which* one to re-send.
    - **`text: null` was a 500, from two copies of the same extractor**: `{"type": "text", "text": null}` is legal for every client (optional fields are frequently serialised explicitly), and `"\n".join` raised `TypeError: sequence item 0: expected str instance, NoneType`. It existed in `base.text_of` **and** in `prompt_optimizer._extract_text_robust` — and the second one runs during *token estimation*, i.e. before routing, so it took down the whole request rather than one message. Non-string text is now ignored everywhere rather than `str()`-ed: `None` must never reach the prompt as the literal word `None`.
    - **An OpenAI `system` parts list became a Python repr**: `server.py` merged the tool contract into `messages[0]["content"]` with an f-string, which stringifies a list *without calling any extractor* — the model read `[{'type': 'text', 'text': 'be terse'}]` immediately before the tool rules. Several client SDKs (and the OpenAI SDK itself) send system content as a part list, so this was a silent prompt injection of noise on a normal path. The merge now goes through `text_of`.
    - Pinned by `tests/test_content_normalization.py` (6 cases), including two end-to-end cases through `TestClient` that assert the placeholder and the merged system text in the messages the **upstream really receives** — a helper-level assertion would pass even if the pipeline never called it. Pre-fix behaviour was measured directly rather than inferred: `'look'` (image dropped), `'read'` (file dropped), the `TypeError` on `null`, and the repr in the system content.

43. **Responses History Tool Replay (`providers/responses_compat.py:_tool_call_block`)**:
    - **[TOOL-LOOP] S1.5/S1.6 — the assistant turn that vanished from history**: Responses clients replay their whole prior output verbatim, and real clients attach tool calls in one of two shapes: a standalone `{"type": "function_call"}` item (already handled) or `{"type": "message", "role": "assistant", "tool_calls": [...]}` — the OpenAI chat-compatible shape emitted by many SDKs and hand-rolled clients. The `message` branch read only `content` and dropped `tool_calls` entirely, so on the next turn the model received `[Tool Result for c1]` with **no record of having made call c1**: it could not tell which tool produced the output or with what arguments. The loop simply stopped continuing, with no error to look at. The same branch also turned `{"type": "message", "role": "tool", "tool_call_id": ...}` into an ordinary **user** utterance — an ownerless block of text.
    - Both shapes are now replayed as an assistant ```tool_call plus a `[Tool Result for <id>]` labelled result. The assistant message keeps its own prose (the narration before a call is context the model uses); parallel calls in one message all survive, separated as distinct blocks.
    - **One rendering rule, not two**: `_tool_call_block()` is the single implementation, shared by the `message.tool_calls` path and the `function_call` item path. The suite asserts the two render **byte-identically** — the recurring defect class here is one fact interpreted in two places, and a call is the fact that matters most.
    - Pinned by `tests/test_responses_history_tools.py` (4 cases, each verified against the pre-fix code, which reproduces exactly `{'role': 'assistant', 'content': '我来读'}` followed by `{'role': 'tool', 'content': 'print(1)'}`), including an end-to-end case asserting the call and its id reached the prompt the upstream really receives.

45. **Pre-Dispatch Rejection on the Status Line (`server.py` streaming paths)**:
    - **[H4] The silent 200**: `execute_chat` can refuse before making any upstream call at all — whole-ring credential outage (OPT-025), operator disable (OPT-033), a quarantine lease (OPT-021), ring exhaustion by long avoidance (OPT-031). Those are deterministic zero-upstream conclusions; there is nothing to stream. The OpenAI chat and Anthropic streaming paths nevertheless kept that `await` **inside** the response generator, so the headers were already flushed as **200** and the refusal arrived as `data: {"error": ...}`. Most SDKs look at the status code first, treat 200 as success, and discard or fail to parse the body: a silent failure, and the client keeps driving its agent loop into the same wall. `/v1/responses` happened to await before returning and therefore answered 503 — the same protocol rule producing two different outcomes depending on the path, the recurring defect shape of this codebase.
    - **Fix at the seam, not by buffering**: only the call that precedes the *first event* — the handover of the upstream async stream — moved out of the generator and in front of the `StreamingResponse`. Once the upstream stream exists, everything downstream is still forwarded token by token. The suite asserts this explicitly with a provider that yields text and *then* raises: the response stays 200 (a status cannot be changed after content), the error is emitted in-band, and `[DONE]` is never sent, so a client cannot mistake a truncated stream for a complete one.
    - **One rejection, one status across protocols**: the suite drives the same injected `ProviderError` through `/v1/chat/completions`, `/v1/messages` and `/v1/responses` and asserts all three answer 503, which keeps the mapping tables (OpenAI `err_type` names, Anthropic `overloaded_error` / `authentication_error`) from drifting apart.
    - Two pre-existing cases in `tests/test_server.py` (`test_upstream_error_sse`, `test_anthropic_error_mapping`) asserted the old 200-plus-in-band shape. They were **corrected to the new contract**, with a comment recording what the old assertion had been protecting, rather than left as a "known failure" or worked around by weakening the fix.
    - Pinned by `tests/test_stream_preflight.py` (4 cases), verified red on the pre-fix code with the exact message `流式请求的派发前拒绝被报成了 HTTP 200`.

46. **Cooldown State Write Elision & the Silently-Swallowed `NameError` (`providers/failover.py:_persist_state` / `providers/risk_ledger.py:save_state`)**:
    - **[H5] A blocking write on every request, for nothing**: `_persist_state()` sits on two *per-request* paths — `record_success` (called after the first upstream chunk) and `record_failure`. It unconditionally rewrote the entire cooldown state: temp file + `fsync` + `os.replace`, **inside `async with self._lock`**, i.e. synchronously on the event loop. Measured on this machine: a healthy node performing 20 successful requests produced **20 atomic writes**, every one of them byte-identical. `fsync` here costs ~0.57 ms median / ~1.25 ms p95 / up to ~12 ms — a fixed per-request stall, and a serialization point across concurrent connections. This is one concrete contributor to the reported "connecting an agent feels unstable": the gateway stalls on disk in the middle of the handshake.
    - **The rule is "don't write when nothing changed", not "write less"**: the state is snapshotted by `_state_snapshot()` (extracted so the persisted payload and the reload comparison share **one** definition — two copies of the same fact is this codebase's recurring defect), serialized to a JSON fingerprint, and compared against `_persisted_fingerprint`. Equal ⇒ return before touching the filesystem; different ⇒ write and remember only on success. Verified: 50 healthy successes now cost **0** writes, while every genuine transition (cooldown created, failure count incremented, another node cooling, cooldown cleared) still writes exactly once and the on-disk content equals the in-memory snapshot.
    - **A second reason the elision could never engage**: `record_success` set `_failure_counts[provider_key] = 0` rather than removing the entry, so a node's *first* success permanently added a `"<node>": 0` key — semantically "never failed", yet enough to make the fingerprint differ from an empty state forever. Cleared with `pop` in both `record_success` and the cause-scoped release path, so "healthy" and "absent" are now the same state, which is what they always meant.
    - **Seed the fingerprint on restore**: after loading state from disk the in-memory state usually equals what is already on disk, so the first healthy request after a restart used to rewrite the same bytes. `_restore_persisted_state()` now seeds `_persisted_fingerprint` when the reloaded snapshot is identical (and when there is no file at all — an absent state and an empty state agree); if the reload *dropped* expired cooldowns or zero counts, the fingerprints differ and the first write correctly repairs the file.
    - **`save_state` must report the real outcome**: it previously returned `None` unconditionally, so the caller could not distinguish "written" from "not written". It now returns `bool`, and the fingerprint is remembered **only** on `True` — otherwise one transient disk failure would mark this content as already-persisted and no further attempt would be made until the state changed again.
    - **The incident behind this work — a bare `except: pass` hid a `NameError`**: debugging the elision, `sys.settrace` showed `_persist_state` raising `NameError: name 'json' is not defined` — `json` was never imported in `providers/failover.py`, and the bare `except Exception: pass` swallowed it. The consequence was not "one write skipped" but **the entire persistence chain silently disabled, with zero log lines** — cross-restart avoidance (OPT-011), probation episodes (OPT-022), credential-rejection evidence and auto leases (OPT-027) all quietly stopped surviving restarts while every diagnostic continued to claim they would. The exception is now logged at warning level: `best-effort` means "failure is tolerable", never "failure is invisible". This is the same defect shape as the dossier/dispatch mismatches (OPT-031/035) — the system asserting something the code does not do.
    - Pinned by `tests/test_state_write_elision.py` (5 cases), verified red on the pre-fix code with the exact message `健康节点的 10 次成功产生了 10 次磁盘写入`.

47. **Stream Start Reclamation & the Never-Started Generator (`providers/failover.py:ManagedStream`, `server.py:ReclaimingStreamingResponse`)**:
    - **[C2] The resource is acquired before the body exists**: all three streaming paths hold upstream resources by the time the endpoint *returns* the response — `execute_chat` has already read the first chunk and holds the node concurrency semaphore, and `/v1/responses` additionally calls `load_balancer.acquire()` before constructing the response. Every release action, meanwhile, lives in the response body generator's `finally`. Measured (driving the real ASGI stack with a client that vanishes before the response head): for **all three** protocols the LB quota stayed at 1, the node semaphore went **down** and never came back (3→2, 2→1, 1→0 over three runs), and the provider stream was opened once and closed **zero** times. This is a permanent leak, not a transient one: the load balancer gradually marks the node high-load and routes traffic away from it until the process restarts — an operational "the gateway got slower and slower" with no error in any log.
    - **Why "disconnect propagation" does not cover it — Python's never-started generator rule**: `guard_stream` (OPT-009) only observes an interruption once the generator has been advanced. `aclose()` on an **async generator that was never started is a no-op** — its `finally` never runs (verified directly: `done None []`). So the one path that leaks is exactly the one where the generator is never pulled, and no amount of `finally`-written cleanup can fire there. This also means **no wrapper layer can fix it by closing itself**: `sse_keepalive` and `guard_stream` were never started either, so their `aclose()` is a no-op too. The close has to reach the *innermost* object.
    - **The fix, in two halves that are both necessary**: (a) `ManagedStream` wraps the upstream stream and makes reclamation an explicitly callable, **idempotent** action (`release_sync()` for the synchronous semaphore return, `close()` for the full close); its `close()` advances one frame **before** `aclose()` so a never-started source still runs its `finally` (verified: the semaphore returns, the provider's `finally` executes exactly once, repeated `close()` does not run it twice). (b) `ReclaimingStreamingResponse.__call__` unconditionally runs, in its own `finally`: the sync slot reclaim → `aclose()` of the body → the async upstream close → the protocol-level `on_exit` (the `/v1/responses` LB quota). Both are needed because (a) alone is unreachable if nothing ever calls it, and (b) alone is insufficient since `aclose()` on the never-started body is a no-op.
    - **Resources must be reclaimed at the innermost layer, from the outermost point**: the same disconnect-time insight from OPT-009 applies one layer up — cleanup code running in a task that is already cancelled has every `await` immediately re-cancelled (measured: the provider generator's `finally` never ran on the disconnect path). Both `disconnect_guard.safe_aclose_detached()` and `_close_stream_safely()` therefore schedule the close as an **independent task** and `shield` the wait, so cancellation only interrupts the waiting, not the closing.
    - **A `NameError` in the new path, caught by the same discipline**: the first wiring of the `/v1/responses` site referenced `preopened_stream`, which does not exist in that endpoint (it is a chat/anthropic-only variable) — the endpoint returned a 500 and the probe's LB counter read 1. Instrumenting at the ASGI boundary (`ReclaimingStreamingResponse.__call__` entry / exit, plus every `JSONResponse(status>=400)` content) surfaced it in one run. The lesson is the same one as H5: a resource leak in a defensive path is invisible by construction, so the *test* must assert the counter, not the absence of an exception.
    - Pinned by `tests/test_stream_start_reclaim.py` (4 cases), verified red on the pre-fix code with all nine leaks reported (`LB 配额泄漏` / `节点信号量泄漏` / `上游流未关闭` for each of the three paths). `tests/test_stream_keepalive.py`'s outlet-count assertion was tightened at the same time: it counted the substring `StreamingResponse(` and would have counted the class *definition* as a new outlet — it now counts only `return ...(` sites, so the invariant still means "every streaming return is keepalive-wrapped".

48. **Session Affinity Retention Across Short Cooldowns (`providers/session_affinity.py` / `providers/failover.py:is_affinity_retainable`)**:
    - **[M3] Paying tens of times the cost to dodge a fifteen-second window**: `resolve_affinity` had two outcomes — the bound node is available (stay) or it is not (migrate), where "available" was the same predicate the dispatch path uses. That predicate answers False for any soft cooldown, so a single 429 backoff permanently re-married an in-progress long-running agent session to a different vendor. Measured before the fix: one 15-second cooldown on the bound node produced `x-session-affinity: handoff`, `x-session-handoff-from: qwen`, and `affinity_handoffs = 1` — the session was now bound to another provider *for good*, with the upstream conversation id stripped.
    - **Why that is the wrong trade, in this codebase specifically**: adaptive pacing (OPT-014) and correlation-driven slowdowns (OPT-024) exist precisely to *cause* short cooldowns before risk control fires. So the normal, healthy operation of the gateway was triggering the most expensive possible client-side reaction — upstream context rebuilt, prompt cache discarded, tool contract relearned — to avoid a window worth seconds. The handoff mechanism was built for a *sustained* unavailability, not for a backoff.
    - **Two judgements, each asked by the party that owns the question**: `_is_provider_healthy` now means exactly "can this node be used right now" (unchanged), and the new `_is_provider_retainable` means "is the binding still worth keeping". The licence for the distinction is the layering already established at the dispatch boundary (OPT-021/031): **hard blocks** (quarantine/auto lease, `DISABLED_PROVIDERS`, long avoidance) are declarations that waiting is pointless → migrate; **short cooldowns** self-heal in seconds to two minutes → retain. `CooldownTracker.is_affinity_retainable()` is the single judge, so the answer cannot drift from the dispatch gate's idea of "hard".
    - **`degraded` is a third outcome, not a missing one**: the decision reports `AffinityDecision(status="degraded")` carrying the *bound* provider and the *bound* upstream conversation id, and deliberately does not increment `affinity_handoffs`. The request itself is still served by the ordinary candidate (the caller's primary), because the dispatch boundary keeps its own semantics; only the *binding* is preserved. When the cooldown expires the next turn is `bound` again on the original node — verified end-to-end.
    - **The binding must not be polluted while degraded**: `record_turn` writes the serving provider, so letting it run unchanged would quietly re-bind the session to whichever vendor happened to serve the degraded turn — the migration would be invisible but complete. All three streaming/non-streaming record sites therefore keep the bound provider during `degraded` and pass `upstream_conv_id=None`, because the conversation id observed on that turn belongs to the *other* vendor and must never be replayed to the original one (the heterogeneous-id rule from OPT-007).
    - **A stale second copy of the counters, caught by the first run**: `SessionAffinityManager.clear()` rebuilt `self._stats` from its own literal dict — a second definition of the same set of keys. Adding `affinity_degraded` to the constructor but not there made every `/v1/diagnostics` call raise `KeyError` right after any test reset. Fixed by listing the key in both places (and the suite now asserts the diagnostic is present, so the next added counter has to be added in both or fail loudly).
    - Telemetry: `x-session-affinity: degraded` plus `x-session-affinity-degraded: <bound node>` (explicitly stating "served elsewhere, binding kept" rather than leaving it to be inferred from the *absence* of a handoff header), and `affinity_degraded` on `/v1/diagnostics`. See `tests/test_affinity_cooling.py` (5 cases), verified red on the pre-fix code both structurally (the parameter does not exist) and behaviourally (the probe above: `handoff` / `handoffs=1` before, `degraded` / `handoffs=0` after).

49. **Request Timeout Boundaries & "A Timeout Is Not Risk Control" (`providers/failover.py` / `providers/risk_dossier.py`)**:
    - **[M2] No timeout on the whole path belonged to the gateway**: waiting for the first chunk was a bare `await`, bounded only by httpx's 600-second read timeout; the streaming phase pulled frames with nothing but the same socket-level timeout, which **resets on every byte** — so an upstream that emits one byte every 599 seconds, or only `: keepalive`, never trips it. Meanwhile the node concurrency semaphore, the probation serialization lock, the load-balancer quota and an HTTP/2 connection are all held by a half-dead upstream, the gateway's own `sse_keepalive` (unbounded) keeps the client from giving up, and requests on the same account queue behind it. That is half of "稳定性差": an upstream fault that is neither a success nor a failure, just permanently in progress.
    - **`GATEWAY_FIRST_CHUNK_TIMEOUT`** (default 180 s) bounds the handshake. It is deliberately not a "how slow is too slow" tuning knob but a resource boundary: before the first chunk this function holds the concurrency semaphore *and* the probation lock, and a reasoning model legitimately thinking for tens of seconds is healthy (that is why the keepalive exists) — so the bound must sit well above normal thinking time yet still exist. On expiry the provider stream is cancelled and closed (not left as a ghost task holding the connection) and a `504 / err_type="upstream_timeout"` is raised, which the ordinary failover loop treats as an upstream fault and moves to the next candidate. `=0` restores the bare `await` exactly.
    - **`GATEWAY_STREAM_IDLE_TIMEOUT`** (default 180 s) bounds the gap between two frames *after* the stream is open. Implemented with `asyncio.ensure_future` + `asyncio.wait`, deliberately **not** `wait_for`/`timeout()`: those implement expiry by cancellation, which would make "timed out" indistinguishable from "the caller cancelled", and would leave no opportunity to close the upstream cleanly first. On outer `CancelledError` the in-flight pull is cancelled and the cancellation propagated, so a disconnecting client cannot leave a ghost pull behind. `=0` restores the previous pull loop exactly.
    - **Timeout is its own cause, and the discriminator is a parameter, not a string match**: `record_failure(..., is_timeout=True)` is threaded from the two raise sites. It must be decided *before* branch selection, because `classify_interception_severity` defaults **any** non-401/429 input to `waf` — the old non-risk branch would otherwise catch the timeout text (it does not mention RGV587, but the classifier's default-`waf` answer is what gets persisted as the cooldown cause) and give the node a ≤45-second cooldown. Two measured consequences, both wrong: (a) a ≤45 s cooldown falls inside the "short cooling is worth one last try" band (OPT-021/031), so the timing-out node keeps being dispatched — the avoidance does nothing; and (b) `cooldown_cause` becomes `waf`, so the dossier tells the operator to run `login.py` and complete a slider on a platform that never intercepted them. The timeout branch uses `GATEWAY_TIMEOUT_COOLDOWN` (default 60 s, `max(30, base)`), does **not** enter recovery probation (there is no ban-lift thundering herd to protect against), and does **not** write the risk ledger or the credential watch — a timeout is not a risk interception, and polluting the risk picture with it is what makes the picture useless.
    - **Dossier: a cause the ledger cannot express**: `AVOIDANCE_MATRIX["timeout"]` answers `recoverable_by_relogin: False` and points at upstream health / local egress quality. Because timeouts never enter the ledger, `_avoidance()` cannot find this cause there at all — a node *currently* cooling on a timeout would be judged on the ledger's dominant severity (normally `waf`) and told to log in. `_live_cooldown_cause()` reads `CooldownTracker.cooldown_cause()` (the single judge) and only causes listed in `_LIVE_ONLY_CAUSES` (`timeout`) may override the ledger's dominant severity; everything else keeps the all-time ledger judgement, so one 15-second rate-limit backoff can never erase an entire risk history. `cooldown_cause` and the long-avoidance advice branch on it too.
    - Pinned by `tests/test_request_timeouts.py` (5 cases), verified red on the pre-fix code per case: the three behavioural cases hang until the harness's own 3 s `wait_for` fires (the produced symptom, not an assertion), the zero-disables case fails structurally on the missing accessor, and the dossier case reports `ratelimit` where it must report `timeout`.

50. **SingleFlight Follower Backpressure (`providers/singleflight.py:FlightGroup.broadcast_chunk`)**:
    - **[M4] An unbounded queue sized by the client's reading speed**: each follower subscribes with `asyncio.Queue()` (default `maxsize=0`, i.e. unbounded) and the leader hands it every frame with `put_nowait` — which **never raises** on an unbounded queue, so the `except Exception: pass` guarding it was dead code and "what happens when it fills up" had no answer at all. Measured: after a leader broadcast 20 000 frames of 512 bytes, a single non-consuming follower's queue held **20 000 frames, ~10 MB**, with no bound in sight. Real-world version: a client on a slow link, or an SSE consumer that stalls for a moment — which is exactly the shape of an agent session, so this is a quiet amplifier of "the gateway is flaky with agents". Nothing errors; memory just grows.
    - **Detach, never block**: the correct response is not to await the leader's `put` (that lets one slow client stall every other follower on the flight — the very thing SingleFlight exists to prevent) and not to silently stop delivering (a truncated answer read as a complete one is worse than an error). A follower whose backlog reaches `GATEWAY_SINGLEFLIGHT_BACKLOG` (default 256 frames) is removed from the subscriber list, its already-queued frames are **drained** (that memory is the thing being protected, and the follower's outcome is "retry", not "read the half you already got"), and a `RuntimeError` is placed in its queue so `stream_follower_gen` raises it to that client. The leader, the replay history and every other follower are untouched.
    - **A measured trap in the first version of the test, worth recording**: a strictly *faster* leader (broadcast loop with no `await` between frames) legitimately detaches even a follower that drains synchronously — the follower cannot win a race against a producer that never yields. Real broadcasts always have an await point per frame (they are reading a network stream), so the suite models a **slow but consuming** follower instead of a "never consumes" one and asserts the bounded backlog, the detach, the error, and that a synchronously-draining follower on the same flight is *not* detached.
    - Telemetry: `followers_detached` (process-wide, reset by `clear()` like the other manager counters) and `follower_backlog_limit` on `/v1/diagnostics`, so "are we dropping followers" is observable rather than inferred. Pinned by `tests/test_singleflight_backpressure.py` (3 cases); verified red on the pre-fix code — the diagnostic helper does not exist, and the behavioural probe reports 500/500 frames queued pre-fix vs 1 post-fix.

51. **Single Pacing Authority & Locked Slot Reservation (`providers/failover.py:apply_pacing_and_acquire`)**:
    - **[M1] A rate limit that lives in two places is a rate limit in zero places.** `PROVIDER_RISK_SPECS` declares a `min_call_interval` per node (qwen 0.3s, deepseek 0.4s, kimi 0.35s, glm 0.1s, doubao 0.08s) — the cheapest defence there is against being scored as an automated client. Two mechanisms each claimed to enforce it and **neither did** under concurrency:
      1. `server.py` wrapped every dispatch in `async with traffic_pacer.acquire(dispatched_provider) as pacing_delay:` — a *wait-then-immediately-release* block that exits **before** `execute_chat` makes the real upstream call. It delayed only the request holding it, constrained no concurrent caller at all, and its measured `delay_ms` was then reported as `x-risk-pacing-delay-ms` — so the telemetry asserted a throttle that had never been enacted.
      2. `CooldownTracker.apply_pacing_and_acquire` read `_last_call_time`, computed `elapsed`, slept, and wrote the timestamp back — **all outside any lock**. Two concurrent callers read the same `last`, computed the same `elapsed`, slept the same span, were released in the same instant, and overwrote each other.
    - **Measured**: three concurrent dispatches to qwen with `min_call_interval=0.30` produced upstream call timestamps `[0.0, 0.301, 0.301]` — two of three hit the same account in the same millisecond. That is the "one account, several parallel sessions" signature OPT-036 identified at the semaphore layer, arriving again from the pacing layer. For the four vendors the standing constraint says must not be flagged, this was the single most reachable way to flag them.
    - **The fix has two halves, both load-bearing**: (a) `apply_pacing_and_acquire` is now the **only** pacing authority, sitting immediately before the provider is instantiated — the last throttle before the real upstream call; (b) `server.py`'s three second-clock sites now call `_make_risk_headers(None, ...)`, which *reads* `CooldownTracker.last_pacing_wait_ms()` for telemetry rather than running a clock of its own.
    - **A reservation alone is not enough — this is the subtle half, and the first version of the fix got it wrong.** That version took the lock and, inside it, computed `wait = interval - (now - last)` and wrote `last = now + wait`: a reservation, which does stop concurrent callers from sharing one gap. The suite still failed, with `[0.0, 0.398, 0.601]` — a minimum gap of **0.203s** against a 0.240s floor. A caller that **oversleeps** (the loop was busy; a 0.300s slot woke at 0.398s) does not violate its own slot, but it eats into the next one, because a slot is a *prediction* while risk control measures the *real* interval between upstream calls. The authoritative check therefore has to happen at the **moment of release**: after sleeping, the caller re-enters the lock and re-tests `now - _last_call_time >= interval` against the actual clock, waiting again until it holds. Over-sleeping can then only push later calls further back; it can never compress a gap.
    - **Two maps, because they are two different facts** — and keeping them separate is what stops one from being silently substituted for the other: `_next_slot` is the **prediction** (who is queued for when, so concurrent callers do not share a gap), `_last_call_time` is the **fact** (when a call was really released — the quantity upstream observes).
    - **Also corrected here: a probation test that measured the wrong window.** `tests/test_probation.py::test_probation_serializes_concurrent_handshakes` counted in-flight requests from generator entry to generator `finally` — i.e. **generator lifetime** — while OPT-022's gate covers **handshake to first chunk only** and explicitly does not serialize the remainder of a streaming response. It was therefore deterministically red against entirely correct code (3/3 runs on unmodified HEAD). A timeline probe settled it: `chat-enter 0.2615 n=1` -> first chunk released `0.3137` -> next `chat-enter 0.3139`, a 0.2ms gap, so the handshakes *were* serialized and only the post-first-chunk lifetimes overlapped. The probe now counts entry to first chunk, matching the gate's contract. This is the same defect shape as the product bugs the rest of this file records: **an assertion about a window that is not the window the code protects.**
    - Pinned by `tests/test_pacing_race.py` (3 cases): concurrent dispatch is pulled into a staircase measured on *upstream call start times* (not on when the gateway thought it was done waiting), the decision is proven to be under the lock (4 callers x 0.12s must take >= 0.36s, not 0.12s), and a source assertion that `server.py` contains neither `await traffic_pacer.acquire` nor `async with traffic_pacer.acquire` — so a second clock cannot be reintroduced without turning the suite red. `TrafficPacer` keeps its concurrency-limit and statistics duties; only its second *clock* is gone.

52. **A Truncated Answer Must Not Impersonate a Complete One (`providers/stream_completion.py`)**:
    - **[S2] The one failure channel that raises no exception.** An upstream stream that ends *without* its protocol's completion marker — the body closes cleanly, the frame iterator simply stops mid-answer — was treated as identical to a normal finish, at every layer. Three measured facts compose into the defect: (a) `record_success` is recorded at **first chunk** (`failover.py`), and the exhaustion path never revisits it, so the node's failure count stays **0**; (b) all five providers end `chat()` with an **unconditional** trailing metadata frame, so truncation and completion are indistinguishable at the generator boundary; (c) the protocol handler then unconditionally appends `finish_reason: "stop"` and `data: [DONE]`. The client receives a **self-declared-complete half answer**, and the node remains the primary, so the user sees "the reply stops halfway" over and over. This is section 36's C3 ("a mid-stream break must cool the node") arriving through the single door that does not throw — `StopAsyncIteration` is converted to `break` and never reaches the `except Exception` handler that does the accounting.
    - **For an agent client this is the most destructive form**: half a ```tool_call fence parses to nothing, so the turn has no answer *and* no call, with no error anywhere — a cause of "工具调用没跑起来" that has nothing to do with the tool layer at all.
    - **The detectable scope had to be cut down to what actually exists, and the investigation contradicted the initial hypothesis.** Reading all five protocols: qwen reads `data.status == "complete"` (`qwen/provider.py`), kimi reads `event == "all_done"` (`kimi/provider.py`), and **deepseek / doubao / glm have no completion marker that is read at all** — doubao's `is_finish` occurs only in the *outbound request body*, and glm's `finish` does not occur in its provider at all. So only two of five nodes *can* judge truncation. Inventing a heuristic for the other three ("the text does not end in punctuation") would be manufacturing evidence, which is the exact thing this codebase keeps deleting.
    - **The verdict is therefore tri-state, not boolean**: `True` = the protocol has a marker and it was seen (normal end); `False` = the protocol has a marker and it was never seen (truncated); **absent** = the protocol has no marker (unknown) ⇒ **zero behaviour change**. "Absent means unknown, not truncated" is the single assertion that keeps the three marker-less providers working — treating absent as truncated would fail every normal answer from three of five nodes and fabricate a ring-wide outage. It is the same fail-open-on-shape / fail-closed-on-semantics rule as `resolve_allowed_tools`.
    - **Both directions of the scope are pinned by test**: the suite asserts the set of providers reporting completeness is **exactly** `{qwen, kimi}`. The forward direction matters because a scripted-upstream unit test would stay green while the real deployment never sets the key (the fix would be a no-op in production); the reverse direction stops a later change from "helpfully" adding a fabricated marker for a protocol that has none.
    - **Acting on the verdict reuses the existing, already-correct path** rather than growing a second one: a definite `False` raises `ProviderError(status=502, err_type="upstream_incomplete")` from inside the `try`, so the established mid-stream-break handler cools the node and re-raises — which makes the protocol handler emit an in-band error and **never send `[DONE]`**. No retry and no failover: content has already reached the client, so retrying would be half-packet pollution (the same reasoning the existing mid-stream path already uses). Section 45 established why this is the honest signal — the status line cannot change once the stream is open, so partial content + in-band error + no `[DONE]` is the only way a client can tell.
    - **A truncation is not a risk interception — and the suite caught this, not the design.** `classify_interception_severity` defaults **any** non-401/429 input to `waf`, so the first working version recorded a truncation with `cooldown_cause = waf`: the dossier would then tell the operator to run `login.py` and complete a human-verification slider on a platform that had never intercepted them. This is [M2]'s timeout defect, one cause over. `record_failure` gained `is_truncation`, decided **before** branch selection for the same reason `is_timeout` must be, with severity `truncated`; it cools the node (otherwise (a) is unchanged) but does **not** write the risk ledger, does **not** notify the credential watch, and does **not** enter recovery probation (there is no ban-lift thundering herd to protect against). `AVOIDANCE_MATRIX["truncated"]` answers `recoverable_by_relogin: False` and points at upstream health, and `truncated` joins `_LIVE_ONLY_CAUSES` so a live truncation cooldown is not reported as the ledger's dominant historical severity.
    - **One definition of "this is an upstream fault, not a flagged account"**: `is_timeout` had gated three separate risk side-effects, and adding truncation as a second flag would have meant `not is_timeout and not is_truncation` in three places — the "same fact scattered across several sites" shape this file records over and over. The three gates now read a single `is_upstream_fault`, so the next upstream-fault cause is one line, not four.
    - `GATEWAY_DISABLE_STREAM_COMPLETION_CHECK=1` restores the previous behaviour value-for-value. Pinned by `tests/test_stream_completion.py` (6 cases), verified red on the pre-fix code with the exact message `上游在没有完成标记的情况下结束，被当成了正常说完`.

53. **The Dedup Key Must Cover Every Constraint That Changes the Output (`providers/singleflight.py:compute_key`)**:
    - **[S3] A defect *introduced* by the fixes that made those fields work.** SingleFlight collapses in-flight requests with an identical fingerprint into one upstream call: the leader really calls, every follower is handed the leader's answer. So the fingerprint has exactly one correctness criterion — **identical fingerprint ⇒ the two requests' correct answers must be interchangeable.** `compute_key` covered provider / model / messages / tools / temperature / thinking / stream, and omitted `tool_choice`, `stop` / `stop_sequences`, `response_format` / `text.format`, `parallel_tool_calls`, `max_tokens`. **At the time that was harmless**, because those fields were parsed and then never read — they genuinely did not change the output (this file's own "declared then ignored" defect class). Sections 34b and 35 then fixed them one by one: `tool_choice` became an allowlist at the parse, `stop` truncates at the gateway, `response_format` reaches the prompt, `parallel_tool_calls` trims to the first call. Each fix made its field **start** changing the output, and the fingerprint was never updated to match.
    - **The resulting failures are silent wrong answers, not errors**: request A declares `tool_choice: "none"` (it wants prose) and B declares `"auto"` (it wants a call); they fingerprint identically, so whichever arrives first leads. B is handed prose and never receives the call it is waiting for — the agent loop stops where it stands; or A is handed `tool_calls` for a call it has declared it will not execute, so the turn is dead. Same shape for `stop` (one side gets text cut at a terminator it never declared, or uncut text it did), for `response_format` (one side asked for JSON and gets prose, then fails to parse it client-side), and for `parallel_tool_calls` (a client that cannot run calls in parallel is handed several).
    - **Adding fields to a dedup key is the only safe direction**: a more specific key can only *reduce* sharing, never cause a wrong share. Loosening a key is never acceptable. `None` and `{}` produce the same payload and `sort_keys=True` makes the constraint dict order-independent, so every existing call site keeps its exact previous semantics and dedup for genuinely identical requests is unchanged — asserted explicitly, because a key so specific that nothing ever dedups would be a worse regression than the original defect.
    - **The test pins the call sites, not just the signature**, because widening `compute_key`'s signature while leaving the three protocol handlers unchanged is a fix that passes every unit test (which call `compute_key` directly) while the real request path still discards the constraints. `test_all_three_protocols_pass_their_constraints` asserts there are exactly three call sites and that each passes `constraints=`.
    - Pinned by `tests/test_singleflight_constraints.py` (7 cases), verified red on the pre-fix code (structurally — the parameter does not exist).

54. **Retry Suppression & Backoff Signal on Deterministic Refusals (`server.py:_refusal_headers`, `providers/base.py:ProviderError.retry_after`)**:
    - **[H6] The gateway's one moment of certainty, and it said nothing.** Four refusals are *deterministic and zero-upstream*: whole-ring credential outage (OPT-025), operator disable (OPT-033), a quarantine/auto lease (OPT-021), and ring-wide long avoidance (OPT-031). `execute_chat` concludes them without touching a single upstream, so the answer is already final — yet the response carried only `503` and no header of any kind. Measured against a dead-ring gateway with the real `claude` CLI: **7 requests in a 40-second window**, each receiving the same zero-upstream 503. Or worse than noisy — it hangs: without a signal the CLI retries indefinitely (measured alive at 90s, killed by the harness).
    - **The first version of this fix measured the wrong variable, and the correction is the point.** It attributed the 7→1 drop to `Retry-After`. That measurement compared two different ports running two different servers, so the header was not the only variable. Re-measured under control — one server, one client, 40s, header mode toggled per run:

      | headers sent | CLI requests |
      |---|---|
      | none | 7 |
      | `Retry-After: 60` only | **7** |
      | `x-should-retry: false` only | **1** |

      A later 200-second run that appeared to confirm the original claim (11 → 1) is superseded by this controlled one. Reading the CLI's own dispatch confirms the mechanism rather than a guess: `if(k.status===429){let O=parseInt(k.headers.get("retry-after")??"",10);…}` — **`Retry-After` is parsed only on 429**, so on a 503 it is a declaration nobody reads — while `let h=n.headers.get("x-should-retry");if(h==="true")return!0;if(h==="false")return!1;` is evaluated **before** the status-code rules. `x-should-retry: false` is the header that actually suppresses the retry; `Retry-After` is sent alongside it because it is the standard field other SDKs and proxies do read, and it is what a human inspecting the response uses. The two are not interchangeable, and the code comment says so.
    - **The boundary that must hold**: an upstream 502/504 is jitter, worth retrying immediately, and attaching either header to it would make a client abandon a healthy node for an hour — worse than silence. Only the four deterministic refusals carry them; everything else is value-for-value unchanged (pinned by a case asserting a plain upstream 502 has neither header).
    - **The value must be the real window, not a constant — the half that keeps it honest.** `ProviderError` gained `retry_after`, filled at the raise site where the duration is actually known: credential outage reports `CredentialOutageWatch.remaining_seconds()` (measured live: **119** of the 120s TTL), a lease reports its remaining time (72h lease → `3600`, clamped by `GATEWAY_REFUSAL_RETRY_AFTER_MAX`), and ring exhaustion reports the **shortest** remaining avoidance in the ring — the soonest a request could succeed, not the longest. Only `disabled` falls back to the default (`600`), deliberately: an operator disable has no window that expires on its own, so fabricating a countdown would be a lie in the other direction. The plan was originally a flat 600s for all four; the test now asserts the credential case reports **<=120s**, which a hardcoded 600 fails immediately — "there is a header" is not the same claim as "it tells the truth".
    - Clamping to `[1, GATEWAY_REFUSAL_RETRY_AFTER_MAX]` keeps a lease measured in days from handing a client a multi-hour sleep it cannot distinguish from a hung connection. `GATEWAY_REFUSAL_RETRY_AFTER` (default 600) sets the fallback, `GATEWAY_REFUSAL_RETRY_AFTER_MAX` (default 3600) the cap. Pinned by `tests/test_credential_watch.py::test_zero_upstream_refusal_carries_a_backoff_signal` across all three protocols and both streaming/non-streaming paths — it asserts **both** headers on refusals and **neither** on a plain upstream 5xx, so a future change cannot silently drop the one that works while keeping the one that only looks right.

55. **`count_tokens` Fidelity — the number the agent budgets with (`providers/anthropic_compat.py`, `providers/token_counter_cache.py`, `server.py:count_tokens`)**:
    - **[PROTOCOL] Three separate ways the estimate described a request nobody sent.** `/v1/messages/count_tokens` is not a convenience endpoint: Claude Code calls it before every request to decide the context budget, so every inaccuracy below is an agent that compresses too late or too early, with no error anywhere.
    - **Two endpoints, two models for one body.** `/v1/messages` and `/v1/messages/count_tokens` describe the *same* Anthropic request, but each had its own pydantic class — and `system` was typed differently (`Union[str, List[Union[dict, str]]]` vs `Union[str, List[dict]]`). So `"system": ["you are terse"]` — a shape both the SDK and Claude Code emit — returned **200 on messages and 400 on count_tokens**: `system -> list[dict[any,any]] -> 0: Input should be a valid dictionary`. A 400 there reads to the user as "the agent stopped". The body is now one `AnthropicRequestBody` with per-endpoint subclasses, and the test asserts the *property* (every `system` shape messages accepts, count_tokens accepts) rather than enumerating five cases.
    - **The cache key omitted `tool_choice`.** `compute_count_key` covered messages/system/tools, but `tool_choice` is translated into a sentence of the tool prompt, so two requests with different `tool_choice` have different prompts and identical keys. Measured with the cache cleared per request: `none` = **314**, `auto` = **290**; with the cache warm, `none` then `auto` returned **314, 314** — the second request got a number its own prompt cannot produce. This is section 53's rule (`compute_key` must cover every field that changes the output) arriving one file over, so the docstring says so explicitly.
    - **The estimate never saw `disable_parallel_tool_use`.** `count_tokens` called the converter without `parallel_allowed`, while `/v1/messages` passes it — and that flag appends the "do not emit more than one tool call" directive to the tool prompt. Same request body, two different prompts: **1122 vs 1267 characters**, **290 vs 331 tokens**, systematically low on exactly the requests that carry the constraint. The test spies on the converter and compares the two *prompts*, not the two return values, because a fix that only moved the number would pass a value assertion while still estimating a different request.
    - **The test carries the tripwire for a reason.** Writing it, one `/v1/messages` call ran with the scripted provider not installed — the suite's existing zero-hit guard (section 35) exists precisely because that mistake once issued a real upstream request; this test installs the stub explicitly and says why in a comment.

56. **Nameless Tool Declarations (`providers/anthropic_compat.py:format_tools_system_prompt`)**:
    - **[TOOL-LOOP] The empty-name bullet was real, and it was not corruption — those tools genuinely have no name.** Captured from real `codex exec` (v0.145.0) by recording the raw `/v1/responses` bodies: alongside the nine named tools, Codex declares `{"type": "tool_search", "execution": "client", ...}` and `{"type": "web_search", "external_web_access": false}`. Neither carries a `name`. The renderer did `t.get("name", "")` unconditionally, so the prompt ended with an empty-name bullet plus `Args: {…}` — a callable-looking entry for a tool the model can neither name nor invoke, sitting immediately before the rule that forbids inventing tool names.
    - **Consistency with callability, not with the declaration list.** A nameless declaration can never become a call (the model has no name to write, and `tool_names_of` already excludes it), so it must not render as a callable. But silently dropping it loses information the client deliberately declared — `tool_search` means "more tools can be surfaced in a later turn". Known built-ins therefore degrade to a one-line "client-handled, not callable" note under their own heading, bounded to 8 notes so a client cannot inflate the prompt; an unknown nameless type gets one generic sentence, and an empty `type` is dropped entirely.
    - **`apply_patch` needed no further work, and that was verified rather than assumed.** The suspicion was that it rendered as `Args: {}`. Measured through the fixed renderer with the real captured declaration, it produces a genuine contract (the synthesized `{"input": "<raw text>"}` from section 39), and the end-to-end two-round loop creates the file for real (a 20-byte file written by the real binary). `apply_patch_tool_type` only accepts `freeform` in 0.145.0, so the `Args: {}` shape is unreachable from the real client.
    - **A note on the model id.** With `-m gpt-5-codex`, Codex's *own* catalog has no entry for the model, so it falls back to metadata without `apply_patch_tool_type` and never declares `apply_patch` — while its system instructions still tell the model to use it. That is client-side behaviour, not a gateway defect, and it is why a capture taken with that model id shows 10 tools and no `apply_patch`, while a catalog model shows 11 including it.

57. **Mid-Stream Failure Must Be a Terminal Event the Client Reads (`providers/responses_compat.py:ResponsesEventStream.failed`)**:
    - **[RESPONSES-STREAM] The gateway sent an error event Codex throws away.** On an upstream failure *after* content has been streamed, the gateway emitted `event: error`. Codex 0.145.0's SSE dispatch only handles `response.*`; `error` falls into `_ => trace!("unhandled responses event")` and is discarded wholesale. The stream then ends with no terminal event, so the client can only report `stream disconnected before completion: stream closed before response.completed` — the upstream's real reason (quota, context limit, a risk interception) is lost.
    - **Measured with the real binary, three arms, same mock, one variable** (the shape of the terminal event):

      | terminal event | what the user sees | requests |
      |---|---|---|
      | `error` only (pre-fix) | `stream closed before response.completed` | 6 |
      | `response.failed` only | `upstream quota exceeded` | 6 |
      | `error` + `response.failed` (now) | `upstream quota exceeded` | 6 |

      The same holds for a 400 (`upstream chat template rejected the request`) — the cause classes are not special-cased.
    - **What this fix is not.** All three arms produce the *same* request count. An earlier draft of this entry, and of the test docstring, credited the change with cutting retries from 5 to 0; that was wrong and came from reading the pre-fix symptom rather than measuring both arms. Once content has been sent the gateway cannot stop the client from retrying, and it should not try — a retry of a half-delivered stream produces a half-packet replay. The delivery is the fix: the failure reason reaches the user. `error` is still emitted alongside `response.failed` because it is the spec's error event and non-Codex SDKs read it.
    - Pinned by `tests/test_responses_protocol.py::test_mid_stream_failure_is_a_terminal_event_codex_reads`, which asserts `response.failed` is present, is the **last** event, carries the upstream's real message in `response.error.message`, and is not followed by `[DONE]` (a failed stream must never look like a clean finish).

58. **Thinking Display Suppression (`server.py:_thinking_display` / `_thinking_suppressed`)**:
    - **[PROTOCOL] Every Claude Code request asks for the reasoning text and then does not want it.** `/v1/messages` answered "should thinking be on?" (`_wants_thinking`) but never "should the client see it?". `thinking.display` was parsed and dropped. Captured from the real `claude` binary (2.1.293): **every** request carries `{"type":"adaptive","display":"omitted"}` — 6 of 6 bodies across two sessions, on both `claude-opus-5-5` and `deepseek-v4.1-flash`. The gateway emitted the reasoning as `thinking_delta` regardless.
    - **Why this is not a display preference**: the client stores the block in its conversation history and **replays it on the next turn**. Measured against a scripted upstream with the real binary: before the fix one tool loop grew to **310 request bodies and 154 assistant turns**, every one carrying a `thinking` block and re-paying its input tokens; the prompt grew to 464 messages. After the fix, the same probe ran **4 bodies with zero thinking blocks**, and the tool loop still closed (`assistant -> ['text','tool_use']` and a real `tool_result`). The cost is quadratic-ish in an agent session, which is exactly the workload this gateway exists to serve.
    - **Suppression is at the emission boundary, never at accumulation** — this is the load-bearing design point. `accumulated_thinking` still receives every reasoning chunk, so (a) `recover_tools_from_reasoning` still rescues a ```` ```tool_call ```` written entirely into the thinking channel (a turn with no answer and no call is a dead turn), and (b) `usage.output_tokens` still counts the thinking. The thinking *happened*; only its display was declined. Pinning both is the reason the suite has a recovery case and a token-count case rather than only "no thinking_delta" cases.
    - **Fail-open on shape, suppress only on the explicit value**: only `display == "omitted"` suppresses. `summarized`, `{"type":"adaptive"}` with no display, `{"type":"enabled"}` and bare `True` all keep the previous behaviour, asserted in both directions — an implementation that suppressed on "any thinking field" would silently blank every reasoning model's output.
    - **`output_config.effort` is deliberately still unread** (also on every request, `medium` or `high`). All five upstreams expose thinking as a boolean, so there is no granularity for it to land on; the Responses path does honour `reasoning.effort` because Codex needs on/off there. Reading it and mapping everything to `True` would be manufacturing a capability, which this file's own defect catalogue is a list of.
    - Pinned by `tests/test_anthropic_stream.py` (13 → 18 cases), verified red on the pre-fix code with the exact message `客户端要求 display=omitted，网关仍然发出了思考文本: 'thinking...'`. Two of the new cases were themselves wrong on the first write-up: one omitted the `{"reasoning": True}` marker on the closing fence (so the text channel was non-empty and the recovery rule correctly did not fire), and the control case exposed that — the same "an assertion about a window that is not the window the code protects" shape recorded in [M1].


59. **Per-Request Handshake Budget & the Falsified "Short Client Window" (`providers/failover.py:_handshake_budget`)**:
    - **[BUDGET] A boundary attached to the wrong layer.** `GATEWAY_FIRST_CHUNK_TIMEOUT` (180s) is enforced **per candidate**, and the dispatch loop walks every candidate in the capability ring. The real wait is therefore `candidates × per-attempt`, measured directly with `GATEWAY_FIRST_CHUNK_TIMEOUT=1.0` and a dead five-node ring: `failed after 5.0s`. At the default that is **900s**, during which the client receives no bytes at all — the response head has not been sent yet (`execute_chat` is awaited before the response is constructed, see H4), so `sse_keepalive` never gets to run, while the LB quota and the node semaphore are held by a request that is guaranteed to fail.
    - **The client-tolerance claim in the keepalive docstring was falsified by measurement, and the test that "should" have been written was wrong.** The suspicion was that the pre-first-chunk silence must be heartbeat-covered because clients give up quickly. Measured with the real binaries against a gateway whose upstream stayed silent: `claude -p` survived **420s** and `codex exec` survived **600s** — in both cases the harness's own cap fired, not the client. So "clients have a short no-bytes window" is false: an early response head + keepalive for the handshake phase would have solved a non-problem while *breaking* H4 (a real 401 during a slow handshake would degrade from a status line to an in-band event). The first test written for this — asserting headers arrive before the first chunk — was **deleted after measuring**, and the measurement is recorded in `providers/stream_keepalive.py` rather than quietly dropped. What the evidence does support is the actual defect: the *aggregate* wait exceeds both measured tolerances, and the fix belongs at the request level, not the byte level.
    - **A budget, not a shorter per-attempt timeout**: `GATEWAY_HANDSHAKE_BUDGET` (default 180s) caps total handshake time across all candidates and composes with the per-attempt timer via `min()`, so a healthy slow handshake (a reasoning model legitimately thinking for tens of seconds) is untouched, and a single-candidate request is value-for-value unchanged. The test asserts the **total request time** (5.08s → 1.21s), not any single attempt's, because the difference between the two is the defect.
    - **The expiry verdict must fire before `try`, not inside it** — the same "report a decision as an upstream failure" trap this file keeps recording. The budget check sits at the top of the dispatch loop; placing it inside `try` would let the `except` branch record a failure and a 60s cooldown against a node that was never called, turning "we chose not to dispatch" into "that upstream failed". The error names the budget and the tried nodes so an operator does not have to infer them. `GATEWAY_HANDSHAKE_BUDGET=0` restores the previous per-candidate behaviour exactly (pinned).
    - Pinned by `tests/test_handshake_budget.py` (5 cases), verified red on the pre-fix code with the exact message `整条请求耗时 5.08s —— 仍是「候选数 × 每次上限」（5 × 1.0s），请求预算没有生效`.

60. **Real-Binary E2E: A Two-Round Tool Loop Must Be Driven With a *Declared* Tool Name (`/tmp/e2e/loop_server.py`)**:
    - **[E2E] The verification harness can manufacture the very defect it is looking for.** Driving the real binaries against a scripted upstream produced two opposite readings on the *same* gateway: `claude -p` closed a full loop (round 1 emitted a `toolu_`-id call, the real `Bash` ran and printed `e2e-ok`, round 2 received `[Tool Result for toolu_…]` and answered, `EXIT=0`), while `codex exec` printed the ```` ```tool_call ```` fence as **plain text**. The obvious conclusion — "the Responses path does not deliver tool calls" — is wrong. The scripted upstream hardcoded `{"name": "Bash"}`, a name **Claude Code** declares and **Codex does not**: the captured request declares `exec_command`, `write_stdin`, `update_plan`, `request_user_input`, `view_image`, `multi_agent_v1`, `get_goal`, `create_goal`, `update_goal`. The gateway's declared-name allowlist (anti-fabrication, section 32) therefore returned the call to the client as text, exactly as designed. The run was measuring the allowlist working, not a broken loop.
    - **The harness fix is to read the tool out of the injected contract**: parse `` - `name`: … Args: {…} `` out of the prompt the gateway actually received, take a name the client really declared, and fill its `required` args. Re-run: round 1 emits `exec_command {"cmd": "echo e2e-ok"}`, Codex really executes it, round 2's captured prompt carries `[Tool Result for call_69a98e9cddcc41eb8e62685d25687f97]: … Process exited with code 1 … bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`, and Codex answers "The command printed e2e-ok. Done." (`EXIT=0`, 2 captured bodies). The tool result is evidence the round trip closed even though this machine's bubblewrap cannot create a net namespace — that is the sandbox refusing, not the gateway.
    - **A second harness trap, same family**: the round detector must match a *real* id, `r"\[Tool Result for [A-Za-z0-9_-]+"`. A bare `"[Tool Result for " in prompt` fires on round one because the gateway's own tool contract text contains the literal `[Tool Result for <id>]`, so the loop never happens and the run looks like "the client only ever sends one round".
    - **The diagnostic that separated the two cases was instrumenting the *upstream request*, not the client's stdout.** Logging `declared_tools` / `chosen_tool` / `has_tools_section` per captured body turned "Codex prints text" into "the harness asked for a tool Codex never declared" in one run. Client-side output alone cannot distinguish a gateway defect from a harness defect, which is the same reasoning that makes every test in this repo assert on the prompt the upstream really receives (sections 32b, 39, 43).
    - **Also measured, and worth knowing before trusting `apply_patch` E2E**: with `-m gpt-5-codex` (a name absent from `codex debug models`) Codex falls back to metadata with no `apply_patch_tool_type` and declares **no `apply_patch` at all** — while its instructions still tell the model to use one. With any catalog model the declaration appears as `{"type":"custom","name":"apply_patch",…}` (freeform), which the gateway already renders with the synthesized `{"input": …}` contract and emits as `custom_tool_call` (section 39). So an "apply_patch does not work" report against `gpt-5-codex` is a Codex metadata artifact, not a gateway bug.

60b. **Fair Budget Shares & the Retry Storm That Ate the Savings (`providers/failover.py`, `server.py:_DETERMINISTIC_REFUSAL_ERR_TYPES`)**:
    - **[BUDGET-2] The first budget fix introduced a regression worse than the defect.** `GATEWAY_HANDSHAKE_BUDGET` was applied as `min(per_attempt, remaining_budget)`, i.e. the **whole** remaining budget went to whichever candidate was being tried. At the defaults (`GATEWAY_FIRST_CHUNK_TIMEOUT=180`, `GATEWAY_HANDSHAKE_BUDGET=180`) the first slow candidate consumed the entire allowance and candidates 2–5 were never tried. Measured against a dead ring with the real `claude -p`: `[握手预算] 总预算 15.0s 已耗尽（已尝试 1 个节点）`. That is *worse* availability than the pre-fix code, which at least walked all five — and it broke the single most common real fault shape, "first node slow, second node fine". The budget is now **divided fairly among the untried candidates** (`remaining_budget / (later_candidates + 1)`), so the last candidate still takes the whole remainder and the total-time bound is exactly preserved. Verified: with a hung first candidate and a healthy second, the request now self-heals instead of failing.
    - **A sub-second share must be reported honestly**: `f"{timeout:.0f}s"` printed a 0.3s share as `在 0s 内未返回首包`. A number that contradicts the real wait is the same "the report lies" class as the rest of this file; the message now uses `:.1f`.
    - **When every candidate merely times out, the ring-exhausted error no longer said the budget was involved** — and an operator cannot tell "budget too small" from "the nodes are genuinely down". The terminal error now states the budget, the fair share and which knob to raise.
    - **[H7] The 8× retry storm that consumed the entire saving.** With the budget working (15s per request, 504), a real `claude -p` run still burned the full 240s harness cap and issued **8 requests**, each walking all five nodes — 40 upstream calls against a ring already known to be dead. That is exactly the "automated client retrying" signature the whole avoidance line exists to prevent. Controlled experiment (same server, same command, **only the response header differs**): 504 alone → 240s / 8 requests / no verdict; `+ x-should-retry: false` → **19s / 1 request / 5 upstream calls total**, `EXIT=1`, with the full failure reason shown to the user. So the ring walked to completion **is a deterministic conclusion** and now carries the suppression header plus a `Retry-After` taken from the shortest remaining node cooldown (the real window, not a constant). A single-node timeout with candidates left is still *not* suppressed — a different node may genuinely work.
    - **The scope was narrowed deliberately**: `upstream_timeout` joined `_DETERMINISTIC_REFUSAL_ERR_TYPES` only because every raise site for it is terminal — the budget expiry (remaining candidates are provably too slow) and the ring-exhausted branch. 5xx/WAF/401 semantics are decided by their own branches and were not touched.
    - Pinned by `tests/test_handshake_budget_fairness.py` (2 cases, verified red with `第一个候选超时后请求直接失败（upstream_timeout），健康的第二候选一次都没被尝试`) and `tests/test_ring_exhaustion_backoff.py` (2 cases, verified red with `整环握手超时的终局没有带上 x-should-retry: false`; the second case pins that a healthy response never carries it).
