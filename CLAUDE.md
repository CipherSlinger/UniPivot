# CLAUDE.md

This file provides comprehensive guidance to Claude Code (claude.ai/code) and Codex CLI when working with code in this repository.

## Commonly Used Commands

### Environment & Dependencies
```bash
# Set up virtual environment and install dependencies
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# If system Chrome is not installed, install Playwright Chromium
.venv/bin/playwright install chromium
```

### Running the Gateway
```bash
# Start the FastAPI server on 127.0.0.1:8000
./run.sh
# Or directly via uvicorn (note: `python -m uvicorn`, not `.venv/bin/uvicorn`):
.venv/bin/python -m uvicorn server:app --host 127.0.0.1 --port 8000
```

**Why `python -m uvicorn` and not `.venv/bin/uvicorn`**: a venv's console scripts bake in the **absolute** interpreter path from creation time, so a venv that was moved or copied (as this machine's `.venv` was — created under a different project directory) fails with `bad interpreter: No such file or directory` while the venv itself is perfectly usable. `run.sh` therefore resolves an interpreter that can actually `import uvicorn` (project venv first, system `python3` as fallback) and launches it as a module, which needs no shebang and works in both cases. Repairing the moved venv's scripts is `sed`-level work on the stale shebang line; recreating it (`python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt`) is the heavier alternative.

**Before the first start after a long idle period**, run the login pass first: the startup sequence performs a silent token refresh and an initial health probe for each provider, and with stale credentials each of those is a real upstream request — exactly the "automated credential attempt" signature the risk-control line exists to avoid. `.venv/bin/python login.py all` first, then `./run.sh`.

## Architecture & Code Structure

The repository is a local multi-protocol API gateway (`server.py`) supporting three standard protocols:
- **OpenAI Chat Completions** (`/v1/chat/completions`, `/chat/completions`)
- **Anthropic Messages** (`/v1/messages`, `/messages`, `/v1/messages/count_tokens`)
- **OpenAI Responses** (`/v1/responses`, `/responses` for Codex CLI)

### Core Subsystems
1. **Peer Capability Rings & Failover Grid (`providers/failover.py`)**:
   - Manages three capability rings: `REASONING`, `FLAGSHIP`, and `SPEED`.
   - Ensures transparent failover before the first token chunk is emitted, preventing half-packet pollution.
   - Dynamic cooldown avoidance for WAF (e.g., RGV587) and 429 rate limits, with exponential backoff (30s~120s).
   - Adaptive pacing, jitter injection, and per-provider concurrency limiting via semaphores.

2. **Self-Healing & Auto-Hotfix Brain (`healing/`)**:
   - `HealthMonitor` (`healing/monitor.py`): Performs non-blocking background probes (interval: `HEAL_CHECK_INTERVAL`, default 300s). Transitions state across `healthy`, `degraded`, `recovering`, and `offline`.
   - `HealingEngine` (`healing/healer.py`): Upon upstream protocol failure, elects the highest-performing healthy model to craft repair prompts and dispatches local CLI repair agents.
   - `AgentRunner` (`healing/agent_runner.py`): Discovers and bootstraps local `claude` or `codex` CLI environments, launching isolated subagents to update code and run tests.

3. **HTTP/2 Connection Pool Management (`providers/http_client.py`)**:
   - Global singleton `AsyncClient` configured with connection limits (max 100 conns, 40 keep-alive, 30s expiry).
   - Multiplexing enabled via `http2=True`.

4. **Atomic Credential Store (`session_store.py`)**:
   - Resolves credentials with priority: `Environment Variables > session/<provider>.json > None`.
   - Thread-safe POSIX atomic write pattern (`os.replace` + `os.fsync`) with strict `0o700` directory and `0o600` file permissions.

5. **Tool / Function Calling & Token Counting**:
   - `anthropic_compat.py`: Balanced bracket parser supporting deeply nested JSON tool calls and XML tool syntax.
   - `responses_compat.py`: Standard OpenAI Responses protocol serializer with `function_call_arguments.delta` / `done`.
   - `base.py`: Token estimation (`_est_tokens`) supporting bilingual CJK weighting.

6. **Smart Session Affinity & State Handoff Engine (`providers/session_affinity.py`)**:
   - Manages LRU and TTL-based conversation tracking to pin multi-turn agent sessions to the same upstream provider.
   - Detects provider degradation, WAF cooldown, or failure and performs seamless cross-model state handoff with heterogeneous upstream conversation ID stripping.
   - Emits `x-session-affinity`, `x-session-handoff-from`, and `x-session-turns` telemetry headers across all protocols.

7. **SingleFlight & Stream Fanout Engine (`providers/singleflight.py`)**:
   - Computes deterministic cross-protocol SHA-256 fingerprints across wire parameters and payload semantics.
   - Leader/Follower flight groups with streaming multi-subscriber fanout and historical replay buffers.
   - Non-streaming response coalescing with `x-singleflight: leader | follower` telemetry headers and zero duplicate upstream calls.

8. **Disconnect Guard & Upstream Reclamation (`providers/disconnect_guard.py`)**:
   - Propagates client disconnects to the upstream async generator and explicitly closes it, releasing the HTTP/2 connection slot and upstream concurrency quota immediately instead of letting an abandoned stream drain quota.
   - Guarantees a terminal state for the SingleFlight flight group on every exit path, including `CancelledError`, and reclaims flight groups whose leader vanished so followers can never hang.
   - Emits `x-disconnect-guard` telemetry headers across all protocols.

9. **Token Count Cache (`providers/token_counter_cache.py`)**:
   - Memoizes the deterministic `/v1/messages/count_tokens` result behind a bounded LRU, eliminating repeated O(n) estimation on long conversations.

10. **Request Lifecycle Finalization & Quota Reclamation (`providers/singleflight.py:terminate_aborted_group`)**:
    - Guarantees the non-streaming SingleFlight leader path terminates its flight group on every exit, including client aborts (`CancelledError` is a `BaseException`, so `except Exception` never fires) — without it the group stays non-terminal forever, hanging every follower.
    - Makes the `load_balancer` concurrency slot deterministically idempotent-released on abort; the Responses endpoint previously had no `finally`, so an aborted request leaked its slot permanently and the balancer would shed away from that provider until restart.
    - See `tests/test_lifecycle.py`.

11. **Risk-Control Ledger & Durable Cooldown (`providers/risk_ledger.py`)**:
    - Persists each provider's cooldown deadline and consecutive-failure count with a POSIX atomic write (`os.replace` + `os.fsync`, dir `0o700` / file `0o600`), so a restart no longer wipes avoidance and immediately re-pokes a node that upstream has already risk-banned (the ban window is only lengthened by retries).
    - Appends every risk/WAF-captcha/auth interception to an auditable JSONL ledger (time, node, HTTP status, severity tier, reason, evidence excerpt), auto-pruned at `GATEWAY_RISK_LEDGER_MAX_LINES`.
    - Severity tiers `auth > ratelimit > waf`: repeated (≥3) auth failures escalate to a long cooldown (`GATEWAY_AUTH_COOLDOWN_BASE` × 2ⁿ, capped by `GATEWAY_AUTH_COOLDOWN_MAX`), while a first auth failure keeps the short legacy cooldown so a re-login never locks a healthy node for an hour.
    - Exposes `risk_ledger` diagnostics via `/v1/diagnostics` and a 24h summary via `/health`; `GATEWAY_DISABLE_RISK_LEDGER=1` degrades to pure in-memory cooldowns. See `tests/test_risk_ledger.py`.

12. **Cooldown-Aware Health Probe Gate (`healing/monitor.py`)**:
    - `HealthMonitor` consults `CooldownTracker` before every probe: a node in a risk-avoidance cooldown is marked `cooling` and the real network probe is skipped entirely. Without this the 300s audit loop re-poked an upstream-banned node every interval, lengthening the ban window — exactly the failure mode the durable ledger guards against, one layer up.
    - Cooling probes neither increment `consecutive_failures` nor trigger self-healing, so a risk ban is never misread as a node fault; `GATEWAY_DISABLE_PROBE_COOLDOWN_GATE=1` disables the gate and `/v1/diagnostics` exposes `healing_status.cooldown_probe_skips`. See `tests/test_probe_gate.py`.
    - **[OPT-018] Read-time cooldown overlay + healer election avoidance**: `ProviderHealth.status` defaults to `healthy`, so before the first probe cycle (or right after a restart) a node sitting in a risk-avoidance cooldown still *reports* healthy — and `pick_healer_model` would elect it as the self-healing brain, dispatching a real upstream completion through a banned account. `get_status()`/`get_all_statuses()` now overlay live cooldown state ("cooling") at read time without persisting it, `pick_healer_model` excludes cooling candidates via `monitor.get_cooldown_remaining()` and records `cooldown_healer_skips`, and when no non-cooling candidate remains it returns `None` so healing is deferred instead of touching the banned node. The single master switch for all cooldown avoidance is `GATEWAY_DISABLE_COOLDOWN_GATE=1` (`GATEWAY_DISABLE_PROBE_COOLDOWN_GATE` remains as a back-compatible alias).

13. **Cooldown-Aware Token Refresh Gate (`server.py:_auto_refresh_stale_sessions`)**:
    - The startup silent token-refresh pass consults the cooldown tracker: a node in a risk-avoidance cooldown is not refreshed (a login/refresh call to an upstream-banned account would only deepen the ban). Deferred nodes are retried by a bounded background thread (`GATEWAY_REFRESH_DEFER_POLL`, `GATEWAY_REFRESH_DEFER_MAX_WAIT`, default 24h) that refreshes once the cooldown clears and otherwise gives up cleanly. See `tests/test_refresh_gate.py`.

14. **Evidence-Driven Adaptive Pacing (`providers/failover.py:compute_pacing_multiplier`)**:
    - The traffic pacer widens each provider's call interval proportionally to its recent risk-control interceptions (weighted `waf > auth > ratelimit`), so a node that just tripped a captcha or 429 is called more slowly until its 6h evidence window drains. This is the "avoidance" half of the ban problem: when a ban cannot be bypassed, slow down before it happens. Cached per provider (`GATEWAY_PACING_EVIDENCE_TTL`, default 60s); `GATEWAY_DISABLE_ADAPTIVE_PACING=1` reverts to the fixed interval. See `tests/test_adaptive_pacing.py`.

15. **Graceful Shutdown Drain (`server.py:_drain_inflight_requests`)**:
    - A pure-ASGI `InflightTrackerMiddleware` counts in-flight requests across the *entire* response (its `await self.app(...)` only returns after a streaming body finishes, unlike `BaseHTTPMiddleware`). On shutdown the lifespan finally-block waits — bounded by `GATEWAY_SHUTDOWN_DRAIN_TIMEOUT` (default 30s) — for that count to reach zero before stopping the health monitor and closing the HTTP client, so a restart no longer severs a half-sent stream (which would make clients retry and re-load upstream). `inflight_requests` is exposed on `/health` and `/v1/diagnostics`. See `tests/test_graceful_drain.py`.

16. **Durable Conversation Deletion Queue (`providers/conversation_gc.py`)**:
    - Anonymous calls (no client `conversation_id`) leave a temporary session in the user's upstream web sidebar, so the gateway deletes it afterwards. The old `asyncio.create_task(provider.delete_conversation(cid))` was fire-and-forget: a failed delete or a process restart silently leaked the session forever. `ConversationGC` now enqueues each deletion in a POSIX-atomic JSON queue (dir `0o700`, file `0o600`) that survives restarts, retries via a background drain (bounded by `GATEWAY_CONVERSATION_GC_MAX_ATTEMPTS`, default 5, then drops with a warning), and drains once at startup to clean up the previous process's leftovers. `GATEWAY_DISABLE_CONVERSATION_GC=1` degrades to the legacy fire-and-forget behavior. Exposed as `conversation_gc` in `/v1/diagnostics`. See `tests/test_conversation_gc.py`.
    - **[OPT-017] Cooldown-aware deletion gate**: a delete is itself a real upstream request, so firing one at a node in a risk-avoidance cooldown is just another channel that keeps touching a banned account. Deletions for a cooling provider are deferred — the entry stays queued and does **not** consume a retry attempt — and are performed by a later drain once the cooldown clears. Mirrors the probe gate (OPT-012) and the refresh gate (OPT-013). `GATEWAY_DISABLE_CONVERSATION_GC_COOLDOWN_GATE=1` reverts; deferrals are exposed as `deferred_by_cooldown` in `/v1/diagnostics`. A gate-query failure never blocks deletion (zero-regression default).

17. **Test Isolation of Durable Stores (`tests/*`)**:
    - The durable stores (risk ledger cooldowns, interception JSONL, conversation GC queue, device identities) resolve to a `tempfile.mkdtemp()` directory under `TESTING=1`, but several legacy suites set fake tokens *without* setting `TESTING`, so a test run wrote fake cooldowns into the developer's real `session/` directory — and, because every `CooldownTracker` restores from the shared ledger singleton, later cases in the same process inherited cooldowns recorded by earlier ones, making results order-dependent (`tests/test_failover.py` was red for this reason). Those suites now set `TESTING=1` (isolated temp dir, zero writes to `session/`), and `tests/test_failover.py` additionally sets `GATEWAY_DISABLE_RISK_LEDGER=1` so it tests pure in-memory cooldown semantics as designed — cross-restart durability has its own suite, `tests/test_risk_ledger.py`. `tests/test_providers.py` was found writing device identities into the real `session/` for the same reason and now sets `TESTING=1` too (see OPT-030).
    - **[OPT-032] The `.env` hole in that isolation**: `server.py` called `dotenv.load_dotenv()` **at import time**, while every suite's "clear all `GATEWAY_*`" prelude runs *before* the import — so one line of real deployment config in `.env` was re-injected into the process *after* the prelude and defeated the isolation entirely. Measured: adding `GATEWAY_QUARANTINE="deepseek:21d"` to `.env` (a legitimate operator declaration) turned `tests/test_quarantine_hardstop.py`'s first case red (`is_quarantined("deepseek")` expected `False`, got `True`) with the code entirely correct — the same "the developer's machine decides the test result" class of order-dependent failure as above, one layer out. `load_dotenv()` is now gated on `TESTING != "1"`, which is the existing convention of every suite that imports `server` (zero new convention, and semantically right: a test process has no "deployment config"). The two suites that import `server` *without* `TESTING` are unaffected.

18. **Operator Quarantine Lease (`providers/quarantine.py`)**:
    - Automatic cooldowns are **capped** (`GATEWAY_AUTH_COOLDOWN_MAX`, default 24h), but a real account-level ban lasts days. When the cap expires the gateway would re-touch a still-banned node and deepen the ban. `QuarantineStore` lets an operator set a durable long-duration lease per provider — resolved by absolute expiry timestamp, POSIX-atomic on disk (dir `0o700`, file `0o600`), re-applied on restart, and expiring lazily. Leases only ever **extend** the avoidance window (reads take `max()`), so a mistyped short lease can never release a banned node early.
    - **Single source of truth**: the lease is folded into `CooldownTracker.get_remaining_cooldown()` / `is_in_cooldown()`, so *every* existing gate honors it with zero extra wiring — health probe (OPT-012), token refresh (OPT-013), conversation GC (OPT-017), healer election (OPT-018), router selection and adaptive pacing.
    - Configuration and admin surface: `GATEWAY_QUARANTINE="deepseek:72h,glm:30m,kimi:2026-10-20T00:00:00"` applies at startup (durations `s/m/h/d` or ISO-8601), `GET/POST/DELETE /v1/admin/quarantine` views/sets/clears at runtime, `GATEWAY_DISABLE_QUARANTINE=1` turns the store off, and `GATEWAY_QUARANTINE_DIR` overrides the location. Exposed as `quarantine` on `/health` (active leases) and `/v1/diagnostics`. See `tests/test_quarantine.py`.
    - **[OPT-021] Hard-stop at the dispatch boundary**: folding the lease into the *cooldown reading* gated probes, refresh, conversation GC and healer election — but **not** the dispatch path. `get_fallback_candidates` only *demoted* cooling nodes, and `execute_chat` dispatched the primary unconditionally, so a node under a 72h lease was still sent real upstream requests on every failover (empirically confirmed for both DeepSeek and Doubao). Quarantine is now a **hard block with semantics distinct from soft cooldown**: a soft cooldown (automatic, capped at `GATEWAY_AUTH_COOLDOWN_MAX`) stays demote-only so a ring where everything is briefly cooling can still make a last-resort attempt — availability is preserved; an operator lease (account-level ban, measured in days) is never dispatched at all, at any point. A quarantined primary is redirected, quarantined nodes are excluded from the candidate set, and if the whole ring is quarantined the request **fails closed** with `503 / err_type="quarantined"`, zero upstream calls, and a message telling the operator how to lift the lease (`overloaded_error` in the Anthropic protocol). `GATEWAY_DISABLE_QUARANTINE_HARD_STOP=1` reverts to demote-only. See `tests/test_quarantine_hardstop.py`.

19. **Post-Avoidance Recovery Probation (`providers/failover.py`)**:
    - **[OPT-022] Canary re-entry after an avoidance episode**: avoidance solves *not touching* a banned node but not *not re-triggering* the ban. When a multi-day ban lifts, the demand that was suppressed for days releases at once — the same burst signature that caused the original ban, immediately re-banning the account. On the first dispatch after an avoidance episode ends (risk cooldown expiry, or a quarantine lease expiring or being cleared), the node enters a **probation window** (`GATEWAY_PROBATION_WINDOW`, default 300s) during which at most **one handshake is in flight** and the pacing interval is multiplied (`GATEWAY_PROBATION_PACING_FACTOR`, default 2.0×). It graduates after `GATEWAY_PROBATION_MIN_SUCCESSES` (default 3) consecutive successes; the window is a *renewal unit*, not a licence to resume at full speed (see the [OPT-028] bullet below).
    - The serialization gate covers *handshake to first chunk* only, not the whole streaming response, and is acquired **before** the concurrency semaphore so requests cannot occupy concurrency slots while queued behind the gate. Because plain 5xx/timeouts are upstream faults rather than account flagging, they never enter probation — no thundering herd to protect against, hence zero regression for existing paths. **[OPT-028] Graduation is evidence-based, never time-based**: the window is only a *renewal unit* — exhausting one renews it (up to `GATEWAY_PROBATION_MAX_RENEWALS`, default 3, i.e. at most `window × 4` gated) with the serialization gate and widened pacing still in force, and once the renewal budget is spent the node is graduated only if it holds positive evidence (≥1 successful handshake); with zero evidence it stays gated, because gating a node that has never been successfully verified costs nothing (no successful handshake means no burst to release) while un-gating hands a completely unproven account full concurrency. The same applies to `GATEWAY_PROBATION_WINDOW=0` ("no time allowance", not "release immediately"); `GATEWAY_DISABLE_PROBATION=1` remains the full off switch. A late success always graduates the node, so the gate can never deadlock. See `tests/test_probation.py`.
    - `GATEWAY_PROBATION_PACING_FACTOR` is applied inside `CooldownTracker.compute_pacing_interval()` (pure, order-correct: base × evidence multiplier × probation multiplier) so it composes with the OPT-014 adaptive multiplier instead of replacing it. Probation state is persisted (`episode_ends`) and survives restarts, since a restart would otherwise be a one-step bypass — the retention horizon covers the **renewed** window, so a restart mid-renewal cannot discard the episode. `GATEWAY_DISABLE_PROBATION=1` turns it off entirely. Telemetry: `x-risk-probation: 1` header plus `probation.active` / `probation.stats` on `/v1/diagnostics` (the stats include derived `renewing` / `awaiting_first_handshake` / `budget_exhausted`, so "is the probation actually doing anything?" is observable rather than assumed). See `tests/test_probation.py`.

20. **Risk-Control Dossier & Avoidance Verdict (`providers/risk_dossier.py`)**:
    - **[OPT-023] All-time interception record + the "can it be bypassed?" answer**: `recent_interceptions()` is a *sliding window* (24h default), which is right for driving real-time avoidance but wrong for answering the operational question "how many times has this provider been intercepted, for what reasons, can it be worked around, does re-login help?". A per-provider ban window is measured in *days*, so the 24h window has almost always discarded the evidence before the ban lifts. The dossier aggregates the **whole** (bounded) ledger: total count, first/last timestamps, severity breakdown, and the last real upstream message verbatim.
    - **Posture derivation, fail-closed**: the facts are scattered across four places — quarantine lease, soft cooldown, recovery probation (OPT-022) and the OPT-014 evidence-driven pacing multiplier. They collapse into one posture, heaviest-wins: `quarantined` > `cooling` > `probation` > `watch` > `clear`, each with a `dispatchable` flag. Only a hard lease is non-dispatchable; a soft cooldown stays dispatchable, preserving the last-resort availability semantics of OPT-021.
    - **Avoidance verdict per severity** (`AVOIDANCE_MATRIX`): each tier answers `technically_bypassable` (never true — no client-side action evades a risk control), `recoverable_by_relogin`, `auto_recovers`, typical span, and a concrete strategy. `auth` (expired token/session) and `waf` (captcha/RGV587) *do* recover via `python login.py <provider>`; `ratelimit` is transient and self-healing, so re-login is pointless; an account-level ban (`ban`) is **not** recoverable by re-login — the ban binds the account, not the token — and the only correct strategy is zero-touch waiting for the platform to lift it. Providers holding a lease are always judged as `ban` regardless of what the ledger says.
    - **Read-only**: querying the dossier never mutates risk state (no lease cleared, no cooldown reset, no ledger append), so it is safe to expose on diagnostic paths. `GATEWAY_DISABLE_RISK_DOSSIER=1` marks it disabled. Telemetry: `risk_dossier_summary` on `/v1/diagnostics`, full detail (plus `?provider=<key>` for a single node) on `GET /v1/admin/risk`. See `tests/test_risk_dossier.py`.

21. **Cross-Provider Risk Correlation (`providers/risk_correlation.py`)**:
    - **[OPT-024] The blind spot of per-account reasoning**: every avoidance mechanism so far (OPT-011..OPT-023) is scoped to a *single* provider account — that account was intercepted, so cool it, quarantine it, watch it. But there is a second cause of interception: **our own client footprint** (header fingerprint, UA, device params, egress IP, request timing) being flagged by the platform. The accounts are then not intercepted independently — they are multiple symptoms of one root cause. The two causes demand **opposite** responses: for a single-account cause "switch to another node and keep going" is correct; for a systemic cause it is useless and actively harmful, because the new node gets flagged on the same footprint and you simply burn the remaining accounts one by one. Per-account reasoning can never see this layer — it explains each interception as "this provider's risk control is strict" and hands over all five accounts in sequence.
    - **Correlation is measured in *distinct providers*, not interception counts**: one account intercepted a hundred times is still a single-account problem. The detector scans the ledger (read-only) over `GATEWAY_RISK_CORRELATION_WINDOW` (default 900s) and computes the largest number of distinct providers intercepted inside any `GATEWAY_RISK_CORRELATION_BURST_WINDOW` sub-window (default 120s), using a two-pointer sliding window so it stays O(n).
    - **Grading, strongest signal first**: `systemic` when the burst holds `GATEWAY_RISK_CORRELATION_SYSTEMIC_MIN` (default 3) distinct providers — several different accounts hit within minutes is essentially impossible from independent causes; else `widespread` when `GATEWAY_RISK_CORRELATION_WIDESPREAD_MIN` (default 3) distinct providers appear in the window but not as a burst; else `localized`; else `none`.
    - **Global pacing governor**: `systemic` multiplies every node's interval by `GATEWAY_RISK_CORRELATION_SYSTEMIC_FACTOR` (default 2.0), `widespread` by `GATEWAY_RISK_CORRELATION_WIDESPREAD_FACTOR` (default 1.25). This composes as a fourth factor in `CooldownTracker.compute_pacing_interval` and in `TrafficPacer`, so it multiplies with the OPT-014 evidence factor and the OPT-022 probation factor rather than replacing either. The multiplier is TTL-cached (`GATEWAY_RISK_CORRELATION_CACHE_TTL`, default 15s) because the pacing path is hot, and defaults to **1.0** whenever there is no correlation evidence — zero regression.
    - Each grade carries a playbook stating explicitly whether `rotate_node_helps` and `per_account_avoidance_helps`. Telemetry: `risk_correlation` on `/v1/diagnostics`, full report at `GET /v1/admin/risk/correlation`. `GATEWAY_DISABLE_RISK_CORRELATION=1` disables. See `tests/test_risk_correlation.py`.

22. **Whole-Ring Credential Outage & Fast-Fail (`providers/credential_watch.py`)**:
    - **[OPT-025] Live evidence — the outage was misdiagnosed as a WAF ban**: the risk ledger recorded 335 interceptions over 80 minutes, of which **312 were `auth` (401), not `waf`**, with all five providers returning 401 in the *same second*, repeating every ~7 minutes. Five independent token expiries in the same second is not a coincidence: the real sequence is **one client request failing over through all five nodes, every node rejecting on an expired credential**, so a single request emits five auth records in one second. The ring has zero serving capacity — failover cannot possibly succeed.
    - **The storm is itself the risk trigger**: with no usable credentials the gateway still walked all five nodes for every client request. 335 failed requests carrying invalid credentials in 80 minutes is exactly the *automated credential attempts* signature upstream WAFs score on — the storm was itself inflating the risk score, plausibly contributing to the bans. So the correct behaviour is not "retry harder" but **stop immediately**, which is precisely what a per-node cooldown cannot express: each node cooling independently still lets the whole ring be walked.
    - **Semantics distinct from everything else**: a soft cooldown is per-node, time-capped and self-healing; a quarantine lease (OPT-020/021) is per-node, operator-declared and measured in days. A credential outage is **ring-wide**, needs no operator declaration, and recovers the instant credentials are renewed — it is not "this node has a problem" but "we have no usable credentials", so the remedy is re-login, not avoidance. Detection is by **distinct providers** (as in OPT-024, not by failure count): `GATEWAY_CREDENTIAL_OUTAGE_MIN_PROVIDERS` (default 3) different providers auth-failing within `GATEWAY_CREDENTIAL_OUTAGE_WINDOW` (default 300s) trips it.
    - **Fast-fail at the dispatch boundary**: checked at the top of `execute_chat`'s dispatch loop — *before* the OPT-021 quarantine branch and before any provider is even instantiated — so the request is refused with `503 / err_type="credential_outage"` and **zero upstream calls** (`authentication_error` in the Anthropic protocol, the closest enum, since Anthropic has no credential-outage type). The message names the dead providers and tells the operator to run `.venv/bin/python login.py all`.
    - **Never wedges**: the state carries a TTL (`GATEWAY_CREDENTIAL_OUTAGE_TTL`, default 120s) after which exactly one request is let through as a probe; if the ring is still 401ing, the very first failure re-arms it. Probing therefore degrades from "once per client request" to "once per TTL" — the storm is flattened with no possibility of the state deadlocking into permanent refusal. A single success (`record_success` → `note_success`) drops that provider from the failed set, so capacity returning below the threshold **immediately resumes dispatch** (fail-open). `GATEWAY_DISABLE_CREDENTIAL_WATCH=1` disables it (and `GATEWAY_DISABLE_RISK_LEDGER=1` co-disables, matching the quarantine convention so pure in-memory cooldown suites are unaffected). Telemetry: `credential_outage` on `/v1/diagnostics`, `GET/DELETE /v1/admin/credential-outage` to inspect the state and to lift it immediately after re-login. See `tests/test_credential_watch.py`.

23. **Credential Renewal Detection & Cause-Scoped Avoidance Release (`providers/credential_renewal.py`)**:
    - **[OPT-026] The 24-hour tail after the storm**: `record_failure` escalates auth failures as `GATEWAY_AUTH_COOLDOWN_BASE`(1800s) × 2ⁿ, capped at `GATEWAY_AUTH_COOLDOWN_MAX`(86400s). The real ledger shows 54/54/54/87/60 auth failures per node — **every one hit the 24h cap**, and the state is persisted and restored across restarts. So after the storm the five nodes each stay frozen for a full day.
    - **Why the escalation becomes wrong once the cause is gone**: it punishes *holding one dead credential and retrying with it* — which is correct, since every retry is another "automated credential attempt". But once the credential is renewed the offence no longer exists; continuing to freeze punishes the *already-repaired system*. `get_remaining_cooldown()` still returns 24h → probes skipped, healer election excludes the node, routing demotes it, and worst of all `server.py:_deferred_refresh_after_cooldown` **defers the silent token refresh itself by up to 24h** — i.e. the state the credential failure created locks the only mechanism that can repair it. Reverse check: OPT-023's dossier already answers `auth → recoverable_by_relogin = True`, so the gateway tells the operator "re-login fixes this" and then keeps avoiding the node for 24h after they do it.
    - **Renewal detection by content fingerprint**: on every auth failure the credential source (`session/<provider>.json`) is fingerprinted — `sha256(token|cookie|captured_at|user_id|device_id)`, degrading to `meta:mtime_ns:size` when unparseable. The fingerprint is persisted with the cooldown, so "re-login first, restart second" is still recognised. `Session.save()` writes atomically via `os.replace` and refreshes `captured_at` on every capture, so any real re-login necessarily changes the fingerprint. The tracker only *answers* "did the credential change"; the state mutation lives in `CooldownTracker.release_auth_avoidance()`.
    - **Cause-scoped, fail-closed release**: only a cooldown whose most recent severity is `auth` may be released (the severity is persisted alongside the cooldown; when the record is missing — state predating this mechanism, e.g. the real ledger's five 24h freezes — it degrades to a *read-only* query of the ledger's most recent interception for that node, still cause-scoped). A node holding an operator lease is **never** released (a lease is an account-level ban; re-login is useless). A `waf`/`ratelimit` cause is **never** released on its behalf. No record / unreadable credential / unchanged fingerprint → "not renewed". Release re-enters via the OPT-022 recovery probation (serialized canary + widened pacing), because the demand suppressed for days releases at the moment of renewal with the same burst signature the probation exists for.
    - **Unblocks the repair chain**: releasing zeroes `get_remaining_cooldown()`, so the OPT-013 refresh gate stops deferring the silent token refresh — the one automatic repair path. Startup runs the scan (`await cooldown_tracker.release_renewed_credentials()`), because "re-login + restart" is the common operator flow. `GATEWAY_DISABLE_CREDENTIAL_RENEWAL=1` disables it (and `GATEWAY_DISABLE_RISK_LEDGER=1` co-disables, matching the quarantine convention). Telemetry: `credential_renewal` on `/v1/diagnostics`, `GET /v1/admin/credential-renewal`, `POST /v1/admin/credential-renewal/scan` (body `{"providers":[...]}` for env-var credentials with no file to fingerprint), and `DELETE /v1/admin/credential-outage` now also releases the auth avoidance of the cleared providers. See `tests/test_credential_renewal.py`.

24. **Account-Level Ban Inference & Self-Clearing Auto Lease (`providers/failover.py` / `providers/quarantine.py`)**:
    - **[OPT-027] The loop OPT-026 left open**: OPT-026 releases the auth avoidance the moment a renewed credential appears — correct, but *if the node still 401s* the gateway re-dispatches, takes another 401, re-escalates by 2ⁿ back to 24h, and OPT-026 releases again on the next scan. Each round touches the upstream account once more, and the loop never terminates on its own. That is exactly the failure mode the standing constraint forbids: a banned node must be **zero-touched**, not periodically poked.
    - **401 has two causes whose remedies are opposite**: (a) *credential expiry* → the fix is re-login (`python login.py <provider>`), which OPT-026 already handles; (b) *account-level ban* → re-login is **useless** (the ban binds the account, not the token), and the only correct action is zero-touch waiting for the platform to lift it. Treating (b) as (a) is precisely how a retry loop keeps re-triggering a ban. So the mechanism is worthless without a **discriminator**, and the gateway already possesses it: *"the credential has provably changed and the node is still rejected"* — this **excludes** explanation (a), which leaves (b). This is the machine-readable form of the operator's question "现在受到风控的 LLM 能通过重新登陆恢复使用吗": for DeepSeek the answer is no.
    - **Evidence, reset per credential**: `CredentialRenewalTracker.note_auth_failure()` now returns whether the failure landed on a credential *different from the last one it recorded* — and it must decide this **before** overwriting the record, or the evidence destroys itself on every call. `CooldownTracker` keeps `_fresh_credential_rejected[provider]` as a counter, **reset to 1 (not incremented)** each time a newer credential appears: every renewed credential gets its own chance, so one earlier rejection can never accumulate onto a credential that has never actually been tried. Reaching `GATEWAY_BAN_INFERENCE_MIN_FAILURES` (default 2) applies an **auto lease**.
    - **Semantics distinct from all four existing avoidance kinds**: a soft cooldown is the gateway's own inference about *load*; an operator lease is a human declaration about *policy*; a credential outage is ring-wide about *capacity*; an auto lease is the gateway's own inference about *the account itself*. It is marked `source="auto"` in `QuarantineStore`, which is persisted per provider (dir `0o700` / file `0o600`), so a restart cannot launder an auto lease into an undeletable one, and `release_auto_lease()` structurally **cannot** release an operator lease — precedence runs one way only (an operator declaration always overwrites an auto mark, never the reverse; an unknown/missing source is conservative-`operator`). Duration `GATEWAY_AUTO_QUARANTINE_DURATION` (default 259200s = 72h), shorter than the multi-day manual leases because an inference deserves less authority than a human's.
    - **Self-clearing, because an inference must be revisable**: the whole justification for the lease is "we tried a renewed credential and it was still refused"; a *newer* credential invalidates exactly that evidence, so the auto lease is lifted automatically when the fingerprint moves on, the evidence map is cleared, and the node re-enters via the OPT-022 recovery probation. Without this one wrong inference would freeze a perfectly-repaired account for 72h. Operator leases are exempt: they are never auto-lifted, and the fingerprint-comparison logic never touches them.
    - **Zero-touch dispatch**: the auto lease rides the existing OPT-021 hard-stop (folding the lease into the cooldown reading means every gate — probe, refresh, conversation GC, healer election, routing — honours it with no extra wiring), so an inferred ban produces **zero upstream calls** at any point, including as a failover fallback. `GATEWAY_DISABLE_BAN_INFERENCE=1` disables inference (and it co-disables with quarantine/ledger, whose disable switches would leave the conclusion nowhere to live). Evidence, auto-lease fingerprints and the rejection counts persist across restarts, so a restart is never a bypass. Telemetry: `ban_inference` on `/v1/diagnostics`, `GET /v1/admin/ban-inference` for the report, `DELETE /v1/admin/ban-inference` to lift auto leases early once the operator confirms the platform has lifted the ban. See `tests/test_ban_inference.py`.

25. **Severity-Aware Avoidance Duration & Human-Gated Release (`providers/failover.py` / `providers/credential_renewal.py`)**:
    - **[OPT-029] The tier that requires a human had the least patience**: `record_failure` put `waf` and `ratelimit` in the *same* escalation branch (`base × 1.2**min(n-1, 3)`, capped by `GATEWAY_WAF_COOLDOWN_MAX` 900s), so a repeated captcha interception **saturated at ~78s on the 4th failure and never grew again** — the node was re-poked every ~78s forever — while `auth` (whose remedy is a trivial automated re-login) escalated to 24h. That is the semantics exactly inverted: per the OPT-023 dossier, `waf` is the *only* tier whose `auto_recovers` is `False` and whose remedy is a human completing a slider, yet it received the *most* frequent automated retries. Every such retry is another "automated attempt" on a captcha-flagged account — the same signature as the OPT-025 storm, but per-node and self-sustaining, and in direct conflict with the standing constraint of never deepening another vendor's risk score.
    - **Escalation**: repeated `waf` (≥ `GATEWAY_WAF_ESCALATION_MIN_FAILURES`, default 3) escalates by powers of two (`GATEWAY_WAF_LONG_COOLDOWN_BASE` 3600s × 2ⁿ, capped by `GATEWAY_WAF_LONG_COOLDOWN_MAX` 86400s), structurally identical to the auth tier (measured 45 → 54 → 3600 → 7200 → 14400 s). A *single* human-verification hit is never escalated, and a non-captcha risk hit keeps the legacy short cooldown. `ratelimit` is deliberately untouched: it is transient and self-healing, so "retry once it clears" *is* the correct recovery, and its short cooldown and cap are value-for-value what they were before — verified as the suite's first case.
    - **The release, without which the escalation is a dead end**: a long avoidance is only acceptable if a human can end it, and the only observable evidence that a human intervened is that the **credential file changed** (a completed `login.py`/slider necessarily refreshes the token, and `Session.save()` refreshes `captured_at`, so the fingerprint always moves). A WAF interception therefore records a credential baseline (`CredentialRenewalTracker.note_interception`) and the release path accepts `auth` **and** `waf` (`_RELEASABLE_BY_RENEWAL`) — without this half the escalated avoidance would be a permanent freeze, i.e. the self-lock OPT-026 already fixed wearing a different cause. `ratelimit` is never releasable (re-login means nothing there), an operator quarantine lease still wins over every release path, and a released node re-enters the OPT-022 probation so it is re-verified by a serial canary rather than flooded.
    - **The ban-inference discriminator is not polluted**: `note_interception` records *only* a baseline — it does **not** return "was this failure on a renewed credential", which is OPT-027's discriminator and is strictly scoped to 401s. Folding human verification into it would fire auto leases for an entirely different cause; `tests/test_waf_escalation.py` asserts the ban-inference path stays empty and no auto lease is applied.
    - **Dossier advice branches on the cause**: the OPT-023 cooling posture used to hand out one generic recommendation, so an escalated `waf` node inherited `ratelimit`'s "no human intervention needed" — telling the operator to wait out a node only a human can fix. The dossier now exposes `cooldown_cause` per provider and branches: `waf` → a human must complete the verification (`.venv/bin/python login.py <provider>`, and explicitly **do not** script the captcha); `auth` → re-login; `ratelimit` → no human needed and explicitly no re-login. Telemetry: `cooldown_cause` on the dossier entry. See `tests/test_waf_escalation.py`.
26. **Stable Per-Node Device Identity & Self-Consistent Client Hints (`providers/device_identity.py`)**:
    - **[OPT-030] The fixable half of OPT-024's systemic cause**: OPT-024 concludes that several different accounts intercepted inside one burst window cannot be independent — the root cause is *our own client footprint* (headers, UA, device params, egress IP, timing), where rotating nodes is useless and per-account avoidance actively harmful. Its remedy is a **global pacing slowdown**, which treats the symptom: the footprint itself is untouched. This optimizes a root cause inside that footprint that is both verifiable and repairable.
    - **Evidence (reproduced)**: `_make_provider` is called from `execute_chat`'s dispatch loop, so a **fresh provider object is constructed on every dispatch attempt** — and Kimi's `X-Msh-Device-Id` (plus `X-Msh-Session-Id`) and GLM's `X-Device-Id` (which also prefixes `X-Request-Id`) were built as `device_id or random.randint(...)` / `device_id or uuid.uuid4().hex`, with the session file's `device_id` empty (login only captures the ByteDance TEA `web_id`, for Doubao). So **every single upstream request from Kimi and GLM announced a brand-new device** (measured: three consecutive constructions gave three different ids). Qwen and Doubao are stable *with* a cookie, but in the env-token deployment the credential-renewal admin API explicitly supports, Qwen regenerated `x-device-id` per request, Doubao fell back to the **current millisecond**, and its `_fp` re-randomized per request.
    - **Why this is risk-control-grade, not hygiene**: "one account + one stable cookie/token + a different device on every request" is among the strongest automation signatures an anti-bot system can score. A real browser's device identifier is *constant* within a profile; it varying per request can only come from automation. It is also the *strongest* thing we could do to trip the four vendors the standing constraint says must be protected — Kimi and GLM are two of them.
    - **The fix — identity is minted once and reused forever**: `stable_device_id(key, generate)` persists per-node identities in `session/device_identity.json` (dir `0o700` / file `0o600`, POSIX atomic `os.replace` + `os.fsync`), so the caller's random expression runs exactly **once**; every later request reuses the stored value. It is **decoupled from credentials on purpose** — a real device is still the same device after a re-login, so a token refresh or re-login must *never* change it (this is a deliberately separate evidence chain from OPT-026/OPT-029's credential fingerprint).
    - **Zero regression by construction**: an explicitly passed `device_id` (the captured truth) and an identity already present in the cookie always win — the store only takes over the cell that *would have* been randomized. Identities are **node-scoped and mutually distinct** (a shared id would itself be a new correlation signal across platforms, i.e. exactly OPT-024's shared footprint) and slot-scoped within a node. Unreadable/corrupt storage degrades to the caller's generator without raising, and `GATEWAY_DISABLE_DEVICE_IDENTITY=1` restores the pre-fix behavior exactly. Diagnostics expose only a 6-char prefix plus age and counters (`created` / `reused` / `revived_from_disk` / `bypassed`) — device identifiers are the most sensitive field an anti-bot system keys on, so a screenshot or log line must not leak a complete one.
    - **Self-consistent client hints (same insight)**: GLM hardcoded `Sec-Ch-Ua: "Chromium";v="130"` alongside a *dynamic* `User-Agent`. It matched only because Playwright's bundled Chromium happens to be 130 — the moment the browser updates, the UA says Chrome/141 while the hint still claims 130, a **self-contradictory fingerprint** that modern anti-bot stacks cross-check. The hints are now derived from the effective UA (`Sec-Ch-Ua`, `Sec-Ch-Ua-Mobile`, `Sec-Ch-Ua-Platform`), and for a non-Chromium UA they are **omitted entirely** — which is what a real Firefox/Safari does, and therefore the only self-consistent choice. See `tests/test_device_identity.py`.
27. **Long-Avoidance Hard-Stop at the Dispatch Boundary (`providers/failover.py`)**:
    - **[OPT-031] The gap between OPT-021 and OPT-025**: the dispatch loop had exactly two pre-flight gates — OPT-021 blocks *operator/auto leases* (`is_quarantined`) and OPT-025 blocks a *whole-ring 401 outage* (`credential_watch`). Between them lies **a ring where every node sits in a long avoidance of mixed causes** (some escalated `waf`, some escalated `auth`, hours-to-days). `apply_pacing_and_acquire` only sleeps the *pacing interval* — it never waits out the cooldown — and `get_fallback_candidates` merely **demoted** cooling nodes, so every client request still walked all five nodes, producing several fresh interceptions for a request that could not possibly succeed. This is exactly the OPT-025 storm shape (the storm *is* the risk trigger), with the cause moved from 401 to waf/auth escalation.
    - **The design tension, and the only defensible discriminator — duration**: OPT-021 deliberately keeps soft cooldowns **demote-only** "so a ring where everything is briefly cooling can still make a last-resort attempt — availability is preserved". A blanket "all cooling → fail closed" would contradict that decision. The discriminator is *how long*: a **short** soft cooldown (rate-limit backoff, seconds-to-two-minutes) is worth one last-resort attempt; a **long** avoidance (escalated auth/waf, hours) is not — upstream has already answered with *repeated* interceptions.
    - **The threshold is a vacuum band, not a tuned constant**: the short-cooling max is the code-level cap `GATEWAY_WAF_COOLDOWN_MAX` (default 900s; the rate-limit exponential also saturates at `base × 1.2³`, deepest reachable 103.7s), and the escalation floor is `GATEWAY_AUTH_COOLDOWN_BASE` (default 1800s) with WAF escalation starting at 3600s. The band is `(900, 1800)` and `GATEWAY_LONG_AVOIDANCE_THRESHOLD` defaults to **1200**, its value **clamped** to `[short_cap + 1, escalation_floor - 1]` so a misconfiguration can neither invade the short-cooling band (eating OPT-021's last resort) nor reach the escalation floor (re-opening the storm). Both bounds are *strict* with a 1-second margin — taking the threshold as exactly 1800 was measured to flip the verdict immediately, because the escalated cooldown *is* 1800 and the read-back is 1799.99. `tests/test_long_avoidance.py::test_threshold_sits_in_the_gap` *proves* the band rather than assuming it.
    - **Semantics distinct from all neighbours**: a long avoidance is neither a lease (no human declared it, it is not account-level by itself) nor a credential outage (it is not ring-wide nor 401-only) — it is *the same node*, just given a duration long enough that touching it again is worse than waiting. `is_in_long_avoidance()` therefore treats it as a **hard block**, never a demote: long-avoidance nodes are excluded from `get_fallback_candidates` (short cooling stays demoted, unchanged), a long-avoiding primary is **redirected** to a healthy candidate, and if the ring has no non-avoiding member the request **fails closed** with `503 / err_type="ring_exhausted"` (Anthropic `overloaded_error`), **zero upstream calls**, and a message naming each node with its cause and remaining hours plus the per-cause remedy.
    - **The cause must not mislead the operator**: `long_avoidance_cause()` reports `ban` for anything holding a lease (re-login is useless — the ban binds the account) and only falls back to the soft-cooldown severity otherwise, so the advice never tells an operator to re-login against a banned node — the same class of error OPT-026/027/029 each fixed. `GET /v1/diagnostics` exposes `long_avoidance` (`enabled` / `threshold_seconds` / `avoiding` / `stats`), and the OPT-023 dossier gains a `long_avoidance` posture between `quarantined` and `cooling` with `dispatchable: false`, so the dossier never claims a node is dispatchable when the dispatch boundary hard-blocks it. `GATEWAY_DISABLE_LONG_AVOIDANCE_FAST_FAIL=1` restores the walk-the-ring behaviour exactly. See `tests/test_long_avoidance.py`.
28. **Zero-Upstream Dispatch Dry-Run (`providers/failover.py:audit_dispatch`)**:
    - **[OPT-032] The confirmation cost after every operator action**: the whole avoidance line (OPT-021…031) makes the gateway *refuse* to dispatch to a banned node, but nothing let an operator confirm that a declaration had actually taken effect without sending a real request and observing which nodes got touched — which is exactly the "spend an upstream touch to buy an answer" habit the line exists to eliminate. This was measured, not hypothesised: after declaring the DeepSeek ban, confirming it required a hand-written script that injected a fake provider factory and posted through `TestClient`. That confirmation is a *daily* action (after every lease change, env change and restart), and none of the five admin endpoints answers it — they all report a node's *posture*, whereas the question is "what is this request's dispatch decision right now".
    - **Read-only, zero upstream calls, and provably so**: `audit_dispatch(provider_key, wire_model)` never instantiates a provider — it only asks the **same gate predicates** the dispatch loop asks, in the **same order** (ring-wide credential outage → operator disable `DISABLED_PROVIDERS` → operator/auto lease → long avoidance), because "which gate fires first" is itself the information an operator needs. `GET /v1/admin/dispatch-audit?model=<alias>` resolves the alias and returns `upstream_calls: 0`, per-node `blocked_by` (`credential_outage` / `disabled` / `quarantine` / `long_avoidance`) with remaining time and cause, plus `predicted_primary_dispatchable` / `predicted_redirect_target` / `predicted_fail_closed` / `predicted_err_type`. `tests/test_dispatch_audit.py::test_endpoint_never_instantiates_a_provider` proves the zero-upstream claim *constructively* by swapping `_make_provider` for an implementation that raises.
    - **No drift, by construction and by test**: the redirect target is taken from the real `get_fallback_candidates()` — **not** from "the first dispatchable ring member". Measured: those differ, because the candidate list is sorted by `(cooldown, risk level, failure count)`, so `glm` can precede the ring-earlier `qwen`; the first version of this feature predicted `qwen` while the real dispatch served `glm`. The suite now asserts the prediction against what `execute_chat` actually does — both the redirect target (from the observed touched-node set) and the thrown `err_type` / status — so a dry-run that stops matching reality fails the build instead of becoming a more convincing lie. For the same reason the audit **raises** on an unresolved model alias rather than silently answering about a provider key that does not exist (which would report a banned node as dispatchable).
    - **Scoped honestly rather than completely**: it deliberately does not simulate load-balancer selection or session affinity, so the fields are named `predicted_*` and the payload carries a `scope_note` saying exactly that. Re-implementing each protocol's pre-dispatch pipeline here would recreate the "documented behaviour drifts from real behaviour" defect this codebase keeps fixing; saying clearly what it does not cover is the better trade.
    - Idempotent and side-effect-free (verified by `test_audit_is_read_only`: no lease changed, no cooldown reset, no ledger append), so it is safe on any diagnostic path.

29. **Single Gate Definition & Operator-Disable Hard-Stop (`providers/failover.py:evaluate_dispatch_gate`)**:
    - **[OPT-033] The bug OPT-032's own dry-run exposed — a gate with two copies**: OPT-032 made "preview == dispatch" a property enforced by *tests* (predicted redirect X ⇒ real dispatch must serve X). That is one step better than two code paths that happen to agree, but tests only cover the cases you thought of. This one was missed and found by measurement: `execute_chat` had **no gate at all** for `DISABLED_PROVIDERS` (the operator's declaration that a node is not part of this deployment), while the dry-run reported such a node as `blocked_by="disabled"` and predicted a redirect to `glm`. Reproduced: `DISABLED_PROVIDERS=deepseek` + `execute_chat("deepseek", …)` dispatched **deepseek** (`TOUCHED=['deepseek']`) — the request went straight into a node the operator had explicitly disabled. The load balancer and session affinity both honoured it; the dispatch boundary, which is the last line and must be self-protecting (the OPT-021 rationale verbatim), did not. The cause was not a missing `if`: the gate **order** existed in two copies, one in the dispatch loop and one in `audit_dispatch`.
    - **The fix is to have one copy**: `FailoverRouter.evaluate_dispatch_gate(provider_key, outage_active)` is now the single definition of the gate order (ring-wide credential outage → operator disable → operator/auto lease → long avoidance), returning `dispatchable` / `blocked_by` / `remaining_seconds` / `cause`. `execute_chat`'s loop selects its handling branch from `gate["blocked_by"]` instead of re-deriving the predicates, and `audit_dispatch` asks the same function — so "preview == dispatch" is now **structural**, not merely tested. `tests/test_dispatch_gate.py::test_dispatch_decision_is_derived_from_the_single_gate_definition` proves the structural claim the only way that really proves it: it **rigs the single gate** to claim a healthy node is blocked and asserts the real dispatch then refuses that node — a dispatch loop that had kept its own copy would sail past the tampering and fail the test.
    - **The new gate is a hard block, never a demote**: `DISABLED_PROVIDERS` is an operator declaration, the same authority tier as a quarantine lease, so it follows OPT-021: a disabled primary is **redirected**, disabled nodes are excluded from the candidate set, and if the ring holds no non-disabled member the request **fails closed** with `503 / err_type="disabled"` (`overloaded_error` in the Anthropic protocol, alongside `quarantined` / `ring_exhausted`), **zero upstream calls**, and a message naming the effective disabled set. Availability is preserved by construction: only an *explicit* declaration blocks, and short soft coolings keep OPT-021's demote-only "last resort".
    - **One reading per configuration**: `server._is_provider_healthy` (the session-affinity availability check) used to parse `DISABLED_PROVIDERS` **itself**, while `CooldownTracker` snapshotted the same variable into a set at construction — the same configuration interpreted in two places, which disagree the moment it changes inside a running process (the defect class this codebase keeps fixing, cf. OPT-026/029/030). It now delegates to `CooldownTracker.is_disabled()`, which is the single judge and takes the **union** of the programmatic set and the live env read — merging conservatively (a second declaration can only disable more), deliberately preserving the live-env behaviour that `tests/test_affinity.py`'s node-handoff case depends on.
    - Telemetry: `/v1/diagnostics` gains `dispatch_gates` (`disabled_providers` — the effective union — plus `gate_blocks`, a per-gate refusal histogram, so "which gate is carrying the refusals" is observable rather than inferred from logs, and `stats` = redirects / zero-upstream fast-fails). `audit_dispatch` members also carry informational `disabled` / `quarantined` / `in_long_avoidance` flags, so a node whose own state is masked by the ring-level credential-outage gate is still visible. See `tests/test_dispatch_gate.py` (10 cases).

30. **Operator-Disable Propagation to Every Upstream Self-Maintenance Channel (`providers/failover.py:touch_avoidance_reason`)**:
    - **[OPT-034] The same declaration, honoured by only some channels**: `DISABLED_PROVIDERS` is the operator's statement that a node is not part of this deployment. The dispatch boundary honours it (OPT-033) and so does the health probe (OPT-012) — but the other three self-maintenance channels only asked about *cooldown*, never about *disable*. A node declared out of scope that happened to hold no cooldown was therefore still touched upstream for real: a startup silent token refresh (**a real upstream login request**), the deletion of an anonymous call's temporary conversation (**a real delete request**), and the election of a repair model for self-healing (**a real upstream completion**). Reproduced: with `DISABLED_PROVIDERS=kimi` and no cooldown, `_refresh_stale_provider("kimi", …)` really invoked the refresher (`[网关] kimi 令牌已超过 6h，尝试静默刷新…`). An account the operator had already taken out of service kept being touched — precisely the failure mode the standing "never touch a banned/withdrawn node" constraint exists to prevent.
    - **One declaration, one judge**: `CooldownTracker.touch_avoidance_reason()` is the single judgement for all background touches — `disabled` → `quarantined` → `cooldown`, heaviest-wins, `""` meaning "may touch". All four channels (probe, token refresh, conversation GC, healer election) evaluate it, and it is wired once in `server.py`. This is the OPT-020 pattern again (fold the declaration into the reading so every gate honours it with zero extra wiring), applied to a declaration that had been left out.
    - **Distinct from every neighbour, and *stricter* than the dispatch gate in exactly one place**: a background touch is never worth risking an avoiding node for, so the short soft cooldown that the dispatch boundary deliberately leaves as a "last resort" (OPT-021) blocks here unconditionally. The **cause is returned honestly** rather than collapsed into "cooling": disabled is lifted by editing configuration, a lease by a human revoking it, a cooldown by waiting — conflating the three is the "misleading the operator" defect class this codebase keeps fixing (OPT-026/027/029/031).
    - **Disabled is not deferred; cooling is**: a cooling node is waiting on a window that will expire, so it re-enters a bounded deferred-retry queue (OPT-013/017). A disabled node is waiting on a human to change configuration — there is no window to wait for — so a disabled provider is never refreshed and never queued, and re-enabling it simply means the next startup refreshes it. This is why the verdicts must stay distinguishable rather than both reporting `cooling`.
    - **One reading per configuration, again**: `HealthMonitor.is_disabled` used to read `DISABLED_PROVIDERS` **itself** — a third copy of the same configuration, disagreeing with the tracker's set the moment the set changes in-process. It now receives the tracker's `is_disabled` as an injected gate (falling back to the env read when constructed standalone, so the class stays usable outside the gateway).
    - **The cooldown master switch must not release a disabled node**: `GATEWAY_DISABLE_COOLDOWN_GATE=1` means "revert to no cooldown awareness", but operator-disable is a deployment declaration, not cooldown awareness — the switch silently releasing a node the operator had declared out of service was the trap. Disabled judgements are therefore *not* covered by that switch; lease/cooldown judgements still are, value-for-value as before.
    - Telemetry: `touch_gates` on `/v1/diagnostics` (`blocked_by_cause` — a refusal histogram per cause; each call site asks the judge exactly when it is about to touch upstream, so the histogram reads as *blocked touch attempts*, not node counts), and conversation GC's `deferred_by_cooldown.per_cause` splits deferrals by cause. `GATEWAY_DISABLE_CONVERSATION_GC_COOLDOWN_GATE=1` still reverts the GC gate; without an injected cause gate the GC falls back to the cooldown float gate and reports `cooldown`, value-for-value as before. See `tests/test_disabled_propagation.py` (9 cases).

31. **Dossier/Posture Agreement with the Dispatch Fact (`providers/risk_dossier.py:derive_posture`)**:
    - **[OPT-035] The same "the dossier lied" bug as OPT-031, one cell over**: the dossier's job (OPT-023) includes answering "can this node be dispatched right now", and the dispatch boundary is the only source of that fact. OPT-031 found the *long-avoidance* cell where the boundary hard-blocked a node while the dossier reported `cooling (dispatchable)`, and added a posture. The **operator-disable cell was missed in exactly the same way**: the boundary hard-blocks it (OPT-033) while the dossier reported `posture=clear, dispatchable=True`. Reproduced with `DISABLED_PROVIDERS=qwen`, no lease, no cooldown: `dispatch gate → {'dispatchable': False, 'blocked_by': 'disabled'}` vs `dossier posture → clear`. An operator reading the dossier concludes a node they had declared out of service is healthy and available.
    - **Posture vocabulary gains `disabled`, ordered danger-first**: `POSTURE_ORDER` is `quarantined → disabled → long_avoidance → cooling → probation → watch → clear`. The order is deliberate, not alphabetical: a node that is **both banned and disabled** (this machine's DeepSeek) must report `quarantined` first, because if it reported `disabled` the operator's natural reaction is "then just lift the disable" — re-dispatching a node upstream has banned. Reporting the ban gives the correct action (wait for the platform), and `disabled` stays visible as an informational per-node flag (`entry["disabled"]`) and in `POSTURE_LABELS`.

OPT-031 and OPT-035 were both a single missed cell; a property test means the next missed cell turns red instead of waiting for an operator to measure it. The one deliberate exception — a **ring-wide credential outage** (OPT-025) is a ring-level fact while the dossier is per-node, so the dossier reports `clear` while the gate reports `blocked_by=credential_outage` — is asserted explicitly rather than hidden, so it can neither be mistaken for a bug nor silently change.
    - **The verdict branches on the cause, and never recommends a useless remedy**: `AVOIDANCE_MATRIX["disabled"]` answers `technically_bypassable: False`, `recoverable_by_relogin: **False**` (a configuration declaration is not a credential problem — re-login cannot help), `auto_recovers: False`. `_avoidance()` places the disabled branch *after* the quarantine branch so a leased node keeps its `ban` advice, and `recommended_actions` for `POSTURE_DISABLED` names `DISABLED_PROVIDERS` and says re-login is useless — the recurring "misleading the operator" defect class (OPT-026/027/029/031/034) closed in the dossier too. `entry["disabled"]` is informational only and never mutates risk state; the whole query path stays read-only.
    - Telemetry: `posture_counts` on the dossier summary gains a `disabled` bucket, and `AVOIDANCE_MATRIX` gains a `disabled` row — both are part of the `/v1/admin/risk` and `/v1/diagnostics` surface, and `tests/test_risk_dossier.py` pins them so a vocabulary change cannot slip through unnoticed. `GATEWAY_DISABLE_RISK_DOSSIER=1` still disables the whole surface. See `tests/test_dossier_dispatch_agreement.py` (6 cases).

32. **Tool-Loop Closure & Anti-Fabrication (`providers/base.py`, `providers/tool_streamer.py`)**:
    - **[TOOL-LOOP] The loop had two open ends, and both were silent.** (a) `flatten_messages` read only `content` and never `tool_calls`, so an agent's second round sent a tool result for a call the model could not see itself having made; `continuation_content` unconditionally took the last `user` message, so in continuation mode the tool result was skipped entirely and the *previous question* was re-sent — the loop could never close. (b) `finalize()` parsed without the declared-name allowlist, so a name the streamer had already rejected could be re-accepted at the end of the stream, producing a call the client cannot execute while swallowing the tail as already-emitted text. Both are fixed at the source, with the same allowlist threaded through every parse site.
    - Anti-fabrication is three layers, each necessary: a **format whitelist** (`json` stays allowed — real models do emit ```` ```json ```` for calls; `python`/`ts` are rejected), a **strict shape** check (`_extract_single_tool_strict`), and a **declared-name allowlist**. Format alone cannot work: disabling `json` would break normal calls, and keeping it lets any JSON block look like a call. A rejected call is returned to the user as text rather than disappearing.
    - The behavioural claim is asserted end-to-end in `tests/test_agent_loop.py`, on **the prompt upstream actually receives** — not on the gateway's own response object. A gateway that returns a perfect `tool_calls` payload while upstream never saw the call still fails the user's agent.

32b. **Streaming Item Lifecycle (`server.py`, all three protocols)**:
    - **[ANTHROPIC-STREAM] / [RESPONSES-STREAM] The same bug, twice, in two protocols.** Anthropic's tools path closed the thinking block when switching to text but not the text block when the model thought again, so an alternating turn emitted `start(1,text)` immediately followed by `start(1,thinking)` — one index opened twice and never closed in between. Responses' path went further: every index increment was deferred to the end of the stream, so a reasoning item and a message item both claimed `output_index 0`, and a *second* reasoning stretch was appended to a message item that already carried text. Clients archive content by index, so duplicate indices overwrite each other — the symptom is "the agent's output is missing half of it", with no error anywhere.
    - Reasoning that reappears after text is not an edge case: it is what a reasoning model does on every tool turn. Both paths now close the current item before opening the next (buffer cleared per item, so a second reasoning item does not inherit the first one's text) and give each item its own index in arrival order.
    - The invariant is asserted structurally, not case by case: `_assert_item_lifecycle` (Responses) and `_assert_block_lifecycle` (Anthropic) check, for every case in both suites, that indices are unique and sequential, that deltas only land on an open item of the matching kind, that `done` content equals the concatenated deltas of that same item, and that items close in order.

33. **Streaming Heartbeat (`providers/stream_keepalive.py`)**:
    - **[STREAM-KEEPALIVE] The silence between two bytes is the failure.** All six `StreamingResponse` exits were bare generators: whatever the upstream web UI did between "request accepted" and "first character" (tens of seconds, and longer for reasoning models), the client saw nothing. Codex CLI / Claude Code judge "connection opened, no bytes" on a short window and reconnect or give up — the user sees "the gateway connected but the agent says nothing" while the gateway log looks perfectly healthy.
    - `sse_keepalive()` yields `: keepalive` comment frames during silence. The `:` prefix is a spec-level SSE comment, so all three protocols' clients must ignore it and no event stream can be polluted; it is still real bytes, so it resets the client's idle timer. Default 15s (`GATEWAY_STREAM_KEEPALIVE`), 0 disables to the byte-identical old behaviour.
    - **The implementation detail is the point**: the obvious `await asyncio.wait_for(iterator.__anext__(), timeout)` is *wrong* — on timeout it cancels `__anext__`, which is thrown into the async generator body and closes it, so **every chunk after the first silence is permanently lost**. The first version did exactly that and `tests/test_stream_keepalive.py` caught it dropping the second and third chunks. The pull now lives in a task that is never cancelled mid-stream (only in the `finally`, for the disconnect path), and the timeout merely emits a frame. Upstream exceptions still propagate — a heartbeat must never disguise a real failure as "still thinking".
    - All six exits are structurally asserted to be wrapped (`test_all_streaming_responses_are_wrapped` fails when the exit count changes), because six hand-wired call sites is precisely the shape of change that goes half-done.

34. **Agent-CLI Model Alias Coverage (`server.py:resolve_model`)**:
    - **[AGENT-LOOP] A 404 at handshake is indistinguishable from "the gateway does nothing".** `resolve_model` matched OpenAI names from a fixed table; `gpt-5`, `gpt-5-codex`, `o4-mini` and `codex-mini-latest` — what current Codex CLI builds actually request — were absent, so the client got `404 model_not_found` and never sent a single request. The table gained those names, and unknown `gpt-*` / `o*` / `codex*` ids now fall back to a tier by prefix. The failure direction is deliberate: a fixed table can never keep up with vendor releases, so an unrecognised id is served at the most plausible tier rather than refused — a degraded answer beats a handshake rejection.

34b. **`tool_choice` Enforcement & Agent-History Fidelity (`providers/tool_streamer.py:resolve_allowed_tools`, `providers/responses_compat.py`)**:
    - **[TOOL-LOOP] A constraint that lived only in the prompt is not a constraint.** `tool_choice` was translated into one sentence of system prompt ("Do not call any tool in this turn") and nothing else; the parser still admitted every declared tool. Web models do not reliably obey prompt constraints, so a `tool_choice:"none"` request that came back with a ```` ```tool_call ```` block still returned `tool_calls` / `tool_use` / `function_call` — measured on all three protocols (`finish_reason: tool_calls` with `tool_choice:"none"`). The client, following its own contract, never executes that call, so the whole turn is dead. Enforcement now lands on the **parse**: `resolve_allowed_tools(tools, tool_choice)` returns the effective allowlist (`none` → empty set, a named tool → just that name, `auto`/`required`/unknown → all declared names), and all six parse/stream sites ask it instead of `tool_names_of`. The prompt directive stays, as the thing that lowers the probability; the allowlist is what guarantees the outcome. A tool call filtered by the allowlist is returned to the user as text, never silently dropped — the same rule as an undeclared name.
    - **Fail-open on shapes, fail-closed on semantics**: an unrecognisable `tool_choice` shape, or a named tool that was never declared, keeps the full declared set rather than narrowing to nothing — narrowing there would turn a perfectly serviceable turn into an empty one. `none` is the only value that empties the set, because it is the only one that means "no tools at all".
    - **[AGENT-LOOP] Codex replays its own reasoning items, and they were arriving as user input.** The Responses input converter's fallback branch serialised any unknown item to JSON, so `{"type": "reasoning", "id": "rs_1", "summary": [...]}` — which Codex sends back verbatim in the next turn's `input` — reached the upstream model as a **user message containing raw JSON**. Every turn paid tokens for a blob the model could not interpret, and the model's own prior thinking was replaced by noise. Reasoning items now render as an assistant `<thinking>` block (empty ones are skipped), and `item_reference` / `compaction` — pointers that cannot be resolved without a response store — are skipped instead of being dumped as content. `tests/test_agent_loop.py::test_reasoning_replay_is_not_a_user_message` asserts no `{"type": "reasoning"` text can reach the upstream prompt.
    - **[AGENT-LOOP] `reasoning: {"effort": ...}` was silently dropped.** Codex CLI sends the reasoning intent as an object (`{"effort": "high", "summary": "auto"}`), while the gateway only read the older flat `reasoning_effort` string. Code models such as `gpt-5-codex` also do not match the `o1/o3/o4` reasoning prefixes, so there was no fallback: "think before acting" was lost entirely. Both spellings are now read (`minimal` included), pinned by `test_codex_reasoning_object_enables_thinking`.
    - **[TOOL-LOOP] The same defect class, one field over: `parallel_tool_calls` was never read at all.** All three protocols let a client declare that only one tool call may come back in a turn — OpenAI/Responses `parallel_tool_calls:false`, Anthropic `tool_choice.disable_parallel_tool_use:true` — and the gateway ignored the field on every path. Measured: when upstream returned two ```` ```tool_call ```` blocks, all three protocols returned two calls. For an agent client that cannot execute calls in parallel or merge their results, the second call is one it neither expected nor will run, so the tool-result pairing breaks and the turn is wasted. `parallel_calls_disallowed()` decides, `format_tools_system_prompt(parallel_allowed=...)` adds an explicit "Do NOT emit more than one tool call in a turn" directive, and `cap_parallel_tool_calls()` trims to the **first** call at all six parse/stream collection points.
    - **First, not none**: keeping the first call is what makes the constraint useful — the model's current intent is executed, and the client's next turn continues the remaining work; dropping every call yields a turn in which nothing happened. The rule about which values tighten is the `resolve_allowed_tools` rule exactly: only an explicit `false` / `true` disables, and an absent or unrecognisable shape leaves parallel calls allowed (fail open, zero regression) — pinned by the trailing no-flag assertion in the same test.
